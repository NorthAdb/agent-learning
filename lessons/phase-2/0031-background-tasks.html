s11：慢命令先交回编号，结果以后再送回来

s10 把任务进度写成了磁盘上的图，但图上的每一步仍然是同步工具： 一条 bash 不返回，整轮循环就停在那里，同一次回复里的下一个工具也不会开始。 本课只解决这一件事：模型明确要求时，把这条 Bash 放进后台线程， 当前工具调用立刻交回一个编号；命令真正结束之后，再在后续轮次把结果通知进对话。 大目标还是造 harness：慢操作不必把整轮循环堵住。

为什么现在学？

读一个小文件、跑一次 git status，主线程干等一会儿并不显眼。 安装依赖、跑完整测试、构建项目可能要几分钟。在这条命令返回之前， Harness 不能执行当前这条回复里的下一个工具，也不能进入下一轮模型调用。

如果后面的工作和这条命令无关，继续干等就没有必要。 测试已经在跑的时候，本来还可以读文档、列文件。同步执行会把整轮停在这次 Bash 上。

s10 回答的是「哪一步现在能不能开始」。它不让慢命令和循环重叠。 s11 回答的是「这条命令能不能先交回编号」。两件事叠在不同层： 任务图记录进度，后台执行只改 Bash 的等待方式。本章代码甚至没有把 s10 的六个任务工具带进来， 工具表仍是 s04 的五个：bash、读、写、改、glob。

问题陈述： README L13–19。 工具数量： README L149–150。

一次完整运行

README 用三轮把形状走完。编号在运行时递增，这里沿用它的 bg_0001。 「轮」指循环回到模型之前的那一次；不一定是你又敲了一句新问题。 

第 1 轮  模型发出 bash，run_in_background=true
  主线程  PreToolUse 审批通过
          start() 记下 bg_0001，守护线程开始跑 npm install
          tool_result: "[Background task bg_0001 started] ..."
          模型可以说：先去读配置，安装结果以后再看

第 2 轮  模型发出 read_file，这是快操作
  主线程  同步读完 package.json
          tool_result: 文件内容
          此时安装可能还没结束，完成队列是空的

第 3 轮  再次调用模型之前
  主线程  collect() 发现 bg_0001 已完成
          把 <task_notification> 贴进上一条 user 消息
          模型同一次请求里看见：文件内容 + 安装通知

一句话：这次工具调用只承诺「已经开始」；命令输出是以后的另一段文本， 而且要等循环下一次准备叫模型时才送进去。

同一条剧本： README L118–136。

同一次回复里的两个工具

模型有时会在同一条助手回复里同时发出「后台安装」和「读 package.json」。 参数在任何一个工具执行前已经写死。这和 s10 的两阶段建图是同一条协议限制。 差别是：后台启动会立刻返回，所以主线程可以接着执行这条回复里的下一个工具，不必等安装结束。 

助手回复里已经有两个 tool_use
  1. bash("npm install", run_in_background=true)
  2. read_file("package.json")

主线程按顺序执行
  启动后台线程，马上得到占位结果
  接着同步读文件
  两条 tool_result 一起追加

模型要到下一轮请求才同时看见这两条结果
它不能在「读文件正在执行」的中途插一句新的想法

所以「边等边读」是 Harness 在继续干活，不是模型在命令运行期间并行思考。 循环确实会按顺序执行同一条回复里的工具： code.py L483–491。

结果会在两个时刻被看见

inject_background_results 只出现在 agent_loop 每次调用模型之前。 后台线程完成时只是把编号放进 _ready，没有人去打断正在等你打字的提示符， 也没有人去打断已经发出的那次模型请求。

完成发生的时候通知什么时候进对话
同一次提问里，模型还在继续调工具 下一次 messages.create 之前。通知贴在上一条 tool_result 用户消息后面。
模型已经不再调工具，循环回到 s11 >> 你再输入一句、再次进入 agent_loop 的开头。通知贴在这句新输入后面。
你直接退出，进程结束 不会再注入。守护线程也不保证把命令跑完。

注入点： code.py L461–464。 README 写明后台结果不会主动唤醒 Agent： L116。

状态放在哪一层？

位置保存什么谁看得到生命周期
占位 tool_result 「bg_0001 已启动」 下一轮模型，作为这条 tool_use 的唯一结果 留在这次 messages 里
BackgroundManager.tasks 编号、原 tool_use_id、命令、状态 只有进程内的管理器。本章没有列出后台任务的工具 收集后从字典里删掉；进程退出即丢失
_ready 队列 已经跑完、还没送进对话的编号 主线程在下次注入时取走 取走后清空
<task_notification> 状态、命令、最多 500 字摘要 模型，作为稍后的文本块 写进 messages 之后，登记表里的那条就删了

和 s10 对照：任务图的 JSON 重启还在；后台编号只活在这次进程里。 文件落盘回答「进度还在不在」，内存队列回答「这条命令的输出还没送进对话」。

规则先看三条小例

例 1：布尔真，不是「看起来像真」

should_run_background("bash", {"command": "pip list", "run_in_background": True})
  → True     进后台

should_run_background("bash", {"command": "pip list", "run_in_background": False})
  → False    主线程同步等

should_run_background("bash", {"command": "pip list"})
  → False    缺省也是同步。schema 不要求这个参数

should_run_background("bash", {"command": "npm install", "run_in_background": "true"})
  → False    字符串不是布尔真。不会因为命令像安装就放后台

should_run_background("read_file", {"path": "a.py", "run_in_background": True})
  → False    只有 bash 可以

判断用的是 is True，不是 Python 里「非空即真」的那种真值。 1 和 "true" 都过不了。 出处： code.py L403–407。 README 明确不再按关键词猜测： L54。

例 2：一条工具调用只有一条结果

tool_use id = toolu_01
  立刻得到 tool_result
    tool_use_id = toolu_01
    content     = "[Background task bg_0001 started] The result will be collected on a later turn."

后来的用户消息里另有一段文本
  <task_notification>
    <task_id>bg_0001</task_id>
    <status>completed</status>
    ...
  </task_notification>

第二段没有 tool_use_id。 管理器内部虽然记下了原来的 block.id，收集时不把它写进通知。 一个 tool_use 仍然只对应一个 tool_result。 出处： README L92， 登记 code.py L337–341， 通知正文 L386–392。

例 3：同一次退出码，两套字段各说各的

命令结果status摘要正文

例 4：run_bash 自己不会开线程

def run_bash(command: str, run_in_background: bool = False) -> str:
    return _format_bash_result(*_run_bash_process(command))

这个函数收下 run_in_background，然后完全不用它。 谁调用它，谁就在当前线程里等到命令结束或超时。 后台分叉发生在 execute_tool：条件成立时它调用 start_background_task， 根本不会进入 run_bash。 若你在别的地方直接 run_bash("sleep 5", run_in_background=True)，它仍会干等 5 秒。

细节实现

先审批，再决定要不要启动

execute_tool(block):
  1. PreToolUse          权限和日志。拒绝则立刻返回说明文字
  2. should_run_background
       真 → start()，占位字符串
       假 → call_tool()，其中 bash 会同步跑完
  3. PostToolUse         看见的是上面那个字符串，不是命令的完整输出
  4. 这个字符串成为唯一的 tool_result

拒绝发生在第 1 步时，函数直接返回，不会启动线程，也不会跑 PostToolUse。 因此被拒绝的命令没有 bg_id。 需要你在终端回答 Allow? [y/N] 的命令，会先把主线程停在这个提问上； 你回答允许之后，线程才启动。后台不等于跳过审批。

后台路径的 PostToolUse 收到的是那句很短的占位文字。 large_output_hook 的 10 万字符警告看不到命令本身的输出。 命令输出要到通知的 summary 里才会出现，而且最多 500 字符。

执行顺序： code.py L438–456。 权限钩子仍是 s04 那一套，挂在 PreToolUse： L301–304。 大输出钩子： L272–278。

start：先登记，再启动，锁不罩着命令

start 只接受 bash，而且命令必须是非空字符串。 空命令或别的工具名会抛 ValueError。 execute_tool 接住它，把 Error: ... 当成这次的工具结果，不会留下半个编号。

编号在锁里递增：bg_ 加上至少 4 位数字，所以第一个是 bg_0001。 同一把锁还保护 tasks、results 和 _ready。 锁（threading.Lock）是互斥：同一时刻只有一个线程能待在 with self._lock 里面。 0016 讲过它。这里拿锁只为了改登记表；thread.start() 在锁外面，命令更在另一条线程里。 

with lock:
    编号加一
    tasks[bg_id] = {tool_use_id, command, status: "running"}
# 锁已经放开
thread = Thread(target=_run, args=(bg_id, command), daemon=True)
thread.start()
print started
return bg_id

若 start() 本身失败，刚记下的那条会从 tasks 里删掉，避免留下永远停在 running 的编号。 线程是守护线程：你退出主程序时，它不会把进程留住。 Python 文档 说明进程关闭时守护线程会被直接停掉，不保证把任务做完。

code.py L327–355。

collect 与注入

后台线程跑完后，在锁里把状态改成 completed 或 failed， 把格式化后的全文放进 results，再把编号追加到 _ready。 主线程的 collect 一次取走队列里全部已完成编号，拼好通知，然后清空队列。 取走的同时把 tasks 和 results 里的对应项删掉。 所以通知送出之后，管理器里就不再留着这条任务。

通知是拼出来的字符串，不是有解析器的 XML。模型把它当文本读。 summary 只保留结果前 500 个字符。进程里那份输出最早在 _run_bash_process 已经截到 5 万字符。

inject_background_results 没有通知时什么也不改，返回 0。 有通知时，如果 messages 最后一条已经是 user：

  • 内容是列表：把通知文本块追加到这个列表末尾。工具结果和通知可以在同一条用户消息里。
  • 内容是字符串：改成「原文字」加通知块。这就是你再次输入一句时的形状。

最后一条不是 user 时，才新追加一条用户消息。 正常循环里，工具结果刚刚追加过，最后一条就是 user，所以走追加，不另起一条。

收集： code.py L374–395。 注入： L418–435。

进程组清理不是沙箱

每条命令用 subprocess.Popen(..., start_new_session=True) 启动。 新会话在这里的意思是：这个 shell 成为自己进程组的头，方便以后按组发信号。 命令结束、超时，或者进程收到 SIGTERM、正常退出时， _stop_process_group 会向这个组先发 SIGTERM 再发 SIGKILL。

README 把边界写死了：这只是生命周期清理，不是沙箱。 命令内部如果再为自己新建会话，那个进程可以离开原来的组，清理就够不着它。

os.killpg 和 signal.SIGKILL 是 POSIX 接口。 Python os.killpg 标明仅 Unix。Windows 原生解释器上没有这组名字。 清理写在 _run_bash_process 的 finally 里，所以每条命令结束都会走到。 若你在 Windows 上看到通知摘要是 AttributeError 提到 killpg 或 SIGKILL， 那是收尾代码在这个系统上失败，不是「没有进入后台」。 终端里仍应先出现 [background] started bg_0001。 要看完整命令输出，用 WSL 或别的 Unix 环境跑同一份 code.py。

清理函数： code.py L57–81。 启动参数： L86–96。 README 的沙箱边界： L81。

观察一：先看见编号，再看见通知

Run a short sleep in the background, then list all Markdown files

期望终端先打印 [background] started bg_0001， 工具结果是占位句子而不是 sleep 的输出。 glob 或读文件不应被这个 sleep 堵住。 过一会儿，在下一次模型调用前，应出现 [background] collected bg_0001: completed， 对话里有一段 <task_notification>。 若模型第一轮就停下来，通知会等到你再发一句才出现。这是代码的行为，不是漏收集。

观察二：不写布尔真，安装也会堵住

看模型发出的参数里有没有 "run_in_background": true。 没有的话，pip list 会占住主线程，直到它返回；这仍然符合本章规则。 系统提示要求把独立命令放进后台，但代码不会替模型改参数。

观察三：审批仍在主线程

不要真的跑破坏性命令。只要记住顺序： 命中拒绝名单的 bash 在 PreToolUse 就返回，终端没有 [background] started。 需要你确认的命令，会先问 Allow?，你回答之后才可能看到编号。

常见坑 + 边界

  • 命令里有 install、build、test 就会自动后台：不会。只有布尔真。
  • 字符串 "true" 或数字 1 也算：不算。判断是 is True。
  • 读文件也可以 run_in_background：不可以。条件里写死了工具名是 bash。
  • run_bash 看到真就会自己开线程：不会。它忽略这个参数，始终同步。
  • 占位结果之后还会用同一个 tool_use_id 再交一条结果：不会。通知是后来的文本。
  • 命令一结束，模型马上被叫醒：不会。只在下一次调用模型之前收集。
  • 模型停在提示符上时，完成结果会自己再开一轮：不会。要等你再输入，或模型自己还在调工具。
  • 后台就可以绕过权限：不能。审批在主线程，而且发生在 start 之前。
  • PostToolUse 能看见命令的完整输出：后台这条看不见。它看见的是占位句子。
  • 超时算成功，因为退出码是空：状态是 failed。空退出码只影响要不要再包一层 “exited with status”。
  • 通知里有 5 万字的全文：没有。summary 最多 500 字符。
  • bg_id 会写成 .tasks/*.json：不会。本章登记表只在内存里，也没有任务图工具。
  • 进程组清理等于沙箱：不等于。另建会话的子进程可以离开这个组。
  • 同一条回复里的后一个工具必须等后台命令结束：不必。启动立刻返回，主线程继续执行后面的工具。模型仍要等整批结果一起回来才看见。

过关标准

  • 能用一句话区分 s10 任务图和 s11 后台执行：一个把进度和依赖写成文件，一个让明确要求的 Bash 先交回编号。
  • 能说出进入后台的唯一条件：工具名是 bash，且 run_in_background is True。关键词、字符串 "true"、其他工具都不算。
  • 能按顺序讲出 execute_tool：先 PreToolUse，再分叉，再 PostToolUse。拒绝没有 bg_id，钩子看见的是占位句子。
  • 能说明 run_bash 忽略后台参数；分叉在调用它之前完成。
  • 能区分占位 tool_result 和 <task_notification>：前者配完这一次 tool_use，后者是稍后的文本，不带原来的 tool_use_id。
  • 能说明通知只在下一次调用模型之前注入；模型已经停住时，要等下一次进入 agent_loop。
