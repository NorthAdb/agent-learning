s07：需要时再加载技能

s06 解决了“一个任务太大，交给干净上下文”的问题；但即使上下文是干净的， system prompt 仍可能被一大堆与当前任务无关的说明占满。假设 Agent 既要改 React，又要写 SQL，还要设计 API：如果三份规范在启动时全部塞进 system prompt， 模型每次请求都要带上三份全文。本课给 Harness 增加一种更细的知识边界： 启动时只告诉模型“有哪些技能以及各自的一句话简介”，模型确定需要某项技能后， 再调用 load_skill(name) 取回完整的 SKILL.md。 主技能是读懂知识何时进入 system、何时进入消息轨迹，不是把 “skill”误解成一个会自动执行的工具。

为什么现在学？

s05 让计划状态变得可见，s06 让大任务可以换一条干净的消息轨迹。 但“消息更干净”不代表 system prompt 就应该无限变长。现实项目通常会同时有 代码审查规范、PDF 处理规范、MCP 开发规范、数据库风格指南等文档。 当前任务只改 Python 文件时，把所有文档全文永久放进 system prompt，会让每一次 模型请求都重复携带无关内容。

无关内容有两个代价。第一，它占用输入 token 和上下文窗口，真正的代码、对话、 工具结果可用空间变少。第二，模型要在更多规则中寻找当前任务相关的规则，提示之间 可能互相干扰。s07 的办法不是把技能删除，而是把“知道有哪些技能”和“知道某项技能 的全部细节”分成两个时机：目录常驻，正文按需进入。

North 对“把全部文档固定放进 system prompt”的问题说明见 README L13–26； “名称描述进入 system、完整正文进入 tool_result”的解决方案见 README L33–40。

先看全局：两层知识、三种状态、一个循环

先不要从 yaml.safe_load 的细节开始。把整支脚本压成一条信息流： 

启动
  ↓
SkillLoader.scan()
  ↓ 读取 skills/*/SKILL.md
skills registry：name → description + full content
  ↓ catalog()
system prompt：技能名称 + 简介（短）

用户 prompt
  ↓
父 Agent loop 请求模型
  ↓ 模型觉得某项技能适用
tool_use(name="load_skill", input={"name": "code-review"})
  ↓
TOOL_HANDLERS 查到 SKILL_LOADER.load
  ↓
完整 SKILL.md 字符串
  ↓
tool_result 回到 messages
  ↓
模型带着已加载的技能继续工作

这里有一个容易忽略的时间顺序：完整正文在启动扫描时已经被 Python 读入内存， 但在模型的输入上下文里要等到 load_skill 的结果回填后才出现。 “按需加载”在这份教学实现里主要指“按需注入模型上下文”，不是“按需从磁盘读取”。

层次保存什么何时进入模型请求
技能元数据目录 name + description 启动后每次 messages.create 的 system 参数
技能完整正文 原始 SKILL.md 全文 模型调用 load_skill 后，作为 tool_result
self.skills registry name、description、content 的 Python 字典 不直接发送；由 catalog 和 load 读取

一句话：system prompt 放“菜单”，tool_result 放“点菜后的全文”。 菜单让模型知道可选项；完整技能只有在模型选择后才进入消息轨迹。 但本课的 Python 进程为了建立菜单，启动时已经缓存了所有正文；不要把 “不注入上下文”误读成“从未读过磁盘”。

一次加载的完整故事

假设启动目录下存在 skills/code-review/SKILL.md，用户输入： Review README.md and load the relevant skill first。先预测控制流，再读局部代码：

  1. 模块加载时创建 SKILL_LOADER = SkillLoader(SKILLS_DIR)； 构造函数调用 scan()，读取每个直接子目录的 SKILL.md。
  2. scan() 解析 --- ... --- 中的 YAML，得到 name="code-review" 和一行 description，并把完整文件文本放入 self.skills["code-review"]。
  3. build_system_prompt() 调用 catalog()，system 中出现 - code-review: ...，但不会出现整篇 checklist。
  4. 用户输入先由外层 REPL 触发 UserPromptSubmit，再追加到 history，进入父 agent_loop。
  5. 模型看到 system 中的技能目录和 load_skill 工具说明，返回 一个 tool_use，输入是 {"name": "code-review"}。
  6. execute_tool 先走 PreToolUse hooks，再从 TOOL_HANDLERS 找到 SKILL_LOADER.load，按名称查字典。
  7. load() 返回缓存里的完整 SKILL.md 字符串。它不启动新 Agent， 不执行 checklist 中的 shell 命令，也不打开一个新的 Python 进程。
  8. 父循环把返回值放进与原 tool_use_id 配对的 tool_result，追加进 messages；模型下一轮才看到完整技能。
  9. 模型接下来可能调用 read_file、bash 等基础工具。 技能正文提供的是规则和建议，真正执行仍由这些工具和原有 hooks 完成。

如果模型一开始不调用 load_skill，代码不会自动替它加载最“相关”的技能。 当前实现只把目录交给模型，让模型自己选择；这正是“知识加载”和“自动路由知识检索” 的边界。

系统讲解

1. 为什么不能把所有技能全文拼进 system prompt？

先看一个“看起来直白”的方案： 

本例 L1  SYSTEM = (
本例 L2      "You are a coding agent. "
本例 L3      + open("docs/react-style.md").read()
本例 L4      + open("docs/sql-style.md").read()
本例 L5      + open("docs/api-design.md").read()
本例 L6  )

这段做到了“模型能看到所有规范”，但没有做到“当前任务只携带需要的规范”。 每次请求模型时，system 都会重复包含三份正文。若当前只改 React， SQL 和 API 文档仍然占用上下文。

策略system 里有什么当前任务的代价
全部预加载 所有技能完整正文 输入变长；无关规则一直存在；正文会随每次请求重复发送
s07 目录 + 按需正文 所有技能的一行名称/简介 先付目录成本；选择后只注入被加载的技能
什么都不提供 没有技能目录 模型不知道仓库里有什么可复用的操作规范

这不是“正文永远不进入上下文”，而是把进入时机推迟到模型判断“这项技能适用”之后。 技能目录是发现能力，load_skill 是取正文能力；两者缺一不可。

2. SKILL.md 为什么有两段？

一个技能文件通常先写 metadata，再写给模型读的正文。以仓库中的 code-review/SKILL.md 为例： 

真实文件 L1  ---
真实文件 L2  name: code-review
真实文件 L3  description: Perform thorough code reviews with security, performance, and maintainability analysis. Use when user asks to review code, check for bugs, or audit a codebase.
真实文件 L4  ---
真实文件 L5
真实文件 L6  # Code Review Skill
真实文件 L7
真实文件 L8  You now have expertise in conducting comprehensive code reviews...

真实示例： code-review/SKILL.md L1–8。

区域作用本课如何使用
--- 之间 机器可读的 metadata 取 name 作为注册表键，取 description 生成目录
第二个 --- 之后 技能的完整 Markdown 正文 仍保留在 content 全文中，调用 load 时返回

注意：parse_frontmatter 返回 (metadata, body)，但 scan() 最后保存的是原始 content，而不是只保存 body。 因此模型调用 load_skill 后拿到的正文仍然包含原始 frontmatter。 这属于当前实现的真实行为，不要凭“正文”这个词猜成只剩第二段。

3. parse_frontmatter：先找边界，再解析 YAML

  1. L61 用 splitlines(keepends=True) 把文本拆成行，同时保留换行符。 保留换行让后面用 "".join(...) 拼回内容时不改变原始布局。
  2. L62 要求第一行去掉换行后恰好是 ---。如果文件没有 frontmatter， 返回空字典和原文；这不是异常。
  3. L65–69 从第二行开始寻找下一条独立的 ---。找到的是 frontmatter 的结束位置， 不是随便找一个包含三个短横线的行。
  4. L73 把边界内文本拼成 YAML 字符串；L76 的 yaml.safe_load 把 YAML 文本 转成 Python 值。这里的 safe 表示使用安全加载方式，不把普通配置当成 可执行 Python 代码。
  5. L76 的 or {} 把 YAML 空值转换成空字典；L79–80 又检查解析结果确实是 字典。frontmatter 写成列表或字符串时，当前实现会把它当作“没有可用 metadata”。
  6. L77–78 只捕获 yaml.YAMLError，解析失败时返回空 metadata，而不是让整个 启动过程因一份坏 frontmatter 直接崩溃。

辨析：解析 frontmatter ≠ 加载技能正文。 parse_frontmatter 只负责把一个文件拆成 metadata 和 body； 真正建立 registry 的是 scan()；真正把技能返回给模型的是 load(name)。三个职责不要混成一个函数。

5. resolve()、is_relative_to() 和“路径不是名称”

代码里有两种看起来都和文件有关的输入：扫描时的 manifest 路径， 以及模型调用 load_skill 时的 name。它们不能混为一谈。

真实源码： code.py L115–122。

  1. L116 用字典的 .get(name) 查表。name 是键，不是文件名拼接模板。

load("code-review") 完整 cached SKILL.md registry 中有完全相同的键

这套精确匹配让“模型能否读取哪个技能”取决于启动扫描出的注册表，而不是由 模型自由构造一个磁盘路径。它不是完整的权限系统：技能正文本身仍可能包含危险建议， 基础工具也仍然由原有 hooks / permission hook 保护。

10. 完整正文怎样穿过原有 Agent loop？

L346              messages=messages,

真实源码： code.py L341–370。

s07 没有复制一套“技能专用循环”。它让 load_skill 遵守 s02 以来的同一协议：

  1. 模型先在 response.content 中产生 tool_use block。
  2. 父循环调用 execute_tool(block)；工具先经过 PreToolUse，再进入 handler。
  3. handler 返回完整技能字符串，执行函数把它转成字符串。
  4. 循环用原来的 block.id 填入 tool_use_id，保证结果配对。
  5. 整个结果批次作为 role: user 消息追加到 messages。
  6. 下一次 messages.create 仍使用相同的 system、tools 和变长的 messages。

从 Agent loop 的视角看，技能正文和文件读取结果没有特殊魔法：二者都是 handler 返回的字符串，都会变成观察。区别在于技能正文改变的是模型接下来遵守的 指令/知识，而 read_file 通常提供的是项目事实；两者都必须通过正确的 tool_result 回填才能被模型看见。

11. execute_tool 和 hooks：加载技能不会绕过治理

L324  def execute_tool(block) -> str:
L325      blocked = trigger_hooks("PreToolUse", block)
L326      if blocked:
L327          return str(blocked)
L329      handler = TOOL_HANDLERS.get(block.name)
L330      try:
L331          output = handler(**block.input) if handler else f"Unknown: {block.name}"
L332      except Exception as e:
L333          output = f"Error: {e}"
L335      trigger_hooks("PostToolUse", block, output)
L336      return str(output)

真实源码： code.py L324–336。

s04 的 hooks 在 s07 仍然是同一套注册表。调用 load_skill 时：

  1. PreToolUse 先运行 permission_hook 和 log_hook。 当前权限规则主要检查 bash 和文件路径，不会把普通 load_skill 拦掉。
  2. handler 查到 SKILL_LOADER.load，返回内容或 Unknown 错误字符串。
  3. PostToolUse 可以观察输出长度；若返回正文超过 100000 字符， large_output_hook 打印警告，但当前不会自动截断或拒绝。

三件事不要混淆：Skill 是知识文档；load_skill 是取回文档的工具； hooks 是包住工具调用时机的治理扩展。加载技能不会自动执行文档里的命令，也不会让 技能跳过原有权限 hook。

12. 技能正文进入消息后，属于哪种状态？

用三个对象跟踪同一份技能：

状态位置示例内容生命周期模型是否直接看到
磁盘文件 skills/code-review/SKILL.md 直到文件被修改或删除 不会自动看到
SKILL_LOADER.skills name / description / cached content 从启动扫描到进程结束，除非手动 scan 不会直接看到；catalog/load 读取它
messages load_skill 的 tool_result 正文 当前 REPL history 持续保留 下一次模型请求能看到
SYSTEM 技能名和简介目录 脚本启动后构造的一份字符串 每次模型请求都看到

这个表解释了一个重要边界：加载一次技能后，完整正文会留在 messages，后续每一轮请求都会随着历史再次携带它，直到本课 s08 的上下文压缩机制来处理。s07 解决的是“不要从一开始把所有正文都塞进去”， 不是“加载后正文永远不占上下文”。

四个案例：从现象推回实现

案例一：只问有哪些技能，不需要加载正文

What skills are available?

模型可以直接读取 system 中的目录回答。如果它调用 load_skill， 那是额外动作，并不是为了回答“有哪些名字”所必需的。这个案例验证： catalog 是可用技能的发现层，不是完整正文。

案例二：先加载再审查

Load the code-review skill and review README.md.
Follow the skill instructions and report concrete findings.
  1. 模型根据目录选择 code-review。
  2. load_skill 返回包含 frontmatter 和正文的完整字符串。
  3. 字符串进入 tool_result，下一轮模型才可以使用 checklist。
  4. 模型还必须调用 read_file 获取 README 的真实内容；技能只是规则，不是 README 本身。

如果模型只加载技能却没有读 README.md，它拥有“如何审查”的知识， 但还没有“要审查的事实”。技能加载不能替代工作区观察。

案例三：加载一个不存在的名字

Load the nonexistent security-audit skill.

当前 handler 返回： 

Error: Unknown skill 'security-audit'. Available: code-review, pdf

这是一个普通字符串 tool_result。模型可以根据可用列表改试正确名称； Python 不会因为一个未知技能就抛出未捕获异常，也不会根据相似度自动猜 code-review。

案例四：启动后修改技能文件

  1. 脚本启动，scan() 读取旧版 SKILL.md 并保存到 content。
  2. 你在另一个编辑器里修改磁盘文件。
  3. 当前进程再次调用 load_skill。
  4. load() 只查 registry，因此返回旧版缓存，不会重新读磁盘。

若要看到新内容，当前教学实现需要重启脚本，或者由开发者显式调用 SKILL_LOADER.scan() 并重新构造 SYSTEM。注意只调用 scan() 会更新 registry，但已经构造的 SYSTEM 字符串不会 自动改变；这再次说明“数据表”和“已组装的 system prompt”是两个状态。

常见坑 + 边界

  • 所有 SKILL.md 全文都在 system prompt：错。 system 只放 catalog() 生成的名称和 description；全文在调用 load_skill 后作为 tool_result 进入 messages。
  • 按需加载就是调用时才从磁盘读文件：当前实现不准确。 scan() 启动时已经把全文保存到 registry；按需的是模型上下文注入。
  • Skill 是一个可以直接运行的 Python 函数：错。 Skill 是 SKILL.md 指令文档；真正执行动作仍要调用 bash、文件工具等。
  • catalog() 会把所有技能正文拼起来：错。 它只使用每条记录的 name 和 description。
  • frontmatter 就是 Markdown 正文：错。 它是两条 --- 之间的 YAML metadata 区域；正文从第二条分隔线后开始。
  • 缺少 name 就一定丢弃技能：当前实现错。 若 metadata 没有合法字符串 name，扫描器退回使用技能目录名。
  • 缺少 description 就一定没有目录项：当前实现错。 它会退回取 body 第一行并压缩空白。
  • glob("*/SKILL.md") 会递归扫描所有层：错。 这个模式只匹配 skills 的直接子目录；更深层路径不在本课范围内。
  • load_skill 接收的是任意文件路径：错。 handler 用字符串查 registry；名字不存在就返回 Unknown，不直接打开传入路径。
  • resolve() 本身就会拒绝越界路径：不准确。 resolve 只规范化路径；真正跳过越界项的是 is_relative_to(skills_root) 判断后的 continue。
  • registry 是模型直接看到的对象：错。 registry 在 Harness 本地；模型只看到 system 里的 catalog 或 messages 里的 tool_result。
  • schema 有 name 就会自动调用 loader：错。 schema 只是模型契约；TOOL_HANDLERS["load_skill"] 才把名字接到方法。
  • 加载完整技能会创建新的子 Agent：错。 load 只是返回字符串；没有第二个 messages，也没有嵌套模型请求。
  • 技能正文进入 tool_result 后就变成永久 system 指令：错。 它留在当前 messages 轨迹；system 仍是启动时构造的目录字符串。
  • 加载技能后模型一定会遵守技能：不能保证。 当前代码只负责把正文提供给模型，不做规则执行器或完成度验证。
  • 修改磁盘上的 SKILL.md 后当前进程立刻看到新版本：错。 registry 保存的是启动时的 content；本课没有 reload / watch 机制。
  • 技能目录替代了项目事实：错。 技能告诉模型如何做；read_file、glob、bash 等工具才提供工作区的实际观察。
  • 加载技能绕过 s04 hooks：错。 load_skill 仍经过统一的 execute_tool 和 Pre/Post hooks。
