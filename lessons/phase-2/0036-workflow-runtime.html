s16：步骤写在代码里，模型只交一次工具调用

s15 的每一轮仍由模型决定下一步。审查代码若总是「每个维度先审计再验证，再合并」， 顺序其实在执行前就知道。把顺序留在对话里，中断之后只能靠历史回忆走到哪。 本课在 s15 的工具池上加一个 Workflow 工具：模型只提交保存好的名字、参数和可选的续跑编号； 宿主运行自己注册的脚本，把每个 agent() 的结果写进 journal。 大目标仍是造 harness：固定编排是代码，临场决策才留给模型。

覆盖声明

主材料：North s16 中文 README （为何写进代码 L13–27， 原语与续跑 L98–187， 相对 s15 L220–239） + s16_workflow_runtime/code.py （journal 键 L321–364， agent / parallel / pipeline L455–532， 启动与续跑校验 L542–564， 模型侧适配器 L744–767）。 本章脚本内部用了 async / await。阶段 0 故意没把这套语法排成课。 本课只讲编排语义：await 表示「这一步的结果回来再往下」，不展开事件循环。 本书没有这套 workflow journal。

本课已内化：模型不能提交脚本文本，只能选 WORKFLOWS 里的名字； schema 只收 name、args、resume_from_run_id； parallel 等齐，pipeline 按条目各自往下走； 带 schema 的 agent() 校验失败会再试一次，仍失败则整次 workflow 报错； journal 的键来自类型、标签、prompt、schema 的稳定哈希，不来自完成顺序； 续跑要求名字和参数与快照一致，并持有 run 锁； 嵌套 workflow() 只允许一层； demo 用假 runner，交互模式才打真实 API。 故意跳过：自己写通用 async 框架、替换 s15 主循环、把 workflow 完成当成用户目标已经达成。 目标是否达成是 s17。 不另写 playground。过关优先跑 demo 和 resume，它们不依赖你再设计一个编排。

名词一句话出处
Workflow 工具 主循环里的一次 tool_use。背后跑宿主注册的脚本，中间结果不塞进对话。 README L43–46

parallel 等齐屏障。全部完成后一起返回；其中一个失败，这次 workflow 失败。 code.py L506–508
pipeline 每个条目自己走完各阶段。条目 A 可以已到后面的阶段，条目 B 还在前面。 code.py L510–519
journal .runtime/<runId>.journal.jsonl。一行一个 agent() 的键和值。 code.py L321–364

为什么现在学？

模型一轮轮决定下一步，适合「下一步取决于刚才看见了什么」。 代码审查的维度列表和「先审计、再逐条验证」在开工前就是知道的。 若顺序只存在于对话，进程在中途停掉，已经花掉的子调用也会一起丢掉。

s06 的子代理是模型临场派一次。s16 把多次调用和它们的先后写成宿主脚本， 并用 journal 记住已经成功的调用。主循环仍是 s15 那一个：模型只是多了一个工具可选。

README L13–27、 L229。

和 Java 怎么对照

s16 概念Java 直觉关键差异
注册脚本 流程引擎里部署好的定义，调用方只传业务键 模型不能上传一段新代码当 workflow。未知名字是错误工具结果。
parallel CompletableFuture.allOf 屏障：都完成才把数组交回脚本。一个失败，整次失败。
pipeline 每个订单自己走状态机，订单之间不必齐步 阶段函数拿到的是上一步结果、原始条目和下标。不是「全体完成第 1 阶段再全体进第 2 阶段」。
语义键 用业务主键做幂等，而不是用消费顺序号 并行完成顺序不稳定。用「第几个完成」当键，续跑会对错缓存。
run 锁 同一流程实例不能两个节点同时往下写 锁盖住执行和最终落盘。另一个进程不能同时 resume 这个 runId。

整体设计

模块地图

s15 主循环不变
  模型调用 Workflow(name, args, resume_from_run_id?)
        ↓
  run_workflow 只从 WORKFLOWS 取出 meta 和函数
        ↓
  validate_meta、权限、预留或校验 runId、拿 run 锁
        ↓
  脚本里的 agent / parallel / pipeline / phase / log
        ↓
  journal 记下每次真正跑过的 agent()
        ↓
  这次 tool_result：启动信息、结果、任务状态
中间变量留在脚本里，不进入主对话

示例注册的名字是 review-changes。每个维度走审计再验证。 demo 用固定的 MockAgentRunner，所以事件顺序可以重复看。 不带参数启动 CLI 时，主模型和子 agent 都走真实 API。

状态放在哪一层？

位置保存什么主对话里有没有
脚本局部变量 维度、findings、confirmed 没有。只有最终返回值进入这次 tool_result
<runId>.journal.jsonl 每个语义键的 agent 输出 没有全文。续跑时运行时自己读
<runId>.json 快照 workflow 名、参数、任务状态 续跑用来核对是不是同一次
主循环 messages 一次 Workflow 工具的结果，外加进度事件如何被宿主打印 有结果，没有每次子 agent 的原始往返

规则先看四条小例

例 1：等齐和不等齐

parallel([验证 finding A, 验证 finding B])
  A 和 B 都结束，才把两个 verdict 交回
  一个抛错，gather 失败，这次 workflow 失败

pipeline(四个维度, audit, verify)
  维度 correctness 可以已经在 verify
  维度 style 还可以在 audit
  没有「四个维度都审计完，才允许任何一个开始验证」这道屏障

下一步要同时用上一阶段的全部结果时，用 parallel。 每个条目都能独立走完同一串阶段时，用 pipeline。

code.py L506–519。

例 2：schema 不对就再试一次

runner 返回的对象
  SimpleJsonSchema.validate
  通过 → 记账、写入 journal、返回

不通过
  再用原 prompt 加上 “Return valid JSON.” 跑一次
  仍不通过 → WorkflowInputError
  这次 agent() 没有成功记录

续跑时缓存若也过不了 schema
  同样报错，不会把坏对象交给下游

这是 s05 的反面：当时不信任工具参数；这里不信任子 agent 的散文。 校验放在编排层，下游拿到的是对象。只自动重试一次。

code.py L483–496、 缓存校验 L466–470。

例 3：键不看谁先完成

basis = kind + label + prompt + schema 的稳定 JSON
key   = kind-十位哈希

parallel 里 B 比 A 先返回
  不会变成 key 是 agent-0001、agent-0002 这种完成序号

续跑时 prompt 或 label 改了
  键不同，缓存不命中，这一步真的再跑
依赖它的后续步骤如果 prompt 里夹了新结果，也会跟着变成新键

缓存命中时不增加 usage.agents 和 tokens。 所以 resume 全部命中时可以看到 agents=0 tokens=0。 命中仍会先占一次 agent 计数上限的检查：claim_agent 在读缓存之前。 上限是每次运行 1000 次 agent() 调用尝试，包括缓存命中这一次计数。

键： code.py L352–356。 命中短路径： L459–474。 上限常量： L36。

例 4：续跑不是换一份参数重来

resume_from_run_id 指向已有 run
  快照里的 workflowName 必须等于这次 meta.name
  args 省略 → 用快照里的参数
  args 给了但和快照不同 → WorkflowInputError

journal 缺文件或某一行不是 {key, value}
  启动前就失败，不去改已经成功的产物

另一个进程已拿着这个 run 的锁
  不能同时 resume

新运行会在打开 journal 之前用排他创建预留新的 runId。 元数据本身也在跑脚本前校验：名字必须是 1–64 字符的安全 slug，缺 description 就 WorkflowInputError。 这和 s12 先 validate_cron 再保存是同一类习惯：注册内容不合法，就不要跑到一半才坏。

code.py L542–565。 元数据： README L83–95。

细节实现

嵌套只一层，计数和账本共用

脚本可以 workflow(name, args) 再跑一份已注册的子流程。 depth >= 1 时再嵌套就报错。子流程共用这一次的 journal、token 账本和 agent 计数，不是另开一个 runId。

code.py L521–532。

未知名字不会拆掉主循环

run_workflow 发现名字不在注册表，或 args 不是对象，就抛 WorkflowInputError。 它作为这次工具调用的失败交给 s15 宿主，宿主按工具错误收成 tool_result。 模型可以改名字再试。不会因此替换掉 s15 的 while。

code.py L744–752。

常见坑 + 边界

  • Workflow 替换了 s15 的主循环：没有。它是工具池里的一个工具。
  • 模型可以传入一段新脚本：不能。schema 没有代码字段，注册表也不接受。
  • pipeline 会等所有条目完成当前阶段：不会。等齐的是 parallel。
  • 子 agent 回一段话，运行时帮你抽字段：带 schema 时不行。校验失败再试一次，仍失败就报错。
  • 续跑的键是完成顺序：不是。键来自调用内容的哈希。
  • 改了 prompt 还能命中旧缓存：不能。prompt 是键的一部分。
  • resume 时可以换一套 args：不可以。和快照不一致就 WorkflowInputError。
  • 全部缓存命中仍会把 tokens 累加上次的数：不会。命中不调用 runner，用量保持 0。但 claim_agent 仍会计一次上限。
  • workflow() 可以无限套娃：不可以。只一层，而且共用这次 journal。
  • 脚本跑完就表示用户的目标已经达成：不表示。那是下一课判断器的事。
  • demo 会打真实模型：不会。它用 MockAgentRunner。交互模式才会。
