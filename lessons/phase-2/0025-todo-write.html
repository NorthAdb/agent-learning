s05：先列清单，再开始做

s04 已经让我们知道怎样把扩展逻辑挂到 Agent loop 上；但一个 Agent 即使能安全地调用工具， 仍可能面对复杂任务做着做着就忘了原目标。本课给它增加一个 todo_write 工具：先把任务拆成可见的清单，再用原来的文件工具和 bash 真正执行。主技能是读懂“计划状态如何进入循环”，不是把待办事项当成又一个会改文件的工具。

为什么现在学？

没有计划时，Agent 的失败不一定是“不会做”，也可能是“做了前几步后忘了还要做什么”。 例如用户说：“把所有 Python 文件改成 snake_case，跑测试，并修掉失败。” Agent 可能先改三个文件；测试失败后注意力全部转向修测试，最后忘记命名目标。 任务越长，工具结果越多，原始目标越容易被当前局部问题盖住。 这正是 README 的问题示例 L13–19。

todo_write 给 Agent 的不是“再多一种执行能力”，而是一块可反复更新的外部工作记忆： 它可以把“调查 → 修改 → 测试 → 修复”显式列出来。真正的调查仍由 read_file / glob 完成，真正的修改仍由 write_file / edit_file 完成，真正的测试仍由 bash 完成。

North 把这层变化概括为“先列步骤再动手” README L7–9； 书第 5 章把它放在 Coding Agent 的工程流程中 L97–130。

先看全局：这支脚本由哪些模块组成？

先不要急着记 update、validated 这些局部名字。 把 s05_todo_write/code.py 想成一间小型工作室：同一个 .py 文件里按职责分成几个模块。这里说的“模块”是脚本内部的逻辑分区， 不是说它们已经拆成了几个独立的 import 文件。 先知道每个分区负责什么，后面看到一行代码时，才知道它处在整条链的哪一段。

源码位置脚本模块它负责什么它不负责什么

可以先用一句话记住整个脚本： REPL 收到任务 → agent_loop 问模型 → 模型选工具 → hooks 在旁边检查 → dispatch 找 handler → 工具结果回到 messages → 模型继续或 Stop。 s05 只在这条既有链上增加了一个“保存计划状态”的 handler 和一个“忘记更新时提醒”的计数器。

四个状态位置：同一个任务的信息分别放在哪里？

初学者很容易把“计划”“对话”“文件”和“计数”想成一个大对象。 实际上它们在脚本中的位置不同，生命周期也不同：

位置里面是什么谁会读 / 写多久存在
TODO.items 规范化后的当前完整 TODO 列表 TodoManager.update 写；render 读 同一 Python 进程；不自动落盘
messages / history 用户消息、模型回复、tool_result、reminder agent_loop 不断追加；下一次 API 请求读取 同一 REPL 进程；本课也不持久化
WORKDIR 下的文件 真实代码、文档和测试产物 read / write / edit / bash handler 直到文件被修改或删除
rounds_since_todo 距离上次使用 todo_write 的工具调用轮次 agent_loop 每轮计算 一次 agent_loop；新用户 prompt 重新从 0

先建立这个区别：模型“看见的计划文字”通常来自 messages 里的 tool_result；程序“保存的计划状态”在 TODO.items。文件内容又是第三份独立状态。它们可以互相反映， 但没有哪一份会自动替代另外两份。

再看一遍：一次请求怎样穿过这些模块？

s05 没有另起一根循环。它保留 s04 的 UserPromptSubmit、PreToolUse、PostToolUse、 Stop 四个 hook，也保留五个旧工具；只新增一条工具和一段计数逻辑。 一次 todo_write 的路线如下： 

User 输入
    ↓
LLM 返回 tool_use(name="todo_write", input={"todos": [...]})
    ↓
PreToolUse：权限 hook 放行 → 日志 hook
    ↓
TOOL_HANDLERS 查表 → run_todo_write
    ↓
TodoManager.update：解析 → 校验 → 替换 TODO.items → render
    ↓
tool_result(content=当前清单或 Error)
    ↓
messages 追加观察 → LLM 决定下一步

如果模型连续调用的是 read_file、edit_file、bash 等其他工具， 每个“模型回复含有工具调用的轮次”都会让 rounds_since_todo 加一。 第三轮仍没调用 todo_write 时，Harness 在同一批结果末尾增加一条文本提醒， 再把整批结果送回模型。这是“提醒模型”，不是“替模型更新”。

先走一个完整故事，再读局部代码

假设你输入： Refactor s05_todo_write/example/hello.py and run a check。 不看细节时，先预测这支脚本应该发生什么：

  1. 外层 REPL 在 L351–358 读入 prompt，把它追加到 history，调用一次 agent_loop。
  2. agent_loop 在 L295–303 把 SYSTEM、历史消息和工具列表交给模型。SYSTEM 建议多步任务先用 todo_write，模型若遵循这个建议，才可能先返回它； 这几行代码本身不判断任务是否多步，也不强制首个工具必须是它。
  3. 这个 tool_use 先经过 s04 的 PreToolUse hooks，然后 dispatch map 按名字找到 run_todo_write。
  4. TodoManager 把清单解析、校验并保存到 TODO.items； 渲染文字同时打印到终端，并作为 tool_result 回给模型。
  5. 模型看到计划后，可能再调用 read_file 读取 hello.py，用 edit_file 修改，再用 bash 做检查。每个工具仍然经过同一套 Pre / Post hooks。
  6. 模型若在过程中更新计划，就再次调用 todo_write，把相应项目改成 in_progress 或 completed；代码不会替它自动改状态。
  7. 某一轮模型只返回文本、不再返回 tool_use 时，agent_loop 触发 Stop hook， 然后退出这次 agent_loop，REPL 打印最后的文本。

如果模型连续三轮只调用其他工具，L334–340 会把 reminder 附加进结果，再让模型继续。 所以“计划模块”并不是把任务包在一个函数里，而是通过一条工具调用和一条反馈， 反复插入原来的模型—工具循环。

工具只更新状态、实际工作仍由旧工具完成： README L23–29； 三轮提醒： code.py L311–340。

现在按模块拆解

刚才先看了“这支脚本有哪些分区”和“一次请求怎样走完”。 下面按源码的职责来读：先读计划数据和状态，再读状态更新， 然后看它如何变成工具、如何接回主循环，最后再看 reminder。 这样遇到一个局部名字时，你已经知道它在全局链条中的位置。

模块一：一个 todo 项到底是什么？

先从最小的数据形状开始。当前实现把一条任务表示为一个字典，至少有两个键： content 是人和模型都能读懂的任务描述，status 是机器可以判断的阶段。 例如下面是一个完整的三项计划： 

本例 L1  [
本例 L2      {"content": "阅读现有实现", "status": "completed"},
本例 L3      {"content": "修改代码", "status": "in_progress"},
本例 L4      {"content": "运行测试", "status": "pending"},
本例 L5  ]

左边的“本例 Lx”只是本例行号。它不是 North 源码的行号，也不要复制进 Python。 这个列表表达的是“第一步已经完成，第二步正在做，第三步还没开始”。 North 的渲染结果会把它变成人类更容易扫读的形式： 

[x] 阅读现有实现
[>] 修改代码
[ ] 运行测试

(1/3 completed)

三种状态的规则要分清：

状态含义渲染标记本课是否自动改变
pending 任务存在，但还没开始 [ ] 不会；模型必须再次调用 todo_write 更新
in_progress 当前正在处理 [>] 不会；工具不会因为执行了 bash 就自动变成进行中
completed 模型认为这一步已完成 [x] 不会；脚本不替模型判断文件是否真的正确

这里的 completed 只是模型写入的状态，不是测试通过证明。 如果任务要求“修改后必须通过测试”，还要调用 bash 跑测试； 这正是阶段 1 学过的“计划”和“验证”不能混为一谈。

模块一的边界：计划工具不等于执行工具

现在把这份数据放回刚才的全局图。下面两次调用看起来都叫工具， 但它们改动的状态层完全不同：

调用它改变什么它不改变什么
todo_write Python 进程里的 TODO.items，以及回传给模型的计划文本 不创建文件、不改代码、不运行测试、不自动调下一个工具
write_file / edit_file 工作区中的真实文件 不会自动把 TODO 标为 completed
bash 命令的真实副作用和输出 不会自动生成或修正计划状态

所以一个合理的多步轨迹可能是： todo_write 列出三步 → read_file 调查 → todo_write 把第一步改成 in_progress → edit_file 修改 → bash 验证 → todo_write 把第一步改成 completed。 脚本没有任何一行会替模型自动安排这条路线；列表只是让路线可见。

“不增加执行能力，只增加规划能力”是 North 的关键洞察： README L108–110。

模块二：一次 update 如何改变计划状态？

到这里我们已经知道三件事：一条任务是字典，状态有三个允许值， todo_write 只负责计划状态。现在再追踪一次 TodoManager.update：模型把一份清单交给它后， 它怎样决定“接受这份新状态”？

先回答：为什么需要校验？要校验什么？

这里的输入来自模型的 tool call。模型通常会按照 schema 输出，但 “通常符合”不等于“程序可以直接信任”：输入也可能来自手写调用、 测试数据，或者只是缺字段、状态拼错的输出。 因此 update 不能一拿到 todos 就直接写入 self.items，它要先做 validation（校验）。 校验的意思是：检查“这份数据能不能作为一份合法的 TODO 状态保存”， 不是检查“用户的代码任务是否已经完成”。

校验层次要问的问题源码位置
整体形状 顶层是不是列表？是不是超过 20 项？ L129–132
每一项形状 列表中的每一项是不是字典？ L136–138
字段内容 content 去空白后是否非空？status 是否属于三个允许值？ L140–145
跨项目规则 整份列表中是否最多只有一个 in_progress？ L146–151

先只记检查清单，不急着记实现细节： 列表 → 数量 → 每项是字典 → content 有内容 → status 合法 → 进行中最多一个。 任一项不合格，就不应该把这份输入当成新的计划状态。

先看一份输入如何被判定

合法：
[
    {"content": "阅读实现", "status": "completed"},
    {"content": "运行测试", "status": "pending"}
]

不合法：
[
    {"content": "   ", "status": "pending"},
    {"content": "运行测试", "status": "working"}
]

第一份满足“每项是字典、content 非空、status 合法”； 第二份至少有两个问题：第一项去掉空格后没有内容，第二项的 working 不在允许状态列表中。它们不是“任务执行失败”， 而是“计划数据本身不合格”。后面 L142–145 的 ValueError 就是在报告这类输入问题。

验证通过后，为什么采用整体替换？

先看结论：North 的 update 是整体替换，不是追加一条。 这个结论不是凭方法名猜出来的，而是从后面 L153 的赋值位置读出来的。 先理解下面这个“旧状态 → 新状态”的例子，再看为什么代码必须这样安排。

它的实现不是 self.items.append(...)，而是先构造一份新的 validated，所有项目通过后才执行 self.items = validated。因此每次 todo_write 都应发送“更新后的完整清单”。

假设当前状态是三项： 

旧状态：
[x] 阅读实现
[>] 修改代码
[ ] 运行测试

如果下一次只发送下面这一项： 

[{"content": "修改代码", "status": "completed"}]

结果不是“给第二项打勾，同时保留另外两项”，而是整个清单被替换成一项： 

新状态：
[x] 修改代码

正确更新应该把三项都发送回去： 

[
    {"content": "阅读实现", "status": "completed"},
    {"content": "修改代码", "status": "completed"},
    {"content": "运行测试", "status": "in_progress"}
]

这和“局部 patch”不同。局部 patch 是“只描述要改哪一个字段”；本课的协议是 “发送完整快照”。把这一点记住，才能读懂后面的 self.items = validated。

现在再看失败分支：为什么旧状态不会被半成品覆盖？

上面已经知道要检查什么。现在回到代码，问题就变成： 如果某一项检查失败，update 怎样保证旧计划不被一半新数据覆盖？ 关键是：真实代码把赋值放在所有检查之后。下面是带 North 行号的核心片段： 

L134  validated = []
L135  in_progress_count = 0
L136  for index, todo in enumerate(todos):
L137      if not isinstance(todo, dict):
L138          raise ValueError(f"todos[{index}] must be an object")
L139
L140      content = str(todo.get("content", "")).strip()
L141      status = str(todo.get("status", "pending")).lower()
L142      if not content:
L143          raise ValueError(f"todos[{index}] requires content")
L144      if status not in ("pending", "in_progress", "completed"):
L145          raise ValueError(f"todos[{index}] has invalid status '{status}'")
L146      if status == "in_progress":
L147          in_progress_count += 1
L148      validated.append({"content": content, "status": status})
L149
L150  if in_progress_count > 1:
L151      raise ValueError("Only one todo can be in_progress at a time")
L152
L153  self.items = validated
L154  return self.render()

上述源码： L134–154。

  1. 新数据先放在局部变量 validated 中，旧的 self.items 暂时不动。
  2. 只要任何一项触发 raise ValueError，函数立即离开，根本走不到 L153。
  3. 因此旧列表不会被半成品覆盖；这是一种“全部通过才替换”的简单保护。
  4. 所有检查通过后，L153 才把新列表交给对象，L154 再渲染它。

注意这不是数据库事务，也不是跨进程的原子提交；它只是这个单线程教学对象里的 “先用临时变量检查，最后一次赋值”结构。

逐行拆开：

  1. isinstance(todos, str) 问“这个值是不是字符串？”。 如果模型 SDK 已经给了 Python 列表，就跳过解析；只有字符串才进入这段。
  2. json.loads 把 JSON 文本转换成 Python 对象。比如 '[{"content":"读文件","status":"pending"}]' 会变成列表。 这里的 loads 中的 s 表示 string；它读的是字符串，不是文件路径。
  3. 如果文本不是合法 JSON，json.loads 抛出 JSONDecodeError，程序进入第二个 try。
  4. ast.literal_eval 只解析 Python 字面量，例如单引号字典、列表、数字、 True、None；它不会像 eval 一样把任意字符串当成可执行代码。
  5. 两种解析都失败时，代码用 raise ValueError(...) from e 把底层解析失败改写成 对调用方更有意义的“todos 必须是列表或 JSON 数组字符串”，同时保留原因链。

为什么 schema 明明要求数组，还要接受字符串？因为 schema 是给模型的契约， 而 handler 仍处在不可信输入边界：实际调用可能来自测试、手写请求或格式不完全正确的模型输出。 这段兼容逻辑让代码能处理两种文本表示，但后面仍会检查解析结果是不是列表。

文本谁能解析结果
'[{"content":"读","status":"pending"}]' json.loads 合法 JSON；双引号、JSON 数组
"[{'content': '读', 'status': 'pending'}]" ast.literal_eval 不是合法 JSON，但可以是 Python 字面量列表
"not a list" 两者都不能变成合格列表 抛出 / 返回校验错误，不更新状态

安全辨析：eval 会把字符串当 Python 表达式执行，能力可能包含函数调用； ast.literal_eval 只接受字面量。模型输出不可信时不要用 eval 解析。 本课脚本选择 json.loads + ast.literal_eval，不是因为文本解析“天然安全”， 而是因为它把允许的输入范围收窄到了数据表示。 官方参考： ast.literal_eval、 json.loads。

6.1 先分清两个层次：tool call 和 tool-call round

tool call 是一个 block，例如一个 read_file； tool-call round 是模型的一次回复里，只要筛出了至少一个 tool_use 块，整个 for block in tool_calls 处理过程就算一轮。 因此：

本轮模型返回used_todo计数变化
一个 read_file False 加 1
三个工具：glob、read_file、bash False 仍只加 1，不是加 3
两个工具：todo_write、edit_file True 清零，不管本轮还有几个其他工具
模型只返回文本，没有 tool_use 不会走计数段 先触发 Stop，再退出或按 Stop hook 继续

轮次tool_calls计算结果
第 1 轮 [glob] 0 + 1 rounds_since_todo = 1
第 2 轮 [read_file, bash] 本轮仍没有 todo → 1 + 1 rounds_since_todo = 2
第 3 轮 [edit_file] 本轮仍没有 todo → 2 + 1 追加 reminder，然后清零
第 4 轮 [todo_write, bash] 本轮使用过 todo → 直接清零 rounds_since_todo = 0

reminder 的真实结构是： 

{
    "type": "text",
    "text": "<reminder>Update your todos.</reminder>"
}

它追加到了与工具结果相同的 results 列表，随后作为一条 role: user 消息进入 messages。它不是某个 tool_use_id 对应的 tool_result，也不是 Messages API 的特殊顶层字段，而是一块额外的文本观察。

6.3 reminder 是提醒，不是强制计划

即使模型收到 <reminder>Update your todos.</reminder>， 当前代码也没有：

  • 直接替模型调用 todo_write；
  • 因为模型忽略提醒就拒绝 bash 或文件工具；
  • 检查 TODO 是否真的描述了用户目标；
  • 检查 completed 是否有测试证据。

它只是一个轻量反馈。真正的强制约束要写进执行前检查；真正的完成验证要跑测试、 lint 或其他命令。这也回应了书第 5 章关于“测试通过而不是代码写完才算完成”的工程原则 L120–130。

源码： L50–54。

这三句话会作为 system 前缀发给模型：

  1. 告诉模型自己处在什么工作目录。
  2. 建议多步任务开始前调用 todo_write。
  3. 建议执行过程中同步状态。

但提示词不是权限管线。模型可能不遵守，Harness 才用 L334–337 的 reminder 轻轻提醒；本课没有在 PreToolUse 里写“没有 TODO 就拒绝所有其他工具”的硬规则。 这正是“指导”和“约束”的差别。

10.2 一次计划调用的真实顺序

假设模型返回一个 todo_write block，顺序是：

  1. L301–303 从 response.content 找出 tool_use，得到 tool_calls。
  2. L314 调用 s04 的 trigger_hooks("PreToolUse", block)。 权限 hook 对 todo_write 不命中文件或 bash 规则，返回 None； 日志 hook 随后打印工具调用。
  3. L320 按 block.name 查到 run_todo_write，L322 用 **block.input 传入 todos。
  4. TodoManager.update 解析、校验、替换并渲染；终端看到 ## Current Tasks。
  5. L326 触发 PostToolUse；L328–329 把 used_todo 设成真。
  6. L331–332 用相同的 block.id 回填一个 tool_result； 下一轮模型才能看到计划文本。

计划文本进入了 messages，但它仍然是 tool_result 观察；真正的权威状态格子是 TODO.items。二者通常一致，但概念上不要把“模型看见的字符串”和“内存对象”混成一个东西。

10.3 一轮里同时有 todo 和其他工具怎么办？

Messages API 一次回复可以包含多个 tool_use block；本教学脚本仍按列表顺序串行处理。 例如： 

tool_calls = [
    todo_write(...),
    read_file(...),
    edit_file(...),
]

实际顺序是： Pre hook → todo handler → Post hook → Pre hook → read handler → Post hook → Pre hook → edit handler → Post hook； 三个结果都追加到 results，最后一起回填。 因为其中出现了 todo_write，这一轮的 used_todo 为真， 不会增加 reminder 计数。

这并不表示 TodoManager 会“自动包住”另外两个工具，也不表示工具并发执行。 TODO 只是列表中的一个 block；调度、权限、执行和结果回填仍然是各自独立的步骤。

综合演练：从输入推导到结果

现在把前面六个模块合起来。下面的案例不再引入新概念， 只练习从一个输入预测：哪个模块先运行、哪个状态会改变、模型会收到什么观察。

案例一：首次计划，状态从空变成三项

  1. 用户要求一个多步重构任务。
  2. 模型第一次返回 todo_write，三个项目都是 pending。
  3. PreToolUse 放行，dispatch 找到 run_todo_write。
  4. TodoManager 通过所有校验，L153 用新列表替换空的 TODO.items。
  5. 工具结果把渲染文本送回模型；模型现在可以决定先做哪一项。

这次调用没有创建任何文件。若终端出现 ## Current Tasks， 那是 print；模型能否继续看到清单，靠的是返回值被包装成 tool_result。

案例二：更新第二项时只发送一项，清单被缩短

旧状态有三项，模型只发送 [{"content": "修改代码", "status": "completed"}]。 校验会通过，L153 会忠实执行整体替换，因此新状态只有这一项。 这不是脚本“丢数据”的随机 bug，而是当前协议的明确定义：更新输入是完整快照。

案例三：两项同时 in_progress，旧状态保持

假设旧状态是“阅读实现 completed、修改代码 in_progress”。新输入把 “运行测试”也写成 in_progress。遍历会把计数加到 2，L150–151 抛出 ValueError；self.items = validated 没有执行。 run_todo_write 返回 Error: Only one todo...， 循环把它作为 tool_result 回填。旧计划仍然是“一个进行中”。

案例四：三轮只做工具，提醒进入结果批次

模型连续三轮分别调用 glob、read_file、edit_file， 每轮都没有 todo_write。第三轮处理完工具后：

  1. rounds_since_todo 从 2 变成 3。
  2. 代码把一个 {"type": "text", ...} 追加到 results。
  3. 计数清零。
  4. 工具结果和 reminder 一起作为 user 消息追加给模型。

模型收到后可能更新 TODO，也可能继续调用工具；脚本只提供反馈，不替它做决定。

案例五：调用内容无效，但计数口径仍按“用了工具名”处理

这是一处要以源码为准的细节。若模型调用了 todo_write，但列表超过 20 项， run_todo_write 会返回 Error。可是 L328–329 的判断只看 block.name == "todo_write"，不看 output 是否以 Error: 开头。因此这一轮仍把 used_todo 设为真，提醒计数清零。

这意味着“调用过计划工具”和“计划成功更新”是两个不同事实。生产实现若需要只在 成功更新后清零，应把 used_todo = True 放到成功结果判定之后； North s05 的教学代码没有这样做，本课不擅自修改它。

第一轮：先观察计划工具，不修改文件

先发一个只读的多步任务，观察模型是否先列计划：

Read s05_todo_write/example/hello.py and explain what would be needed to add type hints, docstrings, and a main guard. Do not modify files.
  1. 终端先出现 UserPromptSubmit 和 PreToolUse 的 hook 日志。
  2. SYSTEM 只是建议先计划；观察模型是否遵循建议，把 todo_write 放在第一批工具调用中。即使它直接调用 read_file，当前代码也不会因此拦截。
  3. 你应看到 ## Current Tasks，并在模型回复的观察中看到同一份清单。
  4. 之后模型可能调用 read_file；因为请求明确只读，不应写文件。

第二轮：观察状态更新与真实执行分离

North README 给的可运行例子是： 

Refactor s05_todo_write/example/hello.py: add type hints, docstrings, and a main guard

这个任务会修改 North 子仓库里的示例文件。运行前确认你接受这次本地教学改动； 完成后可以查看 git diff，必要时由你自己决定是否保留。 观察重点不是文件内容本身，而是：

  • 模型是否遵循 SYSTEM 建议，把 todo_write 作为第一次工具调用；
  • 计划是否先全是 pending；
  • 执行过程中是否重新调用 todo_write 把某一步改成 in_progress；
  • 代码修改由 edit_file / write_file 完成，而不是由 todo_write 完成；
  • 测试或检查之后，模型是否把对应项目更新为 completed。

第三轮：主动制造安全的 reminder 场景

对一个会读多个文件、执行检查的任务，观察连续三轮没有 TODO 时是否出现： 

<reminder>Update your todos.</reminder>

reminder 是否出现取决于模型一次回复如何分批调用工具，不能把“你发了一次 prompt” 直接等同于“一轮”。如果模型一轮同时调用很多工具，计数仍只加一；如果它很快结束， 也可能根本不到三轮。

常见坑 + 边界

  • todo_write 会创建文件：错。它只更新内存里的 TODO.items，文件副作用来自 write_file、 edit_file 或 bash。
  • 模型调用一次 TODO 就会自动完成第一项：错。工具只保存模型发送的 status；不会替模型跑动作，也不会自动迁移状态。
  • update 是给列表追加一项：错。L153 用完整的 validated 替换 self.items；每次应发送更新后的全量列表。
  • 两个 in_progress 会保留前一个并接受后一个：错。 L150–151 先拒绝整批，旧状态不会被 L153 替换。
  • 只有恰好一项 in_progress 才合法：错。代码限制的是最多一个； 全部 pending 或全部 completed 也通过。
  • schema 已经校验完，所以 TodoManager 不需要检查：错。 schema 是给模型的输入契约，L129–151 是真正写入进程状态前的运行时保护。
  • 写了 minLength: 1 就一定拒绝数字 content：不一定。 当前 Python 实现先 str(...)，直接调用 handler 时数字可能被转成字符串； 要以执行代码而不是只看 schema 判定边界。
  • eval 和 ast.literal_eval 只是两种写法：错。 eval 可执行任意表达式，模型文本不能交给它；本课只用 JSON 解析和字面量解析。
  • 三轮 reminder 是三个 tool call：错。它是三个含有一个或多个 tool_use 的模型回复轮次；一轮含三个工具仍只计一轮。
  • 三轮是跨整个交互会话计算：当前实现不是。计数器在 agent_loop 内，每个新用户 prompt 重新从 0；TODO.items 在同一进程内却会保留。
  • reminder 出现就会强制模型更新计划：错。它只是附加的 type: text 观察；当前代码没有拒绝后续工具的闸门。
  • 模型把项目写成 completed 就等于测试通过：错。 completed 是计划字段；测试、lint、类型检查等验证仍要由工具执行并观察结果。
  • TODO 是跨重启的长期记忆：错。TODO = TodoManager() 只创建进程内实例；脚本结束后它的列表不会自动落盘。
  • 调用了无效的 todo_write 就一定会继续提醒：不一定。 当前 L328–329 只看工具名，不看 output 是否为 Error；无效调用也会把 used_todo 设为真并清零提醒计数。
  • s05 把 s04 的 hook / 权限 / tool_result 协议换掉了：错。 它仍先过 PreToolUse、再执行 handler、再过 PostToolUse，并用原 tool_use_id 回填结果； 新增的是 TODO 状态和 reminder。
  • 有了 TODO 就不需要完成定义和测试：错。清单只能让步骤可见， 不能证明结果正确；可靠停止仍需要可运行的验证信号。
