s12：到点再跑，进程关了闹钟也停

s11 让一条已经开始的 Bash 先交回编号，但它不记住「明天早上 9 点再跑一次测试」。 用户仍要自己盯着钟点，到了再发一句 prompt。 本课只加这一层：把五段 cron 表达式和要交给模型的 prompt 存下来， 进程活着时到点入队，等当前回合结束再开一轮 Agent loop。 大目标还是造 harness：时间触发是宿主的事，不是模型自己记得几点。

为什么现在学？

「每天 9 点跑测试」和「这条测试现在在后台跑」是两件不同的事。 s11 回答第二条：命令已经开始，主循环不必干等。 它没有一张表记录下次该什么时候开始，也没有线程每秒看钟。

如果只靠现在的 Agent loop，到点之后仍要有人把 prompt 打进终端。 Harness 要自己保存时间和要说的那句话，到点放进队列，再等 Agent 空闲时送进同一条循环。

本章工具仍是 s04 的五个，再加 schedule_cron、list_crons、cancel_cron。 没有 s11 的 run_in_background。队列里运送的是一句用户消息，不是某次 Bash 的输出。

问题与边界： README L11–13、 L30。

和 Java 怎么对照

s12 概念Java 直觉关键差异
五段 cron Spring 的 cron Spring 常见六段，第一段是秒。本章没有秒，第一段是分钟。

三个时刻，三件事

时刻谁在干活会话里看不看得见
注册 schedule_job 校验并保存 看得见工具结果：Scheduled cron_...。这一分钟不一定触发。

状态放在哪一层？

位置保存什么重启后
scheduled_jobs 全部已注册任务，含非持久的 进程结束即空。持久任务靠文件装回来。
cron_queue 待交付的任务对象 不单独落盘。装载时若 pending_delivery 仍为真，会重新入队。

规则先看四条小例

例 1：五段，而且先校验再保存

validate_cron("0 9 * * *")     → None     合法，没有错误字符串
validate_cron("0 9 * *")       → 字段数量不对
validate_cron("60 9 * * *")    → 分钟超出 0–59
validate_cron("0 9 * * 7")     → 星期超出 0–6
schedule_job("0 9 * *", "run tests")
  → 返回错误字符串，scheduled_jobs 里没有新任务

合法形状是 *、*/N、N、N-M、N,M。 */N 只要求 N 是正整数，不要求 N 小于字段上限。 匹配时用当前值对 N 取余，余数为 0 才算中。 星期 0 是周日：代码把 Python 的周一=0 换成 cron 的周日=0， cron_weekday = (weekday() + 1) % 7。

校验： code.py L349–365。 星期换算： L298。 Python 的 weekday()： datetime.weekday。

例 2：日和星期同时写，是「或」

表达式  0 9 1 * 1
  日字段不是 *
  星期字段也不是 *

cron_matches 的收尾
  两个都不是 *  →  日匹配 或  星期匹配

所以每月 1 日 09:00 会触发
周一 09:00 也会触发，哪怕那天不是 1 日

只有一边被限制时，就只看那一边。两边都是 *，日和星期都不挡。 这是本章代码的规则，不要按「必须同时是 1 日且是周一」去记。

code.py L306–314。

例 3：同一分钟不会入队两次

09:00:01  匹配，last_fired 写成 "2026-10-04 09:00"，pending_delivery=true
09:00:02  调度线程又醒了
          pending_delivery 已是真，直接 continue
09:01     若是每分钟任务，分钟标记变了，可以再入队

模型调用还没成功时
  pending_delivery 保持真
  即使分钟标记被清掉，也不会再入队第二条

入队前先改状态。持久任务要先 save_durable_jobs() 成功，才 append 到队列。 写盘失败就把 pending_delivery 和 last_fired 改回去，队列里不会出现一条只活在内存里的到期任务。

code.py L474–501。

例 4：进程关了，durable 不会补跑

durable=True   定义在 .scheduled_tasks.json
durable=False  只在这次进程的 scheduled_jobs 里

09:00 时进程没开
  没有调度线程
  09:00 这次不会补
  下次匹配要等表达式再次对上「现在」

文件损坏
  启动时打印 [cron] could not load ...
  不会假装装载成功

需要进程关闭后仍准点执行，要用系统自己的 crontab 或 systemd timer。 本章的 durable 只保留任务定义，不代替操作系统的调度服务。

确认发生在工具执行之前。模型已经看见这句 prompt，但 bash 还没跑； 若此时进程退出，重启后 pending_delivery 可能已经是 false，不会为了「测试没跑完」再送一次。 至少一次指的是这句 prompt 的交付，不是工作产品。

code.py L642–672， 确认： L511–538。

定时回合不能问你 Allow?

破坏性 bash、工作区外路径，平时会在主线程里 input("Allow?")。 队列线程不是主线程。它一进 request_permission 就返回拒绝，不会和终端抢输入。 拒绝名单里的命令仍然直接拒绝，和是不是定时回合无关。 普通、不需要确认的 bash 仍可在定时回合里执行。

code.py L187–190。

写盘是临时文件再替换

save_durable_jobs 只序列化 durable 为真的任务，用 asdict 变成字典。 先写带 pid 和线程号的临时文件，再 os.replace 到 .scheduled_tasks.json。 替换是同一目录下的原子改名。写到一半崩溃，旧文件还在。

常见坑 + 边界

  • 把 Spring 的六段 cron 原样贴进来：本章要五段，第一段是分钟。多一段会在校验时被拒绝。
  • 星期 0 是周一：不是。0 是周日，1 是周一，6 是周六。
  • 日和星期都写了就要同时满足：本章是或。两边都不是 * 时，中任意一边即可。
  • durable=True 等于关机后仍会跑：不等于。线程随进程停，错过的分钟不补。
  • 到点会立刻打断正在进行的用户回合：不会。拿不到 agent_lock 就继续等。
  • [Scheduled] 是一条 tool_result：不是。它是追加的用户消息。
  • 模型调用失败会把 prompt 弄丢：不会。刚追加的消息会删掉，任务放回队列。
  • 确认之后测试没跑完，重启还会再送一次：不保证。确认的是模型收下 prompt，发生在工具执行之前。
  • 同一分钟调度线程醒 60 次就会入队 60 次：不会。last_fired 或 pending_delivery 会挡住。
  • 定时回合可以弹 Allow?：不能。非主线程直接拒绝需要确认的操作。
  • 导入模块就会开始每秒扫描：不会。线程在 CLI 启动路径里才开。
  • 文件坏了就静默当成没有任务：不会。启动日志会打出加载错误。
  • 本章也会把慢 bash 放进后台：不会。没有 s11 那条分叉。

s12 之后：真实产品怎么做定时

这一节是延伸，不进入过关标准。它回答两个学完必然会问的问题： 能不能只用 s04 的 hook 做？成熟 Agent 是怎么做的？ 两个答案指向同一件事——计时要待在 Agent 进程之外。

为什么不是 hook

s04 的四个事件（UserPromptSubmit、PreToolUse、PostToolUse、Stop） 都是生命周期事件：只有循环走到那个点，trigger_hooks() 才被调用。 真实 Claude Code 的 hook 事件多得多，但同样全是生命周期事件，没有「到点了」这一类；命令 hook 也明确 「can't trigger / commands or tool calls」，不能自己发起一轮 （出处：Hooks reference 的事件表与 Limitations）。 而 cron 最典型的场景是人不在、循环根本没在跑——没有事件可挂。

官方做法印证了这一点：Claude Code 为定时任务专门加了 CronCreate、CronList、CronDelete 三个工具和一个「每秒检查、低优先级入队」的调度器，而不是复用 hook （出处：Run prompts on a schedule）。 它和本课的 cron_scheduler_loop + cron_queue 是同一套结构。

一句话：hook 是插口，要求「已经有事发生」；闹钟要解决的是「没事发生的时候，谁来碰一下」。

同一套机制，三档部署

Claude Code 现在把定时任务分成三档，差别只在「计时器跑在哪」：

Cloud RoutinesDesktop 任务会话内 /loop
跑在哪Anthropic 云端你的机器你的机器
机器要开着吗不用要要
要开着会话吗不用不用要
跨重启持久持久--resume 时恢复（过期或已过时的一次性任务除外）
能读本地文件不能（每次 fresh clone）能能
审批无，全自动每任务可配继承会话
最小间隔1 小时1 分钟1 分钟

出处： Run prompts on a schedule、 Desktop scheduled tasks、 Routines。 第三档就是本课：会话一关就不响；第二档把调度器搬进常驻进程；第一档搬到云端。

这不是一家的做法。同一个问题的成熟实现分布在四个位置：

成熟产品比本课多补的六件事

成本尾巴 无上限 Claude Code：每会话最多 50 个任务、周期任务 7 天自动过期；ChatGPT：按套餐限 3 / 5 / 10 / 15 个活跃任务，免费版一天一次；Routines：每小时 100 次；LangGraph 直接警告「不删 cron 就等着收 API 账单」
要不要弹审批 非主线程直接拒绝（request_permission） 三种解法：Cloud 全自动不提示；Desktop 每任务独立权限模式 + 记住 always allow；必须交互的 MCP 工具每轮都 stall
谁有权触发 信任存在 .scheduled_tasks.json 里的 prompt Routines 把 API 传来的 text 包进 <routine-fire-payload> 标成不可信数据，只有事先存好的 prompt 才算授权

还有一条边界本课已经讲对、成熟产品又专门写了一遍：「跑起来了」不等于「做完了」。 Routines 的运行列表里，绿点只表示 session 起停没有基础设施错误，不代表 prompt 里的任务成功 （出处：Routines）。 这和本课「确认的是 prompt 交付，不是工作产品」是同一件事，也是 s17 Goal Loop 接着要处理的问题。

两种取舍：复用会话，还是每次新开

会话内调度一次一 run（run-per-fire）
代表本课 s12；Claude Code /loop；本 harness 的 schedule_createCloud Routines；LangGraph cron；ChatGPT tasks
上下文继承同一条对话和 MCP每次新 session / thread，要重新装
隔离和用户回合抢同一份会话天然隔离，可并行；常用 worktree 或 fresh clone
代价会话必须活着，所以要配过期和上限prompt 必须自包含；状态得靠仓库和文件

本节新名词 × 原文

名词一句话出处
调度面 / 投递面 / 执行面 三层切法：谁计时（进程外的调度服务）、到点只入队不打断回合、以及可抛弃的一次 run。本课只把第一层放错了位置。 Run prompts on a schedule；Temporal Schedules
抖动（jitter） 给同一时刻的多个任务加一点确定性偏移，避免整点一起打 API。偏移按任务 ID 算，同一个任务每次都一样。 Run prompts on a schedule；Temporal 的 ScheduleSpec 里也有 jitter（Schedules）
补跑 / 漏跑策略（catch-up、misfire policy） 进程不在的那几拍怎么处理：不补、只补最近一次、还是回填一段时间。必须显式选一个，不能靠默认。 Desktop「只补最近一次、7 天内」（Desktop scheduled tasks）；Temporal backfill（Schedules）
重叠策略（overlap policy） 上一轮还没跑完、这一拍又到点了怎么办：排队、跳过、取消上一次，还是允许并行。 Temporal Schedules
一次一 run（run-per-fire） 每次触发开一个独立的、可抛弃的 session / run，而不是往同一条对话里塞消息。 LangGraph cron jobs（每次新建 thread，可配运行完删或留）；Routines
持久定时器（durable timer） 把「等待」本身写进存储：Worker 和服务都挂了，恢复后 sleep() 照样接着走。这才是「关机也准点」的正解。 Temporal Timers
不可信触发载荷 外部触发传进来的文本当数据、不当指令；只有事先存好的 prompt 才算授权。定时任务等于给外部开了一个入口，这条必须有。 Routines（<routine-fire-payload>）

自己要做的话，按这个顺序补

  1. 把定义和线程搬出 Agent 进程：哪怕先用系统 crontab 到点拉起一个一次性进程。
  2. 显式定两套策略：漏跑补不补、撞车谁让谁。
  3. 加抖动，并且别把时间都压在整点。
  4. 加过期和总量上限，否则忘了的任务会一直烧钱。
  5. 给触发器做信任边界和幂等键：至少一次意味着同一句话可能来两次。

这五步不要求你写代码，只要求能说清「为什么需要」——面试和设计评审问的正是这个。
