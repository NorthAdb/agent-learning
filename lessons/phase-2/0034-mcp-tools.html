s14：连接之后，下一轮才看得见新工具

到 s13 为止，工具定义都写在当章 code.py 里。 每接一个文档系统或部署平台，就要再手写一份 schema 和调用代码。 本课把这件事拆开：server 提供工具列表和调用入口，Harness 负责连接、起名、按宿主策略授权， 再把发现的工具放进下一轮的工具池。 课程里的 docs 和 deploy 是进程内替身，用来看清这条边界。大目标仍是造 harness： 模型看见的工具表可以变，循环的形状不变。

主材料：North s14 中文 README （角色拆分 L11–29， 组装、前缀、宿主策略 L35–153） + s14_mcp_plugin/code.py （MCPClient L163–191， 连接与模拟 server L198–299， 组装工具池 L316–365， 权限与循环 L394–519）。 MCP 这个名字来自模型上下文协议。本章没有实现真实的网络传输。 本书未把这套 MCPClient 写成独立章。

为什么现在学？

手写 search_docs、deploy_status 能跑，但每加一个服务就要改课程代码里的工具表。 把「有哪些工具」留给 server，宿主只保留连接和授权，工具表就可以在运行时变长。

循环仍然是：组工具、叫模型、有 tool_use 就执行、把 tool_result 追加回去。 变化的是组工具这一步不再读一份写死的 TOOLS 常量。

README L11–29。

和 Java 怎么对照

s14 概念Java 直觉关键差异
connect_mcp 服务发现：先连上，再拿接口列表 当前这次模型请求的工具表已经发出去了。新工具要等下一轮组装。
mcp__docs__search 用前缀避免两个 jar 里都有 search 规范化会把 . 和 / 换成下划线。撞名直接报错，不悄悄合并。

状态放在哪一层？

位置保存什么模型看不看得见
mcp_clients 已连接的 client 看不见对象。系统提示里会多一句已连接的名字
本轮 tools 组装出来的 schema 看得见。只包含此刻已经连接的 server
mcp_tool_policies 带前缀的名字 → allow 或 confirm 看不见。权限钩子查这张表
server 上的 annotations readOnlyHint 等 描述可以出现在 schema 里。钩子不拿它当授权

规则先看四条小例

例 1：同一轮看不见刚连上的工具

messages.create 的 tools 在这次调用前就定了。 模型即使在这条回复里先调用 connect_mcp，同一次回复里也不可能合法地调用 mcp__docs__search，因为那个名字还不在它收到的工具表里。 它要等工具结果回到对话，循环再组装一次。

这和 s10「同一条回复里的参数在执行前已经写死」是同一类限制： 后一个工具的参数不能使用前一个工具还没返回的发现结果，除非模型再要一轮。

例 2：前缀和撞名

docs 的 search     → mcp__docs__search
deploy 的 status   → mcp__deploy__status

规范化：字母数字、下划线、减号以外都变成 _
  docs.one / get.version
  docs_one / get_version
  两者都会变成 mcp__docs_one__get_version

assemble 发现 prefixed 已经在 origins 里
  raise ValueError(...collision...)
  agent_loop 抓住异常，写成助手文本 [Error] ValueError: ...
  然后 Stop，这一轮不再执行工具

名字长于 64 字符同样在组装时抛错。空规范化结果也会在 normalize_mcp_name 里失败。 冲突不是「后者覆盖前者」。

code.py L206–211、 L332–340、 L490–499。

例 3：默认参数绑住这一项

handlers[prefixed] = (
    lambda *, client=server, tool=raw_name, **kwargs:
    client.call_tool(tool, kwargs)
)

client=server 和 tool=raw_name 在创建这个函数时就取值。 循环继续，外层的 server 变量会变成下一个 server，已创建的 lambda 仍调用当初那个 client。 模型传入的参数进 kwargs，再交给原始工具名。 漏了必填参数时，call_tool 捕获 TypeError，返回以 MCP error: 开头的字符串。

code.py L350–353、 L183–190。 默认参数在定义时绑定： Python FAQ：默认值。 本章用的是「每个 lambda 自己的默认值」，正是为了避开循环变量晚绑定。

例 4：自我声明的只读不算放行

MCP_HOST_POLICY
  ("docs", "search")       allow
  ("docs", "get_version")  allow
  ("deploy", "status")     allow
  ("deploy", "trigger")    confirm

docs.search 的 annotations 里虽然有 readOnlyHint: true
permission_hook 不读 annotations
它只查 mcp_tool_policies[带前缀的名字]

表里没有的外部工具 → 组装时写成 confirm

所以「描述里写了 readOnly」不会跳过询问。 deploy.trigger 即使你只是想看看，策略仍是 confirm。

策略表： code.py L198–203。 钩子： L414–419。 默认 confirm： L354–356。

细节实现

连接是幂等的失败，不是刷新

同名已经在 mcp_clients 里，返回 already connected，不会重新发现工具。 名字不在 MOCK_SERVERS 里，返回 Unknown server，并列出 docs、deploy。 没有「断开」工具。进程结束，这张字典就没了。

code.py L282–287。

schema 用的是 server 的 inputSchema

组装时把 inputSchema 放进模型的 input_schema。 它必须是对象，且 type 缺省或就是 object。否则组装抛错，同样走到循环的错误返回。 模型看见带前缀的名字；call_tool 使用注册时的原始名字。两边不是同一个字符串。

常见坑 + 边界

  • connect 的同一轮就能调用新工具：不能。工具表在这次 messages.create 之前已经定了。
  • 两个 server 的 search 会重名：模型看见的名字带服务器前缀。
  • 点号和斜杠会各自保留：不会。规范化后撞车就抛错，循环停在错误文本。
  • readOnlyHint 为真就自动允许：不会。只查宿主策略。
  • 没写进策略表的工具默认允许：不。默认 confirm。
  • lambda 都指向最后一个 server：不会。默认参数在创建时绑住 client 和原始工具名。
  • 参数漏了会让脚本崩溃：不会。返回 MCP error: TypeError: ... 这种 tool_result。
  • 再次 connect 会刷新工具列表：不会。返回 already connected。
  • 本章会走真的 MCP 网络：不会。docs 和 deploy 是进程内工厂。
  • 系统提示会塞进每个 MCP 工具的全文：不会。只追加已连接的服务器名字。工具 schema 在 tools 参数里。
