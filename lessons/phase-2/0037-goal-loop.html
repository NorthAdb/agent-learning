s17：想停不等于做完，判断器只看对话里的证据

从 s01 起，模型不再调用工具，循环就返回。这对聊天够用。 「修到 pytest 退出码为 0」却不够：模型可以以为自己做完了，对话里却没有那次命令的结果。 本课在停止点加一个会话级判断。干活的模型和判断器不是同一次调用。 判断器没有工具，只能根据已经写进 messages 的内容说完成、没完成、或已经不可能。 大目标仍是造 harness：谁有权宣布结束，要和谁在改代码分开。

为什么现在学？

s16 可以报告 workflow 正常结束。结束的是那份脚本，不是「pytest 已经是 0」这件事。 若仍用「没有 tool_use 就 return」，模型停下来的愿望会直接变成会话结束。

判断器若自己还能跑命令，它就变成第二个干活的 Agent，宣布完成的人和制造证据的人又叠在一起。 本章把它做成只读对话的那一次调用。证据必须先被主模型写进消息。

README L15–19、 L225–231。

和 Java 怎么对照

s17 概念Java 直觉关键差异
停止点再判一次 业务方法返回前，用另一段代码核对验收条件 核对者也是模型，但它没有仓库权限。它只能读已经发生的对话。
block 后 continue 校验失败把原因塞回同一个请求再处理 没有单独的续跑队列。就在这个 while 里追加一条 user 消息。
defer 异步任务还没回调，先不要把订单标成完成 此刻根本不叫判断器。后台文本进来之后再跑同一条循环。
limit 与 max_turns 熔断：停止自动重试，工单仍开着 两道上限都不把目标改成已完成，也不自动 clear。
一个活跃 Goal 一个请求只有一个验收标准 再设一个就是替换。clear 的别名有六个，不是只认 clear 这一个词。

规则先看四条小例

例 1：口说无凭

主模型最后一句：测试通过了
对话里没有 pytest 的命令和退出码

判断器的提示要求根据具体结果判断
它仍可能被话术骗到，因为它看不到仓库
所以主模型的 system 要求：跑完验证，把命令和结果写进对话

Goal 不是测试框架
它不自己执行 pytest

送给判断器的文本保留最近的完整消息，默认预算 24000 字符。 只有最新一条本身超长时，才保留它的头和尾，中间打省略。 不会为了塞进预算而把最近几条拆碎。

细节实现

恢复不恢复计数器

GoalController.restore 从后往前找 goal_status 事件。 最后一条若 active 为真，就按那条条件新建 GoalState，但判断次数从 0 开始，开始时间是现在，token 起点是 0。 已经完成、失败或清除的事件不会把目标重新打开。 本章命令行不负责把整个会话写盘。恢复是给更大的宿主用的接口。

code.py L448–472。 README： L170。

替换是显式的

已有活跃目标时再 set_goal，先记一条「被新目标替换」，再换上新条件。 不会同时存在两个完成条件让判断器挑。 /goal 不带正文时是查看：条件、已判断次数、经过秒数、这段目标以来的 token、最近理由。

和 s16 的边界

s16 回答一批步骤怎样执行、怎样续跑。s17 回答整件事能否停。 两章的代码可以分开跑。若接到同一宿主，workflow 的通知只是消息； Goal 仍在主循环的停止点决定继续还是返回。

常见坑 + 边界

  • 没有 tool_use 就表示目标完成：只在没有活跃目标时，这才和 s01 一样直接停。
  • 判断器可以自己再跑一次 pytest：不能。它没有工具。
  • 模型说「通过了」就一定 achieved：不保证。提示要求看具体结果，但判断器仍然只是模型。
  • Goal 会替你执行测试：不会。验证靠主模型的工具。Goal 只看记录。
  • 后台还在跑也会先判完成：不会。动作是 defer，而且不调用判断器。
  • workflow 通知有特殊豁免：没有。它和其他消息一样被阅读。
  • 连续拦住 8 次会把目标标成完成或失败：不会。动作是 limit，目标还在。
  • 判断器报错就当成没目标、直接成功：不会。动作是 error，目标保留。
  • MAX_TURNS 用尽会 clear：不会。状态是 max_turns，条件还在。
  • 可以同时挂两个 Goal：不可以。新的替换旧的。
  • 只有 clear 这个词能取消：stop、off、reset、none、cancel 也可以。
  • CLI 会把未完成的目标写进磁盘，下次自动接着判：本章命令行不持久化会话。restore 是接口，而且不恢复旧的次数和时间。

过关标准

  • 能说明没有 tool_use 只是想停；有活跃目标时要先判断。
  • 能列出 allow、defer、achieved、failed、block、limit、error、max_turns 各自是否还留着目标。
  • 能说明判断器没有工具；defer 时甚至不会调用它。
  • 能说明 block 写回同一份 messages；limit 和错误都不把目标标成完成。
  • 能写出一条含结束状态、验证方式、限制的完成条件，并指出「弄好」为什么不能用。
  • 能说明一个会话一个目标；clear 有别名；CLI 不持久化；restore 不恢复旧计数。
  • 能说明 s16 的脚本结束和 s17 的目标完成不是同一句话。
  • 在准备好 API 的前提下真跑 python s17_goal_loop\code.py，看见一次因证据不足而继续，或一次 /goal 状态里目标仍在。
