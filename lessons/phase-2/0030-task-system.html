s10：把任务图写到磁盘上

s05 的清单只提醒「接下来还要做什么」，进程结束就没了，也回答不了「这一步现在能不能开始」。 s09 留下的是以后还用得上的知识，不是「表建完了没有、谁正在写接口」。 本课给 Harness 加上可恢复的任务图：每个任务一个 JSON 文件， 用 blockedBy 记下前置，用 claim / complete 推进状态。 大目标能拆开、排上依赖、换一次进程还能接着做。

为什么现在学？

一个项目拆成「建表、写接口、补测试、写文档」时，清单上的四行字不够。 Harness 还要知道：接口必须等表完成，测试必须等接口完成，文档可以和接口并行， 而且这些关系在下次启动时还在。

s05 能显示「写接口仍未完成」，但不能据此判断它能不能开始。 s08 管的是当前 messages 有多长。s09 管的是哪些知识值得跨会话复用。 s10 管的是工作项的进度和依赖。三个都落在文件附近，回答的却是三件不同的事。

North 对「清单没有依赖和分工」的说明见 README L13–21。

和 Java 怎么对照

一次完整运行

下面用 README 里的四件事走一遍。ID 是运行时随机生成的，这里只用名字代表文件。 箭头「表 → 接口」表示完成顺序：表做完，接口才能开始。 文件里写的是反方向的引用：接口.blockedBy = [表的 ID]。 

第一阶段  创建四个节点，此时谁都不引用谁
  表        pending  owner=空  blockedBy=[]
  接口      pending  owner=空  blockedBy=[]
  测试      pending  owner=空  blockedBy=[]
  文档      pending  owner=空  blockedBy=[]

第二阶段  用第一阶段返回的 ID 加边
  接口.blockedBy = [表]
  测试.blockedBy = [接口]
  文档.blockedBy = [表]

  表 ──完成顺序──▶ 接口 ──完成顺序──▶ 测试
   └─────────────▶ 文档

认领与完成
  claim(表)      成功，表变为 in_progress，owner=agent
  claim(接口)    失败，返回 Blocked by: [表的 ID]
  complete(表)   成功；接口和文档的直接前置都清掉了，测试仍被接口挡住
  claim(接口)    成功
  complete(接口) 成功；这次新解锁的是测试
  claim(文档)    成功（它只等表，不等接口）
  complete(文档) 成功；测试若已经可开始，不会再次出现在 Unblocked 里
  claim(测试)    成功
  complete(测试) 成功

一句话：节点先落地，边后补上；能不能动手看直接前置； 完成只翻转本条状态，并指出哪些下游是这一下才变得可开始。

README 的同一条剧本： L169–196。

状态放在哪一层？

位置保存什么模型何时看到生命周期
messages 当前会话里的对话和工具结果 每次请求按历史发送 这次进程里的这次会话
.tasks/{id}.json 一条任务的全部字段 调用 list_tasks 或 get_task 之后 跨进程保留，直到文件被改掉或删掉
owner 谁把这条任务从 pending 认领走了 列表里的一行，或详情 JSON 认领时写入；完成后仍留在文件里
工具返回的字符串 创建出的 ID、拒绝原因、刚解锁的标题 作为 tool_result 进入下一轮 只在这条消息里

文件在磁盘上，不等于模型已经读过。新会话的 messages 是空的， 进度在 .tasks/。模型要调用列表或详情，才能把任务重新放进上下文。

为什么必须分两阶段？

create_task 不接收依赖。新 ID 要等文件创建成功才存在。 模型有时会在同一条回复里发出好几个工具调用。 这些调用的参数，在循环执行任何一个工具之前就已经确定了。 所以「创建表」和「让接口依赖刚生成的表 ID」不能写在同一次回复里： 第二个调用还不知道第一个调用会返回什么。 

同一条 assistant 回复
  tool_use create_task("表")          参数里没有 ID，这是合法的
  tool_use create_task("接口")        仍然不能填写表的 ID
  tool_use update_task(???, [???])    这里的 ID 只能是猜的，通常会失败

下一轮，工具结果已经在 messages 里
  tool_use update_task(表的真实 ID 不在这里)
  tool_use update_task(接口的真实 ID, addBlockedBy=[表的真实 ID])

循环确实会按顺序执行同一条回复里的工具，但那只是执行顺序。 它不会把前一个工具的返回值塞进后一个工具早已写好的参数。 协议靠系统提示约束模型，代码不会自动把同轮调用重排成两阶段。

设计说明： README L84–87。 循环先收集全部 tool_use，再逐个执行： code.py L554–572。

状态机只有两个动作

pending ──claim_task──▶ in_progress ──complete_task──▶ completed

claim 和 complete 是动作。 pending、in_progress、completed 是状态。 不能从 pending 直接跳到 completed，也不能把完成的任务退回去。 本章也不提供删除任务、修改标题、拆除已有依赖。

README 的状态机： L158–167。

细节实现

1. 一条任务六个字段

@dataclass
class Task:
    id: str
    subject: str
    description: str
    status: str          # pending | in_progress | completed
    owner: str | None
    blockedBy: list[str] # 直接前置的任务 ID

真实定义： code.py L68–75。 @dataclass 在 0012 已经见过：它按字段生成构造方式。 asdict 把实例收成普通字典，后面才能 json.dump。

subject 是列表里看得见的短标题。description 是长说明， 列表不展示，只有 get_task 会把整份 JSON 返回。 blockedBy 用驼峰，是因为工具参数和磁盘 JSON 用的是同一个拼写。 它不是 Python 强制风格，而是让模型和文件对上同一个名字。

字段创建时之后谁改
id task_ 加 8 位十六进制 不再改；文件名和字段必须一致
status pending 只有 claim、complete 这两步
owner None claim 写成调用者；complete 不清除
blockedBy 空列表 只在 pending 且尚未认领时追加

2. ID 和路径是两道闸门

TASK_ID_PATTERN = re.compile(r"^task_[0-9a-f]{8}$")

def _path(self, task_id, create_root=False):
    if not isinstance(task_id, str) or not TASK_ID_PATTERN.fullmatch(task_id):
        raise ValueError(...)
    path = (root / f"{task_id}.json").resolve()
    if not path.is_relative_to(root):
        raise ValueError(...)

真实实现： code.py L65、 L82–97。

re.fullmatch 要求整串匹配，不是「里面含有这段」。 所以 task_abc 太短，task_ABCDEF12 有大写， ../task_abcd1234 带了目录，都会在拼路径之前被拒绝。 通过模式之后，仍然 resolve() 并检查结果还在 .tasks 根目录下。 resolve() 只把路径规范化；拒绝越界的是后面的 is_relative_to。

存储根目录还要落在当前工作区里面。 TaskStore 若被指到工作区外，_root 会直接报错。 本章实际使用的是 当前目录/.tasks。

和 s09 的同构：先拒绝不合法的名字，再确认解析后的路径仍在允许的根目录内。 记忆用的是文件名规则，任务用的是 task_ 加 8 位小写十六进制。

3. 创建：随机 ID，排他写入

subject = subject.strip()
if not subject:
    raise ValueError("Task subject cannot be empty")

for _ in range(100):
    task = Task(
        id=f"task_{secrets.token_hex(4)}",
        subject=subject,
        description=description,
        status="pending",
        owner=None,
        blockedBy=[],
    )
    try:
        with self._path(task.id, create_root=True).open("x", encoding="utf-8") as handle:
            json.dump(asdict(task), handle, indent=2)
        return task
    except FileExistsError:
        continue
raise RuntimeError("Could not allocate a unique task ID")

真实实现： code.py L102–125。 secrets.token_hex 与 open 模式 "x" 的语义在 Python 标准库， North 源码没有再解释这两个词： token_hex 用 nbytes 个随机字节生成十六进制文本，4 字节就是 8 个十六进制字符； open 模式 "x" 表示排他创建，文件已经存在就失败。

标题去掉两端空白后不能是空串。描述可以是空串。 新任务的依赖固定是空列表，负责人固定是空。创建函数没有 blockedBy 参数， 工具 schema 还写了 additionalProperties: false，多传的字段不属于这个工具。

ID 不使用递增计数器。每次取 4 字节随机数，撞上已有文件就换一个，最多 100 次。 模式 "x" 不会把已经存在的任务 JSON 盖掉。 盖掉是后面 save() 的事，那条路径只用于更新已知 ID。

4. 加边：先整批校验，再保存一次

if task.status != "pending" or task.owner is not None:
    raise ValueError("...pending and unowned")

dependencies = list(dict.fromkeys(add_blocked_by))
for dependency in dependencies:
    if dependency == task_id:
        raise ValueError("Task cannot depend on itself")
    if not self.exists(dependency):
        raise ValueError(f"Dependency not found: {dependency}")
    if dependency not in task.blockedBy and self._depends_on(dependency, task_id):
        raise ValueError(f"Dependency cycle detected: {task_id} -> {dependency}")

task.blockedBy.extend(
    dependency for dependency in dependencies
    if dependency not in task.blockedBy
)
self.save(task)

真实实现： code.py L141–171。 环检测的行走： L127–139。

dict.fromkeys 按输入顺序建字典。字典键天然不重复，所以再转回列表时， 重复 ID 只保留第一次出现的那个，后面的顺序不变。这里用它，而不是 set， 是因为集合不保证顺序。

校验按这个顺序做完，中途任何一条失败都还没有 save：

  1. addBlockedBy 必须是列表。工具 schema 还要求至少一项；函数本身遇到空列表会原样再保存一次。
  2. 目标任务要存在，并且仍是 pending、owner 仍是空。已经认领或已经完成，都不能再加边。
  3. 不能依赖自己。
  4. 每个前置文件都要存在。
  5. 若这条边还不存在，就从该前置沿着 blockedBy 往前走。走到了目标任务，说明会成环。
  6. 只把还没有的 ID 追加进去，然后保存一次。

重复添加同一条边是安全的：它不会写进列表两次，也不必再做环检测。 边已经在图里，再声明一次不会制造新环。

4.1 环检测是传递的，开工检查不是

_depends_on(dependency, task_id) 从「将要当成前置的那条任务」出发， 沿着它的 blockedBy 继续走。若能走到正在被修改的任务， 就不能再加「这条任务依赖那个前置」。 

已有：测试.blockedBy = [接口]
      接口.blockedBy = [表]

想加：表.blockedBy = [测试]
行走：测试 → 接口 → 表，走到了「表」
结果：拒绝。否则表等测试、测试等接口、接口等表。

can_start 并不做这次行走。它只看本条 blockedBy 里的直接 ID 是不是都已经 completed。因此：

  • 测试只写了 blockedBy: [接口] 时，接口一完成，测试就可以认领。函数不会再去看「接口是不是还在等表」。
  • 若建图时漏了「测试等接口」这条边，只给测试写了「等表」，表完成后测试就会被允许开始。Harness 不会替模型把缺的边补上。

读图口诀：加边时沿着前置链防止成环；开工时只相信这条任务自己列出的直接前置。

5. 能不能开始，和能不能认领

def incomplete_dependencies(task):
    incomplete = []
    for dependency in task.blockedBy:
        try:
            if load_task(dependency).status != "completed":
                incomplete.append(dependency)
        except (FileNotFoundError, ValueError):
            incomplete.append(dependency)
    return incomplete

def can_start(task_id):
    return not incomplete_dependencies(load_task(task_id))

真实实现： code.py L219–231。

空的 blockedBy 得到空的未完成列表，can_start 为真。 前置文件丢了、ID 对不上、状态字段坏了，都算「还没完成」，而不是「当作没有这条依赖」。 丢文件因此会挡住认领，不会悄悄放行。

can_start 只描述依赖。一条已经是 in_progress 或 completed 的任务，只要前置都完成了，它也会返回真。 认领还要另外满足：自己的状态必须是 pending。

6. 认领：两条业务拒绝都是普通字符串

if task.status != "pending":
    return f"Task {task_id} is {task.status}, cannot claim"
dependencies = incomplete_dependencies(task)
if dependencies:
    return f"Blocked by: {dependencies}"
task.owner = owner
task.status = "in_progress"
TASKS.save(task)
return f"Claimed {task.id} ({task.subject})"

真实实现： code.py L234–245。 工具入口把 owner 写成 "agent"： L381–382。

状态不对，或者还有未完成的直接前置，函数返回说明文字，不抛异常。 模型在 tool_result 里读到 cannot claim 或 Blocked by， 就可以去完成前置，或改认领另一条。 对比之下，非法 ID、给已认领任务加边，会在 TaskStore 里抛 ValueError，再被 execute_tool 收成 Error: ...。 两类文本模型都能看见：前者是预期中的状态拒绝，后者是校验失败。

正常创建出来的 pending 任务，owner 一定是空。 claim_task 本身不再检查「是不是已经有 owner」，它只看状态和依赖， 然后写下本次 owner。本章工具没有把 owner 暴露给模型，所以模型不能指定别人的名字。

7. 完成：先核对身份，再算「新解锁」

if task.status != "in_progress":
    return f"Task {task_id} is {task.status}, cannot complete"
if task.owner != owner:
    return f"Task {task_id} is owned by {task.owner}, not {owner}"

ready_before = {那些 pending、有前置、而且现在就能开始的 ID}

task.status = "completed"
TASKS.save(task)

unblocked = [那些 pending、有前置、刚才还不在 ready_before、现在能开始的标题]

真实实现： code.py L248–273。

必须已经是 in_progress，而且文件里的 owner 必须等于这次调用者。 本章工具调用者永远是 "agent"。手改成别人的 owner 之后，这个进程不能替他完成。 完成后 owner 字段还在，只是状态变成 completed。

「刚刚解锁」不是「所有现在能做的任务」。计算分三刀：

  1. 完成之前，记下已经可开始、而且自己带有前置的 pending 任务。
  2. 把当前任务写成 completed 并落盘。
  3. 再看一遍。仍然 pending、仍然有前置、刚才不在那份集合里、现在 can_start 为真的，才放进 Unblocked。

没有前置的任务一开始就能做，不会因为别人完成而被叫做「新解锁」。 早就可开始的下游也不会被重复报告。 返回里用的是 subject，顺序来自 list_tasks() 的文件名排序， 不是创建顺序，也不是建议的执行顺序。两个任务若标题相同，这行字会分不清是哪一个 ID。

完成不等于做完。complete_task 只改状态文件。 它不检查表是否真的建好、测试是否真的通过。 这和 0020 的验证缺口是同一件事：Harness 记下了「有人宣称完成」，没有记下证据。

8. 列表是摘要，详情才是全文

list_tasks   [ ] task_id: 标题 [pending] (blockedBy: ...)
get_task     整份 JSON，含 description 和全部字段

列表： code.py L354–374。 详情： L215–216、 L377–378。 列举实现是按文件名排序的 task_*.json： L188–193。

标记 [ ]、[>]、[x] 只是给人看的状态缩写。 目录不存在时列表是空字符串提示，不会自动创建目录。 文件名排序不等于拓扑排序。第一行不是「下一个该认领的任务」。 跨会话继续时，短标题往往不够，需要 get_task 把描述读回来。

9. 工具层把负责人钉死

工具成功时模型看见什么本章不允许模型做的事
create_task Created task_xxxxxxxx: 标题 不能在创建时传入依赖或 owner
update_task 更新后的整份 blockedBy 不能删边，不能改已认领的任务
list_tasks 每个任务一行摘要 不返回 description
get_task 完整 JSON 不修改文件
claim_task 认领成功，或状态 / 阻塞说明 不能替别的 owner 认领；工具固定写 agent
complete_task 完成，并可能多一行 Unblocked 不能完成别人认领的任务，也不能跳过认领

README 写明本章只处理顺序执行的状态更新： L118。 owner 字段是为后面的分工留下的，s10 的工具 schema 里没有这个参数。

观察一：先看见四个文件，再看见边

Create tasks: setup database schema, create API endpoints (depends on schema), write tests (depends on endpoints), write docs (depends on schema)

看终端里的工具顺序，再看 .tasks/。 期望是先出现若干 task_ JSON，依赖字段先是空的； 随后另一次 update_task 才把 ID 写进 blockedBy。 若模型在同一次回复里猜 ID，工具结果里会出现找不到任务或 ID 不合法。那正好说明两阶段不是可选文风。

观察二：认领被挡住，完成才会解锁

List all tasks and their statuses
Claim the first unblocked task and complete it
List tasks again — which ones are now unblocked?

「第一行」不是调度结果。没有前置的「建表」应该能认领； 接口和文档在表完成前应得到 Blocked by。 表完成之后，返回文本里的 Unblocked 应包含接口和文档的标题，不包含仍被接口挡住的测试。 退出程序再启动，JSON 还在，但新的 messages 是空的。不调用列表，模型不会自动知道进度。

观察三：完成没有检查工作产品

可以让模型认领并完成「建表」，同时不要真的创建数据库文件。 complete_task 仍会成功。把这个结果记成边界：状态文件记录的是宣称，不是验证。

常见坑 + 边界

  • 任务系统和 TodoWrite 是同一张表：不是。清单整表替换、活在进程里、没有依赖和负责人。
  • 记忆文件会记下任务进度：不会。s09 拒绝把临时任务状态写成长期知识。
  • 创建时就能把依赖一起传进去：不能。create_task 只收标题和描述。
  • 同一条回复里后面的工具能看见前面的返回值：不能。参数在执行前已经定死。
  • blockedBy 的箭头和「谁先做完」同向：不是。列表里存的是前置 ID，图上的完成顺序箭头指向后继。
  • can_start 会沿着整条链检查：不会。它只看直接前置。传递检查出现在加边时的环检测。
  • 漏掉的边会被自动补上：不会。图里没有的前置，就不会挡住认领。
  • 列表第一项就是下一个可做任务：不是。顺序是任务 ID 的文件名排序。
  • 前置文件不见了就当作没有依赖：不是。缺失和非法文件都算未完成，认领会被挡住。
  • pending 可以直接完成：不能。完成要求状态已经是 in_progress，且 owner 匹配。
  • Unblocked 列出所有当前能做的任务：不是。只列出这一次完成之后新变得可开始、并且自己带有前置的任务。
  • 完成后 owner 会被清空：不会。只改状态。
  • 认领之后还能补依赖：不能。加边要求 pending 且 owner 为空。所以边要在认领前加完。
  • 标记完成就证明工作做完了：不能。本章没有检查工作产品。
  • 排他创建和 save 一样不会覆盖：不对。只有创建用 "x"；save 会重写该 ID 的文件。

过关标准

  • 能用一句话区分 s05 清单、s09 记忆和 s10 任务图：一个管步骤提醒，一个管可复用知识，一个管进度和依赖。
  • 能讲清六个字段在创建时的初值，以及状态机只有 claim、complete 两个动作。
  • 能说明 blockedBy 存的是前置 ID，完成顺序的箭头指向后继。
  • 能解释两阶段建图：同一次回复中的工具参数在结果返回前已经定死，所以必须先拿到运行时 ID。
  • 能按顺序说出加边校验：pending 且未认领、非自依赖、前置存在、不会成环、重复边不双写，然后才保存。
  • 能区分环检测会沿前置链行走，can_start 只看直接前置，缺掉的边不会被补上。
  • 能说明认领失败返回普通字符串，而非法更新会变成 Error:；两者都进工具结果，含义不同。
  • 能解释 Unblocked 是完成前后的差分，列表顺序是文件名排序，完成不验证工作产品。
  • 能指出本章工具把 owner 固定为 agent，因此还不是多 Agent 分工。
  • 真跑 python s10_task_system\code.py，至少看见一次先创建后加边、一次认领被阻塞、一次完成后的解锁，并在重启后确认 JSON 还在。
