s06：把过大的任务交给干净上下文的 Subagent

s05 给 Agent 加了可见的 TODO，但一个 TODO 项本身仍可能很大： “读完整个项目，找到测试框架并修复问题”。如果主 Agent 为了完成它不断读取文件， 父对话里的每一次工具调用和结果都会留下来，最后真正重要的结论反而被中间过程淹没。 本课在同一根 Agent loop 上加入 Subagent（子 Agent）： 主 Agent 用 task 工具委派一个边界清楚的子任务，子 Agent 从一份全新的 messages 开始，完成后只把最终文本交回来。 主技能是读懂“隔离哪些状态、共享哪些状态”，不是把 Agent 递归复制成无限层。

为什么现在学？

s05 解决的是“做长任务时别忘记计划”。但 TODO 只是任务清单， 不会自动把一个大任务搬到更合适的上下文里。假设父 Agent 为了回答 “这个项目用了什么测试框架？”先读了十几个配置、源码和文档文件， 这些读取结果都会继续留在父 Agent 的 messages 中。 如果之后父 Agent 还要改代码、跑测试，模型每一轮都要带着这些中间材料继续思考。

s06 增加的不是“更聪明的模型”，而是一条上下文边界： 父 Agent 把调查任务交给子 Agent；子 Agent 在自己的消息轨迹里读取文件、推理、 得出结论；父 Agent 只收到结论文字。这样做的收益是父消息更短、更聚焦， 但代价也要记住：子 Agent 不是沙箱，仍然能改同一个工作区；如果子任务的说明含糊， 被隔离的中间过程也可能让父 Agent 看不到重要证据。

North 对“工具结果留在父 messages[]”的问题描述见 README L13–19； “只隔离消息、不隔离进程或文件系统”的边界见 L23–29。

先看全局：两个循环和三条边界

先不要把“子 Agent”理解成一个神秘的新模型。s06 仍然只有一个 Anthropic client 和同一个模型配置；新增加的是第二份局部消息列表、 一套子工具列表，以及一个同步嵌套的循环。把整支脚本压成下面这张图：

   ↓ 选择 task(prompt)
run_subagent(prompt)
   ↓

   ↓ 可能调用 read / write / edit / glob / bash

这张图要同时读三条边界：

边界隔离 / 共享什么本课的真实效果
消息边界 隔离 父 messages 和子 messages 是两个不同列表；子内部工具结果不进入父列表。
执行环境边界 共享 父子在同一 Python 进程、同一个 WORKDIR；文件修改和命令副作用共享。

一句话：子 Agent 是上下文隔离，不是安全隔离， 也不是文件隔离。看到“fresh messages”时，不能顺手推断出 “新的进程”“新的目录”或“不能改文件”。

一次委派的完整故事

假设你输入： Use a subtask to find what testing framework this project uses。 先只预测模块和消息，不急着读局部代码：

  1. 外层 REPL 把用户输入放进父 history，调用父 agent_loop(history)。
  2. 父模型看到 system 中“可用 task 做 focused exploration”的提示，返回一个 tool_use，名字是 task，输入是 {"prompt": "..."}。
  3. 父循环通过 execute_tool 查表，找到 run_subagent，同步进入子循环。
  4. 子循环创建自己的 [{"role": "user", "content": prompt}]，不会把父的历史复制进来。
  5. 子模型可能调用 glob 找配置、调用 read_file 读配置， 每次结果只追加到子列表；这些中间消息不回父列表。
  6. 子模型返回不含 tool_use 的文本时，子循环提取这段文本， run_subagent 返回它。
  7. 父侧把这个返回值包装成与 task 对应的 tool_result， 用原来的 tool_use_id 回填父 messages。
  8. 父模型下一轮只看到子任务的最终报告，而不是子 Agent 读过的所有文件结果。

如果子任务改了文件，父 Agent 仍可以在下一轮用 read_file 看到修改后的文件； 只是父消息里没有自动出现“子 Agent 当时调用了哪几个工具”的完整轨迹。

系统讲解

1. 新的 messages 到底隔离了什么？

s01–s05 的循环把每一次模型回复和工具结果追加到同一个列表。 messages 是发给模型的对话轨迹：模型下一次推理只能使用本次请求携带的 system、tools 和 messages。s06 的关键不是“把旧消息删掉”，而是创建一个新列表： 

本例 L1  child_messages = [
本例 L2      {"role": "user", "content": "请找出项目使用的测试框架"}
本例 L3  ]

子模型收到的上下文从这一项开始；它看不到父 Agent 之前的用户 prompt、父模型回复、 父侧的工具结果，除非父 Agent 把相关信息写进 prompt 文本中主动传给它。 这是一种显式传递关系，不是 Python 变量自动共享。

问题答案为什么
子 Agent 默认知道父 Agent 读过的文件吗？ 不知道 父的读取结果在父 messages，没有复制给子。
子 Agent 能重新读同一个文件吗？ 能 它在同一个 WORKDIR，并且拥有 read_file。
父 Agent 会自动看到子 Agent 的每个工具结果吗？ 不会 run_subagent 只返回最终文本。
子 Agent 写出的文件父 Agent 能看到吗？ 能 文件系统共享，消息列表不共享。

因此委派 prompt 要写得像一个交接单：说明目标、范围、禁止事项、需要返回的证据。 只写“帮我看看”可能让子 Agent 返回一个过于模糊的总结；上下文隔离减少了噪音， 但不会替你自动补全规格。

3. 为什么要禁止子 Agent 再委派？

如果子 Agent 也拥有 task，它可以再启动一个子 Agent； 新子 Agent 还可以继续启动下一个。这样会带来递归深度、预算、停止、错误传播和 并发管理问题。North s06 选择一个简单的教学边界： 父可以委派，子只做基础工作，不再委派。 

父：BASE_TOOLS + task
  └── 子：BASE_TOOLS
        └── 没有 task，因此到此为止

注意“没有 task”只表示子 Agent 的模型看不到这个工具并且 handler map 里没有它； 它并不表示子 Agent 不能调用五个基础工具。子 Agent 仍然可能读文件、改文件、执行 bash。能力集合是一个有限子集，不是只读模式。

4. extract_text：为什么返回的是文本而不是整个 response？

L260  def extract_text(content) -> str:
L261      if not isinstance(content, list):
L262          return str(content)
L263      return "\n".join(
L264          getattr(block, "text", "")
L265          for block in content
L266          if getattr(block, "type", None) == "text"
L267      )

真实源码： L260–267。

Messages API 返回的 response.content 是 content block 列表； 列表里可能有文本块，也可能有工具调用块。extract_text 的职责是 “从内容中拿出文本”，而不是解释工具调用、执行工具或保留完整子轨迹。

  1. L261 检查 content 是否是列表。正常 SDK 返回通常是列表，但这个分支 让函数遇到其他对象时也能返回字符串。
  2. L263–267 遍历列表，只保留 block.type == "text" 的块。 getattr(block, "text", "") 是按属性名读取 text；没有该属性就用空字符串。
  3. "\n".join(...) 把多个文本块用换行拼成一段字符串。 工具调用块不被拼进最终摘要。

这里的“只取文本”发生在子循环已经判断没有 tool_use之后。 如果回复里仍有工具调用，子循环不能直接把目前已有的文字当最终答案； 它必须先执行工具、回填结果，再让模型继续。

response.content子循环动作
含 tool_use 进入工具处理；不调用 extract_text 作为最终返回。
只有 text 认为本轮结束，提取文本并返回父 Agent。
没有可提取文本 返回 "(no summary)"，明确告诉父侧没有摘要。

s04 把 hooks 挂上循环，s05 的父循环直接写了权限、handler 和结果逻辑； s06 把“执行一个 block”的公共步骤抽成 execute_tool，让父循环和子循环 都能调用。handlers 参数决定当前使用哪个 map： 父传 TOOL_HANDLERS，子传 SUB_HANDLERS。

  2. L245 用 block.name 查当前 map；找不到时不崩溃，而是得到 Unknown: ... 文字。
  3. L246–249 执行 handler，并把异常转换成 Error: ...。 这让父子循环都用同一种工具结果形状。
  4. L251 在 handler 返回后触发 PostToolUse，L252 把输出转成字符串返回。

一个容易漏掉的细节：父子共享的是 hooks 注册表和执行函数， 但不是消息列表。子 Agent 的每个基础工具调用也会经过 trigger_hooks("PreToolUse", ...) 与 trigger_hooks("PostToolUse", ...)。所以“子上下文干净”不代表 “子调用不受权限检查”。

7. 子循环为什么仍然有 Stop hook？

s04 的 Stop hook 并不是父循环专属。子循环在 L287 发现本轮没有 tool_use 时，也会触发同一个 Stop 事件： 

L287  if not tool_calls:
L288      force = trigger_hooks("Stop", messages)
L289      if force:
L290          messages.append({"role": "user", "content": force})
L291          continue
L292      print("\033[35m[Subagent done]\033[0m")
L293      return extract_text(response.content) or "(no summary)"

当前注册的 summary_hook 只打印工具结果数量并返回 None，所以子 Agent 正常进入 L292–293。若未来注册一个返回非空字符串的 Stop callback，子 Agent 会把这条文字追加到子消息，再继续请求模型； 父 Agent 不会直接收到这条中间消息。

这也意味着 shared hooks 带来一致性，同时带来耦合：同一份全局 hooks 会在父循环和子循环 里触发。当前 summary_hook 的统计对象是谁传给它，取决于当前循环； 它第一次收到父 messages，子循环中又收到子 messages。

L303      })
L304  messages.append({"role": "user", "content": results})

真实源码： L295–304。

  1. results 是当前这一轮的结果批次，开始时为空。
  2. 每个 block 都调用一次 execute_tool(block, SUB_HANDLERS)； 由于这里没有线程或 async，代码按列表顺序同步执行。
  3. L298 只打印 output 的前 100 个字符作为人的终端预览； 它不是把 output 截断后再回给模型，L302 仍使用完整的 output。
  4. L301 使用当前 block 的 id，保证每个 tool_result 和具体 tool_use 配对。
  5. 所有 block 处理完后，L304 一次性把结果批次追加给子 messages，再请求子模型。

“一轮”仍然是一次模型回复中的整批工具调用，不是一个 block。 一次回复含 glob、read_file、bash 时， 子循环仍会逐个执行，但只在全部处理完后请求下一次模型回复。

9. task 的 schema 和父侧 dispatch

L310  TASK_TOOL = {
L311      "name": "task",
L312      "description": "Run a subagent with fresh conversation context and return its final text.",
L313      "input_schema": {
L314          "type": "object",
L315          "properties": {
L316              "prompt": {"type": "string", "minLength": 1},
L317          },
L318          "required": ["prompt"],
L319      },
L320  }
L321  TOOLS = [*BASE_TOOLS, TASK_TOOL]
L322  TOOL_HANDLERS = {**BASE_HANDLERS, "task": run_subagent}

真实源码： L310–322。

第一次看到这个 schema 时，把它翻译成人话：

  • name: "task" 是模型发出的工具名，必须与 handler map 的键相同。
  • description 告诉模型这个工具会开启 fresh conversation，并返回 final text。
  • type: "object" 表示输入是对象，在 Python 里通常表现为字典。
  • prompt 是唯一字段，类型是字符串，并且至少要有一个字符。
  • required: ["prompt"] 表示调用时必须提供 prompt；这不是子任务完成标准。

父模型发出： 

{"name": "task", "input": {"prompt": "找出项目使用的测试框架并说明证据"}}

进入父侧 handler map 后，等价于： 

run_subagent(prompt="找出项目使用的测试框架并说明证据")

注意 TOOLS 和 TOOL_HANDLERS 不是重复定义： 前者发给模型，后者留在本地执行。模型只知道工具说明，不会直接拿到 run_subagent 这个 Python 函数。

10. 父循环怎样接住子结果？

L328  def agent_loop(messages: list):
L329      while True:
L330          response = client.messages.create(
L331              model=MODEL,
L332              system=SYSTEM,
L333              messages=messages,
L334              tools=TOOLS,
L335              max_tokens=8000,
L336          )
L337          messages.append({"role": "assistant", "content": response.content})
L339          tool_calls = [
L340              block for block in response.content if block.type == "tool_use"
L341          ]
L343          if not tool_calls:
L344              force = trigger_hooks("Stop", messages)
L345              if force:
L346                  messages.append({"role": "user", "content": force})
L347                  continue
L348              return
L350          results = []
L351          for block in tool_calls:
L352              output = execute_tool(block, TOOL_HANDLERS)
L353              results.append({
L354                  "type": "tool_result",
L355                  "tool_use_id": block.id,
L356                  "content": output,
L357              })
L358          messages.append({"role": "user", "content": results})

真实源码： L328–358。

父循环的主体仍然是 s01–s05 的“模型 → tool_use → handler → tool_result”； 只有 L352 的 handler 可能执行一段嵌套循环。对父循环来说，子 Agent 仍只是一个工具：

  1. 父模型产生 task block。
  2. execute_tool 在父侧先过 PreToolUse，然后查到 run_subagent。
  3. run_subagent 内部运行子循环，直到最终文本或 30 轮上限。
  4. 父侧 execute_tool 得到这个文本，并触发父侧 PostToolUse。
  5. 父侧 L353–357 把文本当作 task 的 tool_result content。
  6. 父侧 L358 把结果追加到父 messages，父模型下一轮读取它。

因此父模型收到的不是 Python 返回值对象，也不是子 messages 列表，而是一个普通的 tool_result content 字符串。子任务的“报告质量”取决于子 prompt 和子模型最终返回的文字。

11. 父子循环的 hook 时机：同一注册表，不同 messages

s06 保留 s04 的 HOOKS、权限规则和四个事件；变化是 execute_tool 让父子基础工具调用共享这套执行边界。一次 task 可能出现如下日志顺序： 

父 PreToolUse(task)
  子 PreToolUse(glob)
  子 PostToolUse(glob)
  子 PreToolUse(read_file)
  子 PostToolUse(read_file)
  子 Stop
父 PostToolUse(task)
父 Stop

这不是说所有调用都必然有这条精确序列，而是帮助你理解嵌套关系： 子循环先完整结束，父侧 task handler 才返回；父侧的 PostToolUse 才有机会运行。 如果子工具被权限 hook 拒绝，拒绝结果回到子 messages，子模型可以根据观察决定下一步。

事件父循环可能收到子循环可能收到
UserPromptSubmit 外层 REPL 提交用户输入时 本实现不会在 run_subagent 内再次触发；子 prompt 直接初始化 messages
PreToolUse task 或其他父工具执行前 子 Agent 的基础工具执行前
PostToolUse 父侧 handler（包含整个 task）返回后 子基础工具 handler 返回后
Stop 父回复无工具调用、准备退出时 子回复无工具调用、准备返回文本时

辨析名字和真实调用：run_subagent 内部没有调用 trigger_hooks("UserPromptSubmit", prompt)；所以不要因为子任务也“像一个新会话” 就推断它会打印一条 UserPromptSubmit。真实代码的入口路径决定事件是否发生。

12. 30 轮上限和父循环的上限不是一回事

L274  for _ in range(30):
    # 子 Agent 最多尝试 30 个模型回复轮次
L306  return "Subagent stopped after 30 turns without a final answer."

L329  while True:
    # 父 Agent 没有在本章代码中设置 max_turns

子循环用 range(30) 给自己设置了局部预算。30 次都没有出现“无 tool_use 的最终回复”时，它返回固定文本，父 Agent 会把这段文本当作 task 的工具结果。这个返回并不抛 Python 异常，也不自动重试。

父循环仍是 while True。因此不能把“子循环有 30 轮”误读为 “整个 Agent 总共最多 30 轮”：父侧在收到子结果后可能继续调用其他工具，直到自己的 回复没有 tool_use，或者某个 Stop hook 改变控制流。max_tokens=8000 也只是单次模型回复的 token 上限，不是子循环轮数。

把状态放回正确的位置

s05 让我们见过计划状态、父消息和工作区文件；s06 的独立脚本沿用基础工具和 hooks， 再增加一份子消息列表。注意 North 每章是一个可单独运行的教学版本： s06 的 BASE_TOOLS 不包含 s05 的 todo_write， 所以下表只列 s06 实际拥有的状态：

状态位置父 / 子关系生命周期谁能直接看到
父 messages 父专有 外层 REPL 当前进程内持续追加 父模型；子不会自动看到
子 messages 子专有 一次 run_subagent；返回后仍在函数局部，但不回传列表 子模型；父只收到最终文本
WORKDIR 下文件 父子共享 直到文件再次被修改 / 删除 父子基础工具和操作系统
HOOKS 注册表共享 模块加载后持续存在 父子执行工具时都会触发

本课的父、子 Agent 都没有 todo_write：s06 选择把注意力放在 “委派与上下文边界”上，而不是把 s05 的计划工具继续叠进脚本。 子 Agent 没有 task 则是另一条更关键的能力边界。 不要把“子 Agent 有自己的消息”推断成“子 Agent 自动拥有前一课的全部能力”。

三种常见的委派边界

案例一：只读调查，最适合隔离上下文

Use a subtask to find what testing framework this project uses.
Read the relevant configuration files and return the framework name plus file evidence.
Do not modify files.

这个任务的输出是一个短报告，父 Agent 不需要知道子 Agent 读过的每个文件。 prompt 同时给了范围、证据要求和禁止修改，适合作为子任务。

案例二：子 Agent 修改共享工作区，父 Agent 必须验证

Use a task to create s06_subagent/example/string_tools.py
with a slugify(text: str) function, then verify it from the parent agent.

子 Agent 可以调用 write_file 创建文件，父 Agent 随后能看到它； 但“能看到文件”不等于“文件正确”。父 prompt 明确要求 verify，父 Agent 仍应调用 read_file 或 bash 检查真实结果。子返回“已创建”只是报告， 不是独立的测试证据。

案例三：把一个过大的任务原样塞给子 Agent，不等于完成拆分

请把整个认证模块重构好。

这句话没有说明边界、完成条件、允许修改的路径、验证命令或返回格式。 虽然技术上可以调用 task，但上下文边界不会自动把“大任务”变成好任务。 更好的拆分是先由父 Agent 定义一个可交付子任务，例如“只调查认证入口并返回调用链， 不修改文件”，再让父 Agent 根据报告决定下一步。

相对 s05，究竟增加了什么？

位置s05s06要记住的变化
工具集合 父循环有 bash、文件工具、glob、todo_write 父循环增加 task；子循环只有五个基础工具 委派能力只向父开放，子不再递归委派
循环数量 一个父 Agent loop 父循环可同步进入一个子 Agent loop 子循环结束后只返回最终文本
消息状态 主要是一份 history / messages 父子各有独立 messages 中间对话隔离，结果跨边界回传
执行环境 父使用当前 WORKDIR 父子仍使用同一 WORKDIR 和同一进程 上下文隔离不等于文件隔离
工具执行代码 父循环内直接执行 execute_tool(block, handlers) 同时复用 通过参数选择父 / 子 handler map
停止边界 父循环由 Stop hook 决定退出 子循环有 Stop hook 和 30 轮上限，父循环仍独立 子耗尽预算后返回普通文本，不代表父循环结束

观察一：子 Agent 的内部读取不会原样回父

Use a subtask to find what testing framework this project uses.
Return the framework name and the exact configuration file that proves it.
Do not modify files.
  1. 外层先出现 UserPromptSubmit 日志。
  2. 父模型若选择 task，看到父侧的工具日志。
  3. 子侧出现 [Subagent started]，基础工具调用显示为 [sub] ...。
  4. 子侧出现 [Subagent done] 后，父模型收到一段 task tool_result 文本。
  5. 检查父侧最终对话：父不会自动收到子 Agent 的每一个 read_file 结果。

观察二：共享文件，但不共享消息

如需练习写入，请只使用可丢弃路径，并明确让父 Agent 验证： 

Use a task to create s06_subagent/example/subagent-demo.txt
containing exactly "created by child", then have the parent read it and verify the content.

运行前确认允许本地教学文件被写入；结束后可手动删除这个临时文件。 重点观察：子 Agent 的 write_file 会改工作区，父 Agent 的 read_file 能看到结果；这两件事不依赖共享 messages。

观察三：权限 hook 仍在子循环生效

不要为了测试执行破坏性命令。只需读代码和日志即可知道：子 Agent 的基础工具通过 execute_tool，所以它调用危险 bash 或越界文件路径时，仍会触发 permission_hook。安全边界没有因为“委派”自动消失。

常见坑 + 边界

  • Subagent 是一个新的 Python 进程：错。当前实现是在同一进程里同步 调用 run_subagent；隔离的是 messages，不是进程。
  • 子 Agent 自动看到父 Agent 的上下文：错。 子列表从自己的 user prompt 开始；父信息必须显式写入 prompt。
  • 父 Agent 会看到子 Agent 的所有工具调用：错。 子内部 messages 留在 run_subagent；父只收到最终文本作为 task result。
  • 子 Agent 不能修改文件：错。子拥有 write / edit / bash， 并且和父共享 WORKDIR；是否允许要靠任务说明和权限 hook。
  • fresh messages 等于安全沙箱：错。消息隔离解决上下文噪音， 不解决文件副作用、命令权限或网络访问。
  • 子 Agent 也能继续调用 task：当前实现错。 SUB_TOOLS 和 SUB_HANDLERS 都只包含基础工具， 本课限制为一层委派。
  • SUB_TOOLS = list(BASE_TOOLS) 会深复制所有工具对象： 不要这样理解。它创建了新的外层列表；本课没有修改其中的工具字典， 所以足以表达子工具集合，但不是通用深拷贝保证。
  • task 工具自己直接执行子任务：错。task 的 handler 是 run_subagent，它启动一个子模型循环；子循环再决定是否调用基础工具。
  • 子模型只回复一段文字就一定成功：错。无 tool_use 只说明它到达 “最终回复”分支；内容是否正确仍需父 Agent 或外部验证。
  • 30 轮是整个父子系统的总预算：错。30 轮只限制一次 run_subagent；父循环仍有自己的 while True。
  • 子循环的 Stop hook 不会运行：错。子在没有 tool_use、准备返回最终文本 时也调用 trigger_hooks("Stop", messages)。
  • 子 prompt 提交会再次触发 UserPromptSubmit：当前错。 run_subagent 直接创建 messages，没有调用该事件；外层 REPL 才触发用户输入事件。
  • 子工具不需要权限检查：错。子基础工具经过同一个 execute_tool，会走共享的 PreToolUse / PostToolUse。
  • 任务越大越应该整个交给一个子 Agent：不一定。 委派仍需要清楚的目标、边界、证据和完成条件；把模糊的大任务原样转交只是换了一个上下文。
  • 子 Agent 返回“已完成”就等于文件正确：错。 返回文本是报告；父 Agent 仍要用 read / bash 等观察和验证。
  • 父侧 task 的 PostToolUse 在子工具执行前触发：错。 父侧 task handler 要等整个 run_subagent 返回后才有 output， 然后父侧 PostToolUse 才运行；子工具自身有自己的 PostToolUse。

过关标准

  • 能用一句话解释 Subagent：父 Agent 通过 task 委派，子 Agent 用 fresh messages 完成子任务，只把最终文本返回。
  • 能明确区分三条边界：消息隔离；同一进程和 WORKDIR 共享；子工具能力是基础工具子集。
  • 能从 SUB_TOOLS = list(BASE_TOOLS) 与 TOOLS = [*BASE_TOOLS, TASK_TOOL] 解释为什么只有父能继续委派。
  • 能解释 extract_text 只提取 text block，以及为什么有 tool_use 时必须先执行工具。
  • 能从 execute_tool(block, handlers) 推导父用 TOOL_HANDLERS、子用 SUB_HANDLERS，并说明 hooks 如何复用。
  • 能按真实顺序讲出一次 task：父 tool_use → 子新 messages → 子工具循环 → 子最终文本 → 父 tool_result → 父继续。
  • 能区分子循环的 30 轮上限、父循环的 while True、单次 max_tokens 上限；不能把三个旋钮混为一谈。
  • 能指出当前 run_subagent 不会触发 UserPromptSubmit， 但子基础工具会经过共享的 PreToolUse / PostToolUse，子结束时会经过 Stop。
  • 能说明子 Agent 返回文本不等于任务已经正确完成；父 Agent 仍要根据完成定义做验证。
  • 真跑 python s06_subagent\code.py，至少观察一次 [Subagent started]、一次 [sub] 工具日志和一次 [Subagent done]；能解释父只收到最终文本而文件仍共享。
