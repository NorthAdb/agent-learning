为什么现在学？

只有 bash 时，模型心里是「读文件」，嘴里却要拼 cat / type。 多一层翻译，浪费 token，Windows 上还容易拼成 Unix 命令卡住（0021 的 date）。 专用工具让模型直接说 read_file。扩展方式必须是注册，不能每加一个工具就改循环骨架。

README「只有 bash 一个工具」 L12–16。

和 Java 怎么对照

s02 概念Java 直觉关键差异
handler 实现某一接口的处理类 / 方法 s02 的 handler 是普通函数对象，不是 Java 接口名。
dispatch map Map<String, Handler> 键必须等于 schema 的 name，不等于 Python 函数名 run_read。
dispatch map.get(name).handle(args) 是查表调用，不是第二套 Agent loop。
REPL 控制台里反复读一行再处理 外层 s02 >>；内层才是工具循环。
TOOL_HANDLERS Map<String, Function> / 策略表 就是本课的 dispatch map，不是另一张表。
handler(**block.input) 反射按参数名调用，或 DTO 再拆字段 模型给的 JSON 键必须对上函数形参名。
safe_path 把用户路径规范到工作根下，拒绝 .. 只罩 file 工具；bash 仍可乱走，那是 s03。
多个 tool_use for 循环按列表顺序调用 教学版不并行；生产 CC 会按 batch 并发，本课不实现。

系统讲解

1. 问题：一个 bash，模型在翻译

s01 能做事，但读 / 写 / 改 / 找文件都要绕 shell。 模型想的是动作，给的却是命令字符串。专用工具把「动作」写进 schema，少一层翻译。

2. 三个词：handler、dispatch map、dispatch

不要把它们当成一个东西。map 是表，handler 是表上的人，dispatch 是查表派单。

词是什么s02 落点
handler 真正干活的处理函数 run_bash / run_read / run_write / run_edit / run_glob
dispatch map 「名字 → handler」的对照表 字典 TOOL_HANDLERS
dispatch 按模型给的工具名查表并调用 handler = TOOL_HANDLERS.get(block.name) 再 handler(**block.input)

可以想成分诊：客人说「read_file」，前台（dispatch）查表（map），把单子递给 run_read（handler）。模型不会自己去调 Python 函数。

键是 schema 的 name（read_file），值才是函数对象 run_read（无括号）。两边名字可以不同，靠这张表缝合。

表： L143–146。 派单： L170–171。

3. 规则：加一个工具 = 两条注册，循环不动

  1. 在 TOOLS 里加一条 schema（给模型看）。
  2. 在 TOOL_HANDLERS 里加 "名字": 函数（给 Harness 执行）。

README 格言：加一个工具，只加一个 handler。 循环里那一行从硬编码 run_bash(...) 换成查表。

README L6–7、 L24–29。

4. 三种接法（易混）

案执行那一行判定
① s01 output = run_bash(block.input["command"]) 写死一个工具。再加 read 就要改 if/else，循环发胖。
② s02（要认） handler = TOOL_HANDLERS.get(block.name) 再 handler(**block.input) 循环形状不变，扩展走注册表。
③ 错法 为每个工具复制一个 agent_loop 骨架被拆碎。North 后面 18 章都叠在同一根循环上。

0012 的 ToolRegistry「存函数、按名调用」是同一肌肉；本课是它在真实 Messages 循环里的落地。

5. 一轮里多个 tool_use：教学版串行

模型可以一次返回「读 a.py、读 b.py、glob *.py」。 s02 按 response.content 出现顺序 一个接一个 跑，每个都有自己的 tool_use_id，结果打进同一条 tool_result 列表。 这不是并行，也不是三个循环。

C. safe_path（L71–75）

def safe_path(p: str) -> Path:
    path = (WORKDIR / p).resolve()
    if not path.is_relative_to(WORKDIR):
        raise ValueError(f"Path escapes workspace: {p}")
    return path

WORKDIR / p：相对路径接到工作区。已经是绝对路径时，Path 的 / 会换成那条绝对路径 （仍要过下一行检查）。

.resolve()：展开 .. 和符号链接，得到真实绝对路径。 不问「字符串长什么样」，问「最终落在哪」。

is_relative_to(WORKDIR)：解析后是否仍在工作区树下。

案输入结果
① 正常README.md工作区内的文件，放行
② 逃逸../secret.txtresolve 后跑出 WORKDIR，抛 ValueError
③ 盘符外Windows 下另一盘的绝对路径同样不是 relative_to，拒绝

handler 里 try/except Exception 会把这次异常变成 Error: ... 字符串，循环不崩。

D. 四个文件工具逐行（L78–123）

schema 名是 read_file 等，函数名是 run_read 等，靠 TOOL_HANDLERS 缝合。四个函数都是：先 safe_path（glob 在循环里再滤）， 出错一律变成 Error: ... 字符串，循环不崩。

D1. run_read → 工具名 read_file

def run_read(path: str, limit: int | None = None) -> str:
    try:
        lines = safe_path(path).read_text().splitlines()
        if limit and limit < len(lines):
            lines = lines[:limit] + [f"... ({len(lines) - limit} more lines)"]
        return "\n".join(lines)
    except Exception as e:
        return f"Error: {e}"
行在干什么
L78 形参 path 对应 schema 的 required 字段。 limit: int | None = None 是联合类型：整数或 None（0009 见过 |）。 默认 None = 不截断。schema 里 limit 不是 required，模型可以不传。
L80 safe_path(path) 得到工作区内的 Path， read_text() 读成一个字符串（默认 UTF-8）， splitlines() 按行切成列表，去掉行尾换行符。
L81–82 if limit and limit < len(lines)： limit 为 None 或 0 时左边为假，不截断。 真要截时只留前 limit 行，再追加一行说明还剩多少行。 这是给模型看的预览，不是把文件从磁盘删掉。
L83 "\n".join(lines) 把行列表拼回一块文本，作为 tool_result。
L84–85 文件不存在、safe_path 拒绝、解码失败，都进这里。 返回字符串，不把异常甩出循环。

L78–86。 Path.read_text： 官方。

D2. run_write → 工具名 write_file

def run_write(path: str, content: str) -> str:
    try:
        file_path = safe_path(path)
        file_path.parent.mkdir(parents=True, exist_ok=True)
        file_path.write_text(content)
        return f"Wrote {len(content)} bytes to {path}"
    except Exception as e:
        return f"Error: {e}"
行在干什么
L88 两个必填形参，对齐 schema 的 path + content。
L90 先过路径围栏，得到要写的那个 Path。
L91 parent 是文件所在目录。 mkdir(parents=True, exist_ok=True)：中间目录没有就建，已经有也不报错（0007）。 这样 a/b/c.py 在 a/b 不存在时也能写。
L92 write_text(content)：整文件覆盖，不是追加。 原内容会被换成 content。
L93 成功观察用 len(content) 当字节数近似（UTF-8 下中文一字符多字节，这是字符数不是严格 UTF-8 字节数；教学上够用）。 返回给模型的是确认语，不是文件正文。
L94–95 路径非法、磁盘满、权限不够 → Error: 字符串。

L88–95。

D3. run_edit → 工具名 edit_file

def run_edit(path: str, old_text: str, new_text: str) -> str:
    try:
        file_path = safe_path(path)
        text = file_path.read_text()
        if old_text not in text:
            return f"Error: text not found in {path}"
        file_path.write_text(text.replace(old_text, new_text, 1))
        return f"Edited {path}"
    except Exception as e:
        return f"Error: {e}"
行在干什么
L98 三个必填：路径、要换成的旧片段、新片段。对齐 schema 的 old_text / new_text。
L100–101 围栏之后读出全文到内存。大文件会很重；s02 不处理这一点。
L102–103 old_text not in text：子串精确匹配，不是正则、不是按行。 找不到就返回错误字符串（走 return，不是 raise），模型下一轮能看到「没找到」。
L104 str.replace(old, new, 1) 的 1 是最多替换次数：只改第一处。 文件里两段相同旧文本时，第二段不动。改完立刻写回磁盘。
L105 成功只回文件名确认，不把新全文再塞进轨迹。
L106–107 读失败、围栏拒绝等进通用 except。

L98–107。 str.replace 第三参数： 官方。

D4. run_glob → 工具名 glob

def run_glob(pattern: str) -> str:
    import glob as g
    try:
        matches = sorted({
            match for match in g.glob(
                pattern, root_dir=WORKDIR, recursive=True)
            if (WORKDIR / match).resolve().is_relative_to(WORKDIR)
        })
        shown = matches[:200]
        if len(matches) > 200:
            shown.append("... (more matches omitted; narrow the pattern)")
        return "\n".join(shown) if shown else "(no matches)"
    except Exception as e:
        return f"Error: {e}"
行在干什么
L110 只要一个 pattern，如 *.py、**/*.md。
L111 函数内部 import glob as g：标准库模块也叫 glob，工具对外也叫 glob。改名 g 避免和工具名、函数名搅在一起。 0014 已过关 glob。
L113–117 g.glob(..., root_dir=WORKDIR, recursive=True)：从工作区当根匹配， ** 才能递归。每个命中再 resolve + is_relative_to， 用集合去重后排序。 root_dir 是 3.10+ 的参数 （glob.glob）。
L118–120 最多回 200 条；更多就追加一行提示，让模型把 pattern 收窄。
L121 有命中：每条路径一行。零命中：(no matches)，不是异常、也不是空字符串 （空串对模型更难读）。
L122–123 非法 pattern 等进 Error:。

这四个都不经过 run_bash。bash 仍在表里，但读文件应走 read_file， 这正是本课要观察的黄字 > read_file。

L110–123。

F. response 的完整结构

client.messages.create(...) 返回 SDK 的 Message 对象（本课变量名 response）。 HTTP JSON 与 Python 属性同名；读的时候用 response.content，不是 response["content"]。

对象上仍有 stop_reason；当前循环只筛 content 里的 tool_use。其余字段每次都在，循环不碰。 DeepSeek 兼容端点核心形状相同；container / stop_details / 缓存用量等可选字段经常是 null 或根本没有。 

response                          # Message
├─ id                 str         # 本条消息 ID，常见 msg_...
├─ type               "message"   # 对象种类；别和 block.type 搞混
├─ role               "assistant" # 永远是助手，不会是 user
├─ model              str         # 实际用的模型名
├─ content            list        # 内容块，按出现顺序
├─ stop_reason        str | null  # 为何停（见下表）
├─ stop_sequence      str | null  # 命中了哪条自定义停词；没配就是 null
├─ usage              object      # token 账
│   ├─ input_tokens
│   ├─ output_tokens
│   ├─ cache_creation_input_tokens   # 可选
│   ├─ cache_read_input_tokens       # 可选
│   ├─ cache_creation                # 可选，按 TTL 拆
│   ├─ output_tokens_details         # 可选
│   ├─ server_tool_use               # 可选
│   ├─ service_tier                  # 可选 standard / priority / batch
│   └─ inference_geo                 # 可选
├─ container          object | null  # 代码执行容器；s02 不用
└─ stop_details       object | null  # 拒答细项；s02 不用
顶层字段含义s02 用不用
id 这一条 assistant 消息的 ID。和下面 tool_use 块自己的 id（常见 toolu_...）不是同一个。 不用
type 固定 "message"。表示「这是一条 Message」，不是内容块种类。 不用
role 固定 "assistant"。L159 自己再写一遍 "role": "assistant" 放进轨迹。 不用（轨迹里手写）
model 服务端实际用的模型字符串。 不用
content 块列表。L159 整表追加；L161–163 筛 tool_use。 用
stop_reason 本轮为什么停。非流式调用里应有值。 用（L158）
stop_sequence 仅当 stop_reason == "stop_sequence" 时，这里是命中的那串自定义停词。 不用（s02 没配 stop_sequences）
usage 本请求的 token 计数。文档写明：账上的 token 不必和可见字符一一对应。 不用
container 官方代码执行工具用的容器信息（id / 过期时间 / skills）。 不用
stop_details 拒答时的结构化说明（如策略类别）。 不用

stop_reason 官方枚举（本机 SDK StopReason）：

F2. L161–175 对着上面那份 content 走

tool_calls = [
    block for block in response.content if block.type == "tool_use"
]
if not tool_calls:
    return

results = []
for block in tool_calls:
    print(f"\033[33m> {block.name}\033[0m")
    handler = TOOL_HANDLERS.get(block.name)
    output = handler(**block.input) if handler else f"Unknown: {block.name}"
    print(str(output)[:200])
    results.append({
        "type": "tool_result",
        "tool_use_id": block.id,
        "content": output,
    })
messages.append({"role": "user", "content": results})
行在干什么
L161–163 从 content 里筛出 tool_use 块，保持原始顺序。 text 不进这张表，但已经在 L159 进轨迹了。
L164–165 表是空的 = 本轮没有工具调用，return。 这是当前脚本的循环出口，不读 stop_reason。
L167–168 准备观察列表，按筛出的块串行执行。教学版不并行。
L169 黄字打印 block.name（read_file），不再打印 $ command：五个工具的参数字段不同，不能假定都有 command。
L170 用名字去 dispatch map 取 handler。 .get 找不到返回 None，不会 KeyError。
L171 有 handler：**block.input 拆成关键字参数再调用 （run_read(path="README.md")）。 没有：观察写成 Unknown: 那个名字，循环继续。
L172 把观察的前 200 个字符打到你的终端（人看的）；完整 output 仍进 results 给模型。
L173 一条 tool_result：tool_use_id 必须等于这个块的 block.id，模型才知道「哪一次调用」对应这段输出。 content 是字符串（handler 的返回值）。

循环结束后 L175： messages.append({"role": "user", "content": results})。 这里的 user 仍是协议里的「工具观察从外侧送回」，不是你又打了一行。 然后 while True 回到 L155，带着更长的轨迹再调模型。

G. REPL（L178–196）

REPL = Read-Eval-Print Loop，不是 API 字段。外层 s02 >> 跟人对话； 内层 agent_loop 才跟模型和工具转圈。两个都是 while True，职责不同。

字母意思s02 外层
Read读你敲的一行query = input("s02 >> ")
Eval拿去跑agent_loop(history)
Print把结果印出来打印最终 text 块
Loop再回到 Read外层 while True

Python 的 >>> 也是 REPL。q / 空回车 / Ctrl+C 结束的是这个 REPL。 打印最终 text 时这里没有 isinstance(..., list)，默认最后一条 content 已是块列表。

常见坑 + 边界

  • 加工具就要改 while：错。改 TOOLS + TOOL_HANDLERS。
  • 函数名必须等于工具名：错。对齐的是字典的键和 schema 的 name。
  • safe_path = 已经安全：只罩文件工具；bash 仍是洞，s03 才关门。
  • ** 是乘法：在调用处是解包关键字参数。
  • 多个 tool_use 就是并行：教学版严格按列表顺序串行。
  • dispatch map = dispatch = handler：map 是表，handler 是函数，dispatch 是查表调用。
  • 以为 response 就是一段字符串：它是 Message 对象；要执行的工具在 content 列表的 tool_use 块里。
  • system 是一条 role: system 消息：错。它是 create 的顶层参数，不进 messages。
  • TOOL_HANDLERS 会发给模型：错。发出去的是 TOOLS schema；handlers 只在本机。
