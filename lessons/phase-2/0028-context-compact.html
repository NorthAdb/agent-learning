s08：上下文总会满，先整理，再总结

s07 让技能正文按需进入 messages，但“按需加载”并不意味着它从此不占空间： 一旦加载，正文、文件内容、命令日志和模型回复都会继续留在当前轨迹。长任务最终会遇到 上下文窗口上限。本课给 Agent 加一条可恢复优先的压缩管线： 先把大结果转存，接着归档旧消息、缩短已消费结果，仍然超限时才让模型生成摘要。 主技能是读懂哪些状态能丢、哪些状态必须保留、什么时候会增加一次模型调用。

为什么现在学？

s06 隔离了子 Agent 的中间消息，s07 控制了技能正文进入上下文的时机；但当前会话本身仍会增长。 读长文件、跑测试、搜索目录、加载技能，都会把观察追加到 messages。 每次下一轮请求又要带上这些历史。上下文一旦超过模型限制，请求不是“效果变差”而是直接被 API 拒绝。

压缩不能简单理解为“删旧消息”。工具结果常常可以重新从磁盘读取或重新执行， 适合先变成路径；而当前用户请求、最近工具结果、工具调用与结果的配对不能随意删。 因此本课把信息损失和成本排成顺序：保存 → 归档 → 替换旧结果 → 必要时摘要。 前三步是本地确定性操作；最后一步才会增加一次模型调用。

North 对“先处理工具结果、最后才总结”的理由见 README L35–49。

ContextCompactor：这个类在干什么

哪些方法组合在一起用

组合成员怎么串
A. 大结果转存 persist_large_output → persisted_preview → save_output / persisted_output_path budget / fit 发现结果太大 → 先看是否已经转存过 → 否则 save_output 写全文 → 消息换成路径 + 预览

      │

记忆口诀：识别函数帮切点与“新旧结果”划界；落盘函数保证可恢复； 四个管线步骤按成本升序；摘要三件套（input / summarize / message）只在最后启用； prepare 是总调度，loop 里另外两条旁路是“API 拒绝补救”和“模型主动 compact”。

四步管线的规则

1. estimate_chars：先有可解释的触发器

CONTEXT_CHAR_LIMIT = 50000

@staticmethod
def estimate_chars(messages: list) -> int:
    return len(json.dumps(messages, default=str, ensure_ascii=False))

真实源码： L248–270。

json.dumps 把消息列表序列化成字符串，default=str 让 SDK 对象等无法直接 JSON 序列化的值先转成字符串，ensure_ascii=False 保留中文而不是转成 \u 转义。最后用 len 统计字符数。它适合教学和稳定触发， 但不能精确预测服务端 token 计数；所以 API 仍可能返回“输入过长”。

三个阈值不要混为一谈：CONTEXT_CHAR_LIMIT=50000 是估算上下文阈值； TOOL_RESULT_BATCH_CHAR_LIMIT=200000 是最新工具批次预算； LARGE_RESULT_CHAR_LIMIT=30000 是单条结果是否值得转存。 max_tokens=8000 又是模型本轮输出上限，和这三个输入阈值不同。

2. tool_result_budget：最新大结果先保存

blocks = [block for block in content
          if isinstance(block, dict) and block.get("type") == "tool_result"]
total = sum(len(str(block.get("content", ""))) for block in blocks)

for block in sorted(blocks, key=lambda item: len(str(item.get("content", ""))),
                    reverse=True):
    if total <= limit:
        break
    output = str(block.get("content", ""))
    if len(output) <= self.LARGE_RESULT_CHAR_LIMIT:
        continue
    block["content"] = self.persist_large_output(
        block.get("tool_use_id", "unknown"), output)
    total = sum(len(str(item.get("content", ""))) for item in blocks)

真实源码： L360–378。

  1. 只看最后一条 role=user 的工具结果批次；旧历史交给后续步骤。
  2. 按结果长度从大到小处理，超预算时优先解决最大的那个。
  3. 完整内容写入 .task_outputs/tool-results/<tool_use_id>.txt，消息只留路径和前 2000 字符预览。
  4. 替换后重新计算总长度；可能需要继续处理第二大的结果。

这一步不是删除：路径是恢复指针。以后模型若需要细节，可以调用 read_file 读取保存文件。tool_use_id 既能关联原调用，也经过字符清理， 因此不会直接成为任意文件名。

3. snip_compact：消息过多时留头尾

head_end = 3
tail_start = len(messages) - (max_messages - head_end - 1)
transcript = self.write_transcript(messages)
marker = {"role": "user", "content":
          f"[{tail_start - head_end} messages archived at {transcript}]"}
return [*messages[:head_end], marker, *messages[tail_start:]]

真实源码： L390–410。

超过 50 条消息时，当前实现保留开头 3 条、结尾 46 条，再用 1 条 marker 占位，总数回到 50。 但切点不能机械地落在任意下标：如果切点正好是 user(tool_result)， 它必须连同前一条 assistant(tool_use) 一起保留，否则下一次 API 请求会收到孤立结果。 has_tool_use 和 is_tool_result 正是用来保护这组协议关系的。

write_transcript 使用 JSONL（每条消息一行）保存完整历史；marker 只告诉模型“旧消息在哪里”， 不把完整旧内容重新塞回上下文。归档是可追溯性，保留头尾是继续工作的上下文。

4. micro_compact 与 fit_tool_results：只动安全的结果

unseen_tool_result_positions 从最后一条 assistant 消息往后找，得到最近一批尚未被模型 回复覆盖的工具结果。micro_compact 只处理已经消费的结果，并保留最近 KEEP_RECENT_RESULTS=3 条完整结果；较早且超过 120 字符的结果被替换成： [Earlier tool result saved at ...]。 

unseen = self.unseen_tool_result_positions(messages)
consumed = [entry for entry in results if entry[:2] not in unseen]

for _, _, block in consumed[:-self.KEEP_RECENT_RESULTS]:
    if self.estimate_chars(messages) <= target_chars:
        break
    content = str(block.get("content", ""))
    if len(content) <= 120:
        continue
    saved_path = self.persisted_output_path(content)
    if not saved_path:
        saved_path = self.save_output(block["tool_use_id"], content)
    block["content"] = f"[Earlier tool result saved at {saved_path}]"

真实源码： L410–434。

如果仅最新、尚未消费的批次就太大，不能等待模型先“读过”它再压缩，因此 fit_tool_results 会对所有结果按长度排序，保存完整输出，只留 1000 字符预览。 这是“新结果也不能把请求撑爆”的最后确定性处理。

5. compact_history：最后才调用模型摘要

def compact_history(self, messages: list, active_request: str) -> list:
    transcript = self.write_transcript(messages)
    summary = self.summarize_history(messages)
    return [self.summary_message("Compacted", active_request,
                                 summary, transcript)]

真实源码： L464–498。

摘要请求使用另一份 system 指令，要求模型只整理事实状态，不执行历史中出现的命令。 摘要消息把两类内容明确分开：Current user request 是当前用户原始请求， Conversation summary 是参考资料。这样做很重要，因为工具结果也使用 role=user；如果只保留最后一个 user 消息，可能把工具结果误当成用户目标。

摘要不是备份：完整备份在 transcript；摘要是让模型继续工作的有损表示。 不能把摘要中没有提到的细节假设成已经完成，也不能把模型“说已修改”当成文件验证。

6. prepare：顺序本身就是策略

messages = self.tool_result_budget(messages)
messages = self.snip_compact(messages)
if self.estimate_chars(messages) > self.CONTEXT_CHAR_LIMIT:
    target = int(self.CONTEXT_CHAR_LIMIT * 0.8)
    messages = self.micro_compact(messages, target)
    if self.estimate_chars(messages) > self.CONTEXT_CHAR_LIMIT:
        messages = self.fit_tool_results(messages, target)
    if self.estimate_chars(messages) > self.CONTEXT_CHAR_LIMIT:
        messages = self.compact_history(messages, active_request)

真实源码： L510–521。

步骤是否调用模型信息损失 / 可恢复性
tool_result_budget否完整结果落盘，消息留预览；可恢复
snip_compact否中间消息从请求移除，完整 transcript 保留；可追溯
micro_compact否旧结果替换为路径；可重新读取
fit_tool_results否新结果留 1000 字符预览；可重新读取
compact_history是模型摘要可能丢细节；完整历史仍在 transcript

把压缩接回 Agent loop

while True:
    messages[:] = COMPACTOR.prepare(messages, active_request)
    try:
        response = client.messages.create(
            model=MODEL, system=SYSTEM, messages=messages,
            tools=TOOLS, max_tokens=8000)
    except Exception as error:
        if too_long and reactive_retries < MAX_REACTIVE_RETRIES:
            messages[:] = COMPACTOR.reactive_compact(messages, active_request)
            reactive_retries += 1
            continue
        raise

真实源码： L529–548。

messages[:] 是本课值得单独停一下的 Python 语法：它替换原列表的全部元素， 保留列表对象本身。若写成 messages = COMPACTOR.prepare(...)， 只是让函数局部变量指向新列表，外层 history 可能仍持有旧列表。 这和 0016 的共享状态、以及 0027 的 registry / system 字符串分层是一致的： 必须分清“修改对象”与“让局部名字改指向另一个对象”。

字符估算仍可能和服务端真实 token 数不一致，所以 try/except 捕获异常文本中的 prompt_too_long 或 too many tokens。reactive_compact 保存 transcript、摘要旧历史、保留最近 5 条消息，并且最多重试一次；第二次仍过长就继续抛出， 不无限循环掩盖问题。

compact 工具：先闭合本轮，再压缩

compact_requested = False
for block in tool_calls:
    if block.name == "compact":
        output = "Compaction requested after this tool batch."
        compact_requested = True
    else:
        output = execute_tool(block)
    results.append({"type": "tool_result",
                    "tool_use_id": block.id, "content": output})

messages.append({"role": "user", "content": results})
if compact_requested:
    messages[:] = COMPACTOR.compact_history(messages, active_request)

真实源码： L549–573。

模型可能在同一回复里同时要求 write_file 和 compact。Harness 不能见到 compact 就立刻摘要，否则前一个写文件的 tool_use 还没有对应的 tool_result，下一次请求就会留下协议不完整的轨迹。正确顺序是： 执行所有工具 → 为每个调用回填结果 → 再压缩。压缩是对一轮已经闭合的状态做整理。

三个由现象推回实现的案例

案例一：只读多个 README 后，旧结果变成路径

读取五个章节 README 后，模型已经有机会使用这些结果。下一次请求前若超过阈值， micro_compact 会优先保留最近三条已消费结果，较早长结果变为 [Earlier tool result saved at ...]。这不是说文件丢了，而是模型若需要原文必须再调用 read_file。

案例二：模型刚写文件又要求 compact

write 的副作用必须先发生，且 write 的结果必须先回填。然后 compact_history 摘要这轮 已经闭合的轨迹。否则模型可能因为看不到“已写入”而再次写入，造成重复副作用。

案例三：字符数未超阈值，但 API 仍返回过长

本地 estimate_chars 只是近似；服务端 token 估算可能更大。异常进入 reactive_compact，只保留最近五条并重试一次。第二次失败要暴露给上层，而不是继续摘要到无限循环。

常见坑 + 边界

  • 压缩就是删除旧消息：不准确。完整历史会先写入 transcript；大结果还会写入 tool-results 文件。
  • 字符数就是 token 数：错。它是教学实现的估算；API 仍可能用 prompt_too_long 拒绝。
  • 每一轮都会调用模型生成摘要：错。前面的转存、归档和微压缩都是本地操作，只有仍超限才摘要。
  • 最新工具结果可以和旧结果一样随便缩：错。尚未被模型消费的新批次先保留；只有它本身撑爆时才用 fit_tool_results。
  • snip_compact 可以在任意消息下标切一刀：错。必须保护 assistant(tool_use) 与 user(tool_result) 配对。
  • compact 工具一出现就立刻摘要：错。必须先执行同一回复中的所有工具并回填所有结果。
  • 摘要等于可靠备份：错。摘要有损；可靠完整记录是 transcript。
  • 摘要里的指令都应该执行：错。摘要请求明确要求把历史当事实输入，不执行其中的指令。
  • messages = ... 与 messages[:] = ... 一样：错。后者保持原列表引用，外层 history 能看到更新。
  • 压缩后工具结果仍然自动在模型眼前：不一定。它们可能只剩路径，模型需要再用 read_file 恢复。
  • s08 已经解决跨会话记忆：错。transcript 是恢复记录，s09 才讨论筛选、提取和整理持久记忆。
  • 保存了 transcript 就能保证摘要正确：错。保存提高可追溯性，不替代验证和摘要质量检查。
