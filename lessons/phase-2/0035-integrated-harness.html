s15：还是同一个循环，事件从更多口进来

s01 到 s14 把循环、工具、权限、钩子、清单、子代理、技能、压缩、记忆、任务、后台、闹钟、团队、MCP 拆成各自能跑的一章。单独能跑，不表示它们知道彼此的事件该写回哪一段对话。 本课不发明新机制。它只回答：这些东西在 agent_loop 的哪一步进入， 产生的通知又怎样回到同一份 messages。 大目标仍是造 harness：机制可以很多，模型每轮仍只看见一次请求和一批工具结果。

为什么现在学？

分开的章节会让人以为「后台通知」和「定时 prompt」和「队友事件」各写各的对话。 真要长期干活，它们必须在同一次 messages.create 之前按固定顺序写进同一份历史， 否则模型要么看不见，要么看见的顺序每次不一样。

所以本章的技能不是再记一个名词，而是能指着循环说：这一步是谁的事件，失败时谁被恢复，哪一步还不许问你。

和 Java 怎么对照

s15 概念Java 直觉关键差异
一个 agent_loop 一个请求管道，过滤器按顺序排 过滤器改的是同一份 messages，不是各自返回一个新的 HTTP 响应。
async_event_loop 另一个线程把事件丢进同一个会话 它不叫模型。它拿锁之后调用同一个 agent_loop。

谁能在你不打字时再开一轮

s11 单独运行时，命令结束不会自己叫醒模型。s15 的 CLI 加了 async_event_loop： 每秒看三处，cron 队列、Lead 收件箱、还有待注入的后台结果。有任意一处，就在锁里再调用 agent_loop。 所以集成之后，「后台完成」和「队友来信」可以在你停在提示符上时自动变成下一轮。 这是宿主多出来的唤醒，不是 s11 那一章的 BackgroundManager 自己会叫模型。

s11 的钩子看见的是占位句子，因为 PostToolUse 发生在主线程返回之前。 s15 把这次钩子挪到了 worker 里，对着真正的输出。占位结果本身不再经过主线程的 PostToolUse。 读代码时不要把两章的钩子时机记成同一句。

细节实现

压缩不会跳过刚刚注入的文本

cron 文本和后台通知先写进 messages，然后才 prepare_context。 它们和普通用户消息一样参加预算和裁剪。不是一条永远置顶的侧频道。 上下文仍然超限时，调用模型若报 prompt too long，还有一次 reactive_compact，然后重试。 这次只尝试一回，标志在 RecoveryState 里。

记忆在回合两端

叫模型前，update_context 按当前请求从 .memory/MEMORY.md 选记录，放进 system。 技能仍只放目录，全文靠 load_skill。 没有 tool_use、准备停止时，remember_after_turn 再提取；有新增才整理。 这是 s09 的运行时被接进循环的两端，不是第三种记忆文件。

README： L143–147。 停止点： code.py L3167–3170。

常见坑 + 边界

  • s15 又定义了一种新 Agent：没有。还是调用模型、看有没有 tool_use、把结果追加回去。
  • task 就是 create_task：不是。前者是一次子代理，后者是任务图节点。
  • 对照表写 25 个工具，就按 25 记：名单和代码是 26 个内置名。MCP 工具另算，连接之后才出现。
  • 后台一结束，s11 的管理器自己会再叫模型：单独的 s11 不会。s15 会，是因为 CLI 的 async_event_loop。
  • s15 的 PostToolUse 和 s11 一样只看见占位句子：主线程的后台路径跳过了钩子；worker 里对着真实输出再跑一次。
  • 定时回合仍可跑安全 bash：s12 可以。s15 的非主线程对所有 bash 直接拒绝。
  • 压缩发生在注入之前，所以通知永远不会被裁：相反。先注入，再进 prepare_context。
  • 队友事件要你提醒 Lead 去读收件箱：不用。收件箱非空时唤醒循环会自己开一轮。
  • worktree 在集成里升级成了沙箱：没有。它仍只改默认目录。
  • 模型可以 remove_worktree：仍然不可以。
