为什么现在学？

0019 的伪代码里，response、tool_call、工具结果看起来很干净； s01 会让你看到它们在真实程序中的形状：SDK 返回对象，内容里混着文本块和工具块， 工具结果还必须带回原来的调用 ID。这个接口边界正是「模型做决定、Harness 负责执行」 的落点。只有把它跑过一次，后面的多工具、权限和 hooks 才不会变成名词堆。

系统讲解

1. 先看真实的消息往返

一次工具往返至少有四个动作。把它和 0019 的「想 → 做 → 看」对齐：

  1. 用户消息进入 messages；这是初始轨迹。
  2. Harness 把消息、系统提示和 TOOLS 一起交给模型；模型决定是否使用工具。
  3. 如果出现 tool_use，Harness 读取参数并执行 bash。
  4. Harness 用相同的调用 ID 生成 tool_result，追加回 messages，再请求模型。
messages = [
  {"role": "user", "content": "当前目录有哪些 Python 文件？"},
  {"role": "assistant", "content": [
    {"type": "tool_use", "id": "call_1",
     "name": "bash", "input": {"command": "..."}}
  ]},
  {"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "call_1",
     "content": "a.py\nb.py"}
  ]}
]

这里第二个 role: user 不是又来了一个人类问题，而是 API 消息协议中 「工具结果由用户侧 / 外部环境送回」的承载位置。关键不是背角色名字，而是确认： tool_result.tool_use_id 必须对应此前的 tool_use.id。

North README 将这件事拆成第 1–5 步： L42–80。

2. 工具不是 Python 函数，是给模型看的契约

tool schema 是结构化说明书。它告诉模型「有一个叫 bash 的工具，需要一个字符串参数 command」； 它不执行命令，也不等于 Python 的 run_bash 函数。 真正的连接在后面由 handler 完成。 

TOOLS = [{
    "name": "bash",
    "description": "Run a shell command.",
    "input_schema": {
        "type": "object",
        "properties": {"command": {"type": "string"}},
        "required": ["command"],
    },
}]

可以把它和 Java 对照成两半：schema 像接口文档和参数 DTO 的合体； run_bash(command) 才像实现类中的方法。模型只能依据 schema 发出调用， 不会因为你在本地定义了一个同名函数就自动执行它。

这是本课第一次把「工具描述」从概念变成 API 输入；原代码见 L59–67， 执行器见 L71–83。

3. 两个停止信号，决定循环是否再转一圈

stop_reason 仍是 Message 对象上的字段：模型结束本轮生成时携带的原因。 当前 s01 不读它。循环改看 content 里有没有 tool_use 块。有 = 还要 Harness 执行工具；没有 = 已经给出文本答案。 它不是 HTTP 状态码，也不是工具执行成功与否。 

messages.append({"role": "assistant", "content": response.content})

tool_calls = [
    block for block in response.content if block.type == "tool_use"
]
if not tool_calls:
    return

# 有 tool_use 才会走到这里：执行工具并回填结果

注意顺序：先把 assistant 回复追加进轨迹，再判断是否停止。 如果有工具调用，下一条消息才是工具结果；如果没有，最后一条 assistant 文本就是答案。 这正是 0019 的「无 tool call 就停」在真实 SDK 上的落地。

真实判断在 code.py L87–102； README 的最小函数在 README L90–114。

4. Harness 执行命令，再把观察送回去

run_bash 是 s01 的执行器。它用 subprocess.run 启动操作系统命令，capture_output=True 把标准输出和错误输出收回来，text=True 让结果以字符串处理， timeout=120 防止命令无限等待。这几个参数是首次在本课组合出现， 不是装饰性的写法。 

r = subprocess.run(
    command,
    shell=True,
    cwd=os.getcwd(),
    capture_output=True,
    text=True,
    timeout=120,
)
out = (r.stdout + r.stderr).strip()

前面的 dangerous 列表只拦截少数字符串，不能把 s01 当成完整权限系统； README 也明确说真正的权限系统留给 s03。这里的教学重点是数据流： block.input["command"] → 执行器 → output → tool_result。

subprocess.run 的完整实现与边界在 code.py L71–83； Python 官方参数说明在 subprocess.run。

5. Windows 边界：工具叫 Bash，不代表本机一定运行 Bash

你当前是 Windows。代码写的是 shell=True，这会使用当前 Python 进程所采用的系统 shell；它不自动安装或切换成 Linux Bash。 因此「工具 schema 的名字是 bash」与「命令实际由哪个 shell 解释」 是两件事。若模型给出 ls、cat、find 等 Unix 命令， 本机可能失败；这属于 0020 的执行环境层，不要先怪模型。

第一次真实运行的安全做法
  1. 不要让 s01 直接修改重要项目；在可丢弃目录或副本里启动。
  2. 先问一个只读、跨平台倾向的任务，例如： Run python -c "print('s01 works')"。
  3. 看到工具命令、工具输出、最终文本各出现一次后，再尝试列文件。
  4. 若命令语法不兼容，记录为环境问题；不要把危险命令加入白名单来「硬跑」。

SYSTEM：系统提示，每次请求都会作为静态前缀发给模型（0019 的静态前缀）。 os.getcwd() 是启动脚本时的当前工作目录，所以 agent「以为自己在哪」取决于你在哪个目录敲 python s01_agent_loop\code.py。 「Act, don't explain」是在催它调工具，不要只空谈。

E. 执行器 run_bash（L71–83）

def run_bash(command: str) -> str:
    dangerous = ["rm -rf /", "sudo", "shutdown", "reboot", "> /dev/"]
    if any(d in command for d in dangerous):
        return "Error: Dangerous command blocked"
    try:
        r = subprocess.run(command, shell=True, cwd=os.getcwd(),
                           capture_output=True, text=True, timeout=120)
        out = (r.stdout + r.stderr).strip()
        return out[:50000] if out else "(no output)"
    except subprocess.TimeoutExpired:
        return "Error: Timeout (120s)"
    except (FileNotFoundError, OSError) as e:
        return f"Error: {e}"

按执行顺序：

  1. dangerous：子串黑名单。any(d in command for d in dangerous) 表示命令文本里出现任一段就拦截，返回错误字符串，不抛异常。 这不是权限系统：改几个字母就能绕过；s03 才做边界。
  2. subprocess.run 不在本文件里定义。 L33 import subprocess 之后调用的是 Python 标准库函数，官方签名见 subprocess.run。 本文件定义的是外套 run_bash（L71）。0014 已讲「起子进程并等结束」； Java 接近 ProcessBuilder.start() 再 waitFor()。 返回值 r 是 CompletedProcess（有 stdout / stderr / returncode）。 s01 传入的关键字参数：
实参对应官方参数这里干什么
command位置参数 argsshell=True 时是一整串命令字符串
shell=Trueshell交给本机 shell 解析，Windows 通常是 cmd
cwd=os.getcwd()cwd子进程工作目录 = 启动脚本时的当前目录
capture_output=Truecapture_outputstdout/stderr 进返回对象，不直接印终端
text=Truetext输出当 str，不当 bytes
timeout=120timeout最多等 120 秒，超时抛 TimeoutExpired
  1. timeout=120 在 Windows 上的真实例子：单独的 date 会等人输入新日期， stdin 又被 divert 走了，就会在这里等到超时，然后走 TimeoutExpired， 返回 Error: Timeout (120s)。这是观察，不是 Python 死锁；不想等就 Ctrl+C。
  2. 把 stdout 和 stderr 拼成一条字符串再 strip。模型看不到「这是错误流」的标记， 只看到一段文本。空输出改成 (no output)，避免喂一个空白回去。
  3. out[:50000]：截断超长输出，避免一次把上下文撑爆。s01 没有 compact（s08）。
  4. FileNotFoundError / OSError：例如 shell 本身起不来。 注意：命令跑失败、exit code 非 0，subprocess.run 默认不抛， 只是 stderr 里有字。所以「ls 不是内部或外部命令」会作为观察喂回模型，而不是把循环炸死。

L71–83。 参数含义： subprocess.run。

F. 核心循环 agent_loop（L87–117）

参数 messages 是可变列表，函数里 append 会改调用方的 history（和 Java 把 List 引用传进去一样）。

每一圈固定四步。

1. 调模型（L89–92）。 client.messages.create 是同步请求：发 model、system、messages、tools、 max_tokens=8000，等到整段回复。 没有流式；终端会在这里停几秒，属于正常等网络。

2. 先把 assistant 整段 content 追加进轨迹（L95）。 response.content 是 content block 列表，可能同时有说明文字和 tool_use。必须先存，下一轮模型才能看见「我刚才要过什么」。

3. 筛 tool_use 块（L98–102）。 列表空就 return：正常完成。 常见伴随的 stop_reason 是 end_turn（说完了），但脚本不读这个字段。 此时 history 的最后一项就是带文本块的 assistant 消息。

4. 否则执行每一个 tool_use 块（L104–117）。 

tool_calls = [
    block for block in response.content if block.type == "tool_use"
]
if not tool_calls:
    return

results = []
for block in tool_calls:
    print(f"\033[33m$ {block.input['command']}\033[0m")
    output = run_bash(block.input["command"])
    print(output[:200])
    results.append({
        "type": "tool_result",
        "tool_use_id": block.id,
        "content": output,
    })
messages.append({"role": "user", "content": results})

先筛再执行：text 块不进 tool_calls，只执行工具块。 一轮可以有多个 tool_use；s01 按出现顺序串行跑。

block.input["command"]：schema 里那个参数。SDK 把 JSON 对象做成了可下标的 input。

\033[33m … \033[0m：ANSI 转义，把那行命令打成黄色。 \033 是 ESC。36m 在入口处把提示符打成青色。 不是密码，也不是给模型看的；只影响你的终端。Windows Terminal / 新版 PowerShell 能显示。

tool_use_id: block.id：配对键。模型下一轮靠它知道「哪一次调用」对应这段输出。 漏掉 ID，Messages API 会拒收或对不齐。

结果以 role: "user" 追加——这是 Messages 协议的规定：工具观察从「用户侧」送回， 不是又来了一个人类。然后 while True 回到第 1 步，带着更长的轨迹再调模型。

s01 没有 max_turns。模型若一直要工具，会一直转，直到你 Ctrl+C。 0019 讲过安全带；本文件故意没写。

max_turns 不是 client.messages.create 的参数。 API 认的是 max_tokens（本轮回复最长多少）。轮数上限是你在 while 上自己数的。

max_turns harness 循环计数 整个任务最多调几次模型 无，while True

G. 入口：外层 REPL（L121–142）

REPL = Read-Eval-Print Loop（读 → 执行 → 打印 → 再读）。 外层 s01 >> 就是 REPL：跟人对话。内层 agent_loop 才是跟模型和工具转圈。 两个都是 while True，职责不同。

字母意思s01 外层
Read读你敲的一行query = input("s01 >> ")
Eval拿去跑agent_loop(history)
Print把结果印出来L137–141 打印 text 块
Loop再回到 Read外层 while True

Python 自带的 >>> 也是 REPL。Java 没有同名内置，接近控制台里反复读一行再处理。 q / 空回车 / Ctrl+C 结束的是这个 REPL，不是 Messages API。

if __name__ == "__main__"：只有直接 python ...\code.py 才跑下面； 被 import 时不自动开对话。0004 已过关。 

history = []
while True:
    query = input("s01 >> ")
    if query.strip().lower() in ("q", "exit", ""):
        break
    history.append({"role": "user", "content": query})
    agent_loop(history)
    response_content = history[-1]["content"]
    if isinstance(response_content, list):
        for block in response_content:
            if getattr(block, "type", None) == "text":
                print(block.text)
    print()

一次回车 = 往 history 追加一条用户消息，再调用一次 agent_loop。 同一会话里 history 不清空，所以上一轮的工具结果下一问还在——这是轨迹，不是 bug。

input() 遇到 Ctrl+Z（Windows EOF）或 Ctrl+C，分别是 EOFError / KeyboardInterrupt，break 退出。 q、exit、空回车也会退出。空回车不是「再问一次」。

L137–141 在内层已经 return 之后执行。 agent_loop 停下来时，最后一次 append 一定是 assistant 的 response.content（L95），所以 history[-1] 是最后一条 assistant。 [-1] 表示列表最后一项。

  1. history[-1]["content"]：一般是 SDK 的 content block 对象列表，不是普通字符串。
  2. isinstance(..., list)：确认是块列表。若哪次变成纯字符串，就跳过，避免把每个字符当一块。
  3. getattr(block, "type", None) == "text"：只打印文本块。 SDK 块用属性 .type / .text，不是 dict 的 ["type"]。 工具块已经在循环里用黄字打过命令，这里不再倒 JSON。
  4. 末尾单独 print()：空一行，和下一次 s01 >> 分开。

对照：问「2 的三次方」时循环里没有黄字，答案就是这里打出来的； 调了工具之后，黄字在循环里，模型的总结仍然走这段。

常见坑 + 边界

  • 把 schema 当 handler：schema 只告诉模型怎么调用； run_bash 才执行。
  • 只追加 assistant，不追加 tool_result：下一轮看不到观察， 轨迹断了；必须把结果带上对应 tool_use_id。
  • 把 tool_use 当成功：它只表示模型要求工具； 命令可能超时、报错或被拦截，工具输出才是观察。
  • 把 stop_reason 当 HTTP 状态码：它描述模型本轮为何停， 与 shell 命令的退出码是两条不同链路。
  • 把 s01 当生产权限系统：少数字符串拦截不是完整安全边界； 权限是 s03 的课题。
  • 在 Windows 上看到 ls 报错就换模型： 先检查 shell、工作目录和命令语法，这是执行环境层。
  • 看到最终文本就算完成：本课的完成定义还包括工具确实被执行、 结果确实回填、循环确实按结果结束。
  • 两层 while 当成一个：外层是 REPL；内层才是 agent loop。空回车退出的是外层。
  • Windows 上 date / ls：交互命令会等到 120s 超时；Unix 命令可能根本不是内部命令。先查执行环境。
  • 自定义 Base URL 却 401：先看有没有残留 ANTHROPIC_AUTH_TOKEN；脚本已在 L50–51 尝试清掉。
  • 以为 subprocess.run 写在本文件里：定义在标准库；本文件只定义 run_bash 再调用它。
  • 把 max_turns 当成 API 参数：API 字段是 max_tokens。s01 没有轮数上限。
  • REPL = agent loop：REPL 是 s01 >> 对人；agent loop 对模型和工具。
