为什么现在学？

s02 的文件工具有 safe_path，bash 几乎没有门。 模型说「清理一下项目」，可能给出 rm -rf /。 安全不能靠「模型应该不会」——要靠执行前的代码。

这就是阶段 1 的约束落到代码：限定能做什么，不是把下一步写死。 模型仍决定调哪个工具；Harness 决定这次准不准跑。

README「安全不能靠信任模型」 L12–16。 书：生产 Harness 的约束 第01章 L273、 伪代码 constrain L288。 0018 已过关这个词。

和 Java 怎么对照

s03 概念Java 直觉关键差异
闸门 1 硬拒绝 黑名单 / 安全过滤器直接 403 这里是命令字符串的子串匹配，不是解析过的 AST，容易绕过。
闸门 2 规则表 一串 Predicate；命中则进入审批 规则写在 Python 字典 + lambda 里，不是注解。
闸门 3 input() 同步阻塞等操作员点批准 卡在 agent loop 中间；模型那头的 HTTP 已经结束，等的是你。
fail-closed 安全默认拒绝；未授权 ≠ 放行 空回车走 deny，不是走 allow。
Permission denied. 进轨迹 过滤器拦了仍给调用方一个错误体 必须带 tool_use_id 回填，否则下一轮 Messages 对不齐。
s02 safe_path vs s03 闸门 2 硬围栏 vs 审批后放行 s03 你若回答 y，文件工具可以写到工作区外。不是同一套锁。

系统讲解

1. 问题：工具在，门不在

s02 能读能写能跑 shell。文件路径逃逸被 safe_path 直接打回错误字符串； bash 只在 run_bash 里用一小段危险子串挡一下，挡不住变体，也没有「问人」。

s03 的解法不是再给每个 handler 复制一份 if：把判断抽到执行前，所有工具走同一条管线。

README 方案 L20–24。 图： permission-overview.svg。

2. 三道闸门，顺序固定

顺序闸门问什么命中后
1 硬拒绝 DENY_LIST 这条 bash 命令里有没有死命令子串？ 不执行、不问你，直接拒绝
2 规则 PERMISSION_RULES 这个工具 + 这些参数，是否「需要人看一眼」？ 不直接执行，交给闸门 3
3 用户审批 ask_user 你允不允许这一次？ allow → 执行；deny → 不执行

三道都没命中 → 直接执行。工作区内写一个 test.txt、用 glob 列文件，通常走这条路。

顺序不能倒：硬拒绝优先。若先问人，rm -rf / 就会变成「你手滑按了 y 就跑」。

README 表 L28–34； 管线图 permission-pipeline.svg。

3. 一次调用的四种结局

NOTES 要求易混点写满分支。对同一次 tool_use：

案路径handler 跑不跑模型看到的观察
① 闸门 1 命中 bash 命令含 sudo 等 不跑 Permission denied.（终端另有红字原因）
② 闸门 2 命中，你否 空回车 / n / 乱按 不跑 Permission denied.
③ 闸门 2 命中，你允 输入 y 或 yes 跑 handler 的真实输出（可能写出工作区外）
④ 两道都没命中 工作区内写文件、普通 ls、glob 跑 handler 输出

①② 对模型来说观察字符串一样。区别在你的终端：① 先打红字原因，② 先打黄字问句。 循环都不会把 Python 异常抛给 API。

4. 和 s02 safe_path 不是同一把锁

这是本课最容易看错的一点。s02 文件工具：路径逃出工作区 → safe_path 抛错 → handler 捕获 → 观察是 Error: ...， 文件不会被写，也不问你。

s03 删掉了 safe_path。run_write / run_read / run_edit 只 resolve() 再读写。 逃出工作区改由闸门 2 判定「要问人」。你回 y，写就会发生。

s02s03
文件逃出工作区 硬拦，当错误观察 问你；y 则真写
bash 危险子串 在 run_bash 内部 return Error（已「进入」handler） 闸门 1，handler 根本不进
glob is_relative_to 过滤命中 handler 里仍保留这一段；规则表没有 glob

所以：不要说「s03 = s02 安全再加点确认」。文件围栏从「代码拒绝」变成了「人批准」。 教学意图是展示审批，不是把生产沙箱做得更严。

B. 闸门 1：DENY_LIST + check_deny_list（L145–152）

DENY_LIST = ["rm -rf /", "sudo", "shutdown", "reboot", "mkfs", "dd if=", "> /dev/sda"]

def check_deny_list(command: str) -> str | None:
    for pattern in DENY_LIST:
        if pattern in command:
            return f"Blocked: '{pattern}' is on the deny list"
    return None
行在干什么
L146 子串列表。比 s02 run_bash 里那五个多了 mkfs / dd if= / > /dev/sda。
L148 返回 str | None：命中给原因字符串，未命中 None。 联合类型见 0009。调用方用 if reason: 判断，因为非空字符串为真、 None 为假。
L149–151 pattern in command 是子串，不是正则，也不是按词切分。 sudo apt 会中；SUDO 大小写不同则不中； rm -rf /tmp 含有 rm -rf / 也会中。
L152 整表扫完没有 → None，交给闸门 2。

三种绕过（教学版故意简）：① PowerShell Remove-Item（不是 del 命令词）；② 插入空格或引号拆开闸门 1 的子串； ③ 文件工具的参数里写 sudo——闸门 1 只检查 bash。 闸门 2 已用正则把 rm / del 当命令词（大小写不敏感）；delimiter、echo del test.txt 故意不中。 README 自己写了：简单字符串匹配不是可靠安全机制。

L145–152； README L42。

C. 闸门 2：规则表 + 命令词 + lambda（L156–179）

DESTRUCTIVE_COMMAND_WORD = re.compile(
    r"(?i)(?:^|[;&|()\n])\s*(?:rm|del)(?=\s|$|[;&|()])"
)

def contains_destructive_command(command: str) -> bool:
    return bool(DESTRUCTIVE_COMMAND_WORD.search(command))

PERMISSION_RULES = [
    {"tools": ["read_file", "write_file", "edit_file"],
     "check": lambda args: not (WORKDIR / args.get("path", "")).resolve().is_relative_to(WORKDIR),
     "message": "Writing outside workspace"},
    {"tools": ["bash"],
     "check": lambda args: contains_destructive_command(args.get("command", "")) or
     any(kw in args.get("command", "") for kw in ["rm ", "> /etc/", "chmod 777"]),
     "message": "Potentially destructive command"},
]

每条规则三块：tools 这张规则管哪些名字； check 是谓词（参数映射 → 是否命中）； message 给人和闸门 3 看的原因。

lambda args: ...：匿名函数，0004 / 0005 见过。 这里把它存进字典，和存 run_read 进 TOOL_HANDLERS 是同一件事（0012 函数对象）。 调用是 rule["check"](args)，括号在取出来之后。

DESTRUCTIVE_COMMAND_WORD：正则，(?i) 忽略大小写； 只在命令开头或 ;&|() 之后认 rm / del 这个词。 所以 del test.txt 会问，delimiter 和 echo del test.txt 不会。这是 0015 的正则，本课当规则用，不展开写引擎。

规则何时 check 为真注意
文件三条 (WORKDIR / path).resolve() 不在工作区下。 args.get("path", "")：没有 path 就当成空串，接到 WORKDIR 本身，is_relative_to 为真，不问。 message 写的是 Writing，但 read_file 逃出时也会问。 文案不准，行为仍是「出界就要问」。
bash contains_destructive_command 为真，或命令里出现 rm （有空格）、> /etc/、chmod 777 rm file、del test.txt、DEL test.txt 会问 （上游为此加了命令词正则）。 rmfile、model、delimiter、 echo del test.txt 不问。

check_rules：工具名必须在 rule["tools"] 里，且 check(args) 为真，才返回 message。第一条命中就返回，不合并多条原因。 glob 不在任何 tools 列表里，闸门 2 对它永远 None（handler 内部仍过滤工作区外的匹配）。

L156–179。 is_relative_to 已在 0022 过关。

D. 闸门 3：ask_user（L183–187）

def ask_user(tool_name: str, args: dict, reason: str) -> str:
    print(f"\n\033[33m[permission] {reason}\033[0m")
    print(f"   Tool: {tool_name}({args})")
    choice = input("   Allow? [y/N] ").strip().lower()
    return "allow" if choice in ("y", "yes") else "deny"
行在干什么
L184–185 黄字原因 + 工具名和参数。这是给你看的，还没执行。
L186 input() 卡住整个 agent_loop。 上一轮 messages.create 已经返回；现在等的是键盘，不是模型。
L187 只有 y / yes（忽略大小写、去空白）→ "allow"。空串、n、no、乱按 → "deny"。这就是 fail-closed。

返回值是普通字符串 "allow" / "deny"，不是布尔。 下面 check_permission 再翻译成 True / False。

L183–187。

E. 串联：check_permission（L191–202）

def check_permission(block) -> bool:
    if block.name == "bash":
        reason = check_deny_list(block.input.get("command", ""))
        if reason:
            print(f"\n\033[31m[blocked] {reason}\033[0m")
            return False
    reason = check_rules(block.name, block.input)
    if reason:
        decision = ask_user(block.name, block.input, reason)
        if decision == "deny":
            return False
    return True
  1. 参数是整个 tool_use 块，用 block.name 和 block.input（0022 的块字段）。
  2. 闸门 1 用 if block.name == "bash" 包住：文件工具从不查 DENY_LIST。bash 没带 command 时 .get(..., "") 当成空命令，扫表不中。
  3. 闸门 1 命中：红字打印原因，return False，不会走到 ask_user。
  4. 闸门 2 命中才问人。你 deny → False；你 allow → 函数不提前返回，落到最后的 True。
  5. 两道都 None → 直接 True。

返回 False 的含义是「不要跑 handler」，不是「不要给模型观察」。 观察在循环里另写。

L191–202。 README 伪代码 L101–128。

观察重点（README「试一下」+ Windows 对照）：

  1. 工作区内创建可丢弃文件： Create a file called test.txt in the current directory —— 应直接过（结局 ④），黄字问句不应出现。
  2. 删除该文件。若模型走 bash + 带空格的 rm ，应出现闸门 2 问句 （结局 ② 或 ③，取决于你）。Windows 上 del test.txt 同样应问（闸门 2 命令词）。
  3. 只读：What files are in the current directory? —— glob 或普通列目录，应直接过。
  4. 写工作区外：Try to write a file to /etc/something —— 应问「Writing outside workspace」。这里请答 n，不要真写。
  5. 闸门 1：让它执行带 sudo 的命令——应红字 Blocked，没有 Allow?。

每次拒绝后，看模型下一轮是否还在说话：它已经收到 Permission denied.，可能会改计划。这就是「观察进轨迹」。

常见坑 + 边界

  • 权限 = 提示词里写了 destructive 要审批：错。拦的是 check_permission，不是 SYSTEM。
  • 拒绝了就不要 tool_result：错。必须回填，否则 ID 对不齐。
  • s03 比 s02 更安全：文件路径上不一定。s02 硬围栏；s03 你点 y 就能写出工作区。
  • 闸门 1 = 解析过的命令黑名单：只是 in 子串。变体、大小写、Windows Remove-Item 仍能漏。闸门 2 的 del 已按命令词匹配，不再当「Windows 必漏」。
  • 空回车 = 允许：错。[y/N] 默认 deny。
  • 生产 CC 也是这三道闸：生产管线是四态 + 多阶段 + 八个规则来源。教学版刻意砍过。本章 README 已不再附源码对照，过关不要求背生产细节。
  • Permission denied. 是 HTTP 401：它只是给模型的观察字符串。
