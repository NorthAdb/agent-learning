本课新名词 × 原文

名词一句话出处
hook（钩子） 预先挂在某个事件时机上的扩展入口；事件发生时，Harness 调用它，不必把扩展代码写进循环正文。 North 格言 README L6–8； 方案 L38–52。
event（事件） Harness 规定的一个时机名称，如 PreToolUse；它描述“什么时候触发”，不是具体功能。 四个事件表 README L46–52； 注册表 code.py L128。
callback（回调） 先作为值保存、以后由触发器调用的函数；本课的 permission_hook 等都是 callback。 register_hook(event, callback) code.py L130–131； 注册具体函数 L203–208。
HOOKS（hook 注册表） 字典：事件名 → 回调列表；它是“哪些扩展要在何时运行”的表，不是执行结果表。 code.py L128； README 工作原理 README L56–80。
register_hook 把一个 callback 用 append 加到某个事件的列表末尾；注册时传函数本身，不加括号。 code.py L130–131。
trigger_hooks 取出某个事件的回调列表，按注册顺序依次调用；遇到第一个非 None 返回值就停止继续调用。 code.py L133–137； README L64–80。
*args（可变位置参数） 让触发器接收任意数量的位置参数，并把这组参数再逐个转交给 callback；所以四种事件可携带不同数据。 trigger_hooks(event, *args) 与 callback(*args) code.py L133–134。 本书未用这个词，来自 Python 函数参数语法。
短路（short-circuit） 回调链收到第一个非 None 结果后立即停止；后注册的同事件 callback 不再运行。 if result is not None: return result code.py L135–137。 这里是本课对控制流的称呼。

为什么现在学？

s03 的循环已经承担了太多角色：拿回复、筛 tool call、查权限、执行 handler、 组装观察、决定退出。现在如果再加“每次调用写审计日志”“执行后检查输出大小” “退出时打印统计”，最直接的写法是继续往 agent_loop 里塞 if 和函数调用。 

def agent_loop(messages):
    while True:
        # ... 调模型 ...
        for block in response.content:
            log_to_file(block)          # 新需求
            check_permission(block)     # s03 需求
            notify_somewhere(block)     # 又一个需求
            output = execute(block)
            check_output(output)        # 执行后需求

这段代码能跑，但循环的稳定骨架和每个项目的扩展策略混在一起。 下一次改日志规则，你必须重新打开并修改循环；下一次加新工具，也更容易碰到循环。 hook 的边界是：循环只保留“在这个时机触发扩展”的一行， 具体扩展由注册表管理。

问题示例 README L12–34； 解法概览 L38–52。

和 Java 怎么对照

s04 概念Java 直觉关键差异
hook / callback 接口实现、监听器或拦截器方法 本课直接把 Python 函数放进列表；没有接口类、依赖注入容器或注解扫描。
HOOKS Map<String, List<Callback>> 键是普通字符串，不是 Java enum；拼错事件名时，Python 运行到查表才出错。
register_hook 向某个事件注册 listener 传 log_hook 是保存方法；传 log_hook() 是现在立刻执行，通常会得到 None，不是注册 callback。
trigger_hooks 发布事件、依次调用 listener 本课自己实现发布循环，并且用第一个非 None 返回值短路；没有消息总线。
None 常见地类似“无结果”的 null 这里是 Python 的空值对象。触发器判断的是“是否为 None”，不是只判断布尔真假； callback 返回字符串就是控制信号。
PreToolUse 调用 service 前的过滤器 / 授权拦截器 s04 中返回原因字符串就不进 handler，但循环仍要回填 tool_result 给模型。
PostToolUse 调用完成后的 listener 当前 trigger_hooks 的返回值没有被调用方使用，所以它只能观察或打印，不能替换 output。
Stop 请求结束前的拦截器 返回非空继续；本课把返回文本作为新的 user 观察追加进同一份 messages。

系统讲解

1. 先分清三件事：事件、表、函数

这三个词不能混成“hook 就是一行魔法”：

东西问题s04 的例子
event 什么时候发生？ "PreToolUse"、"Stop"
callback 发生时要调用哪个函数？ permission_hook、log_hook
HOOKS 这个事件要调用哪些函数，顺序是什么？ {"PreToolUse": [permission_hook, log_hook]}
trigger 现在把这组函数真正调用起来 trigger_hooks("PreToolUse", block)

HOOKS 是配置 / 注册状态；trigger_hooks 才是执行动作。 就像 0022 的 TOOL_HANDLERS 是“工具名 → handler”的表， 这里是“事件名 → callback 列表”的表。两张表都不会因为存在就自动执行。

2. 函数对象：注册时不加括号

0012 已经见过把函数放进字典。这里把同样的规则用于列表： 

def log_hook(block):
    print(f"[HOOK] {block.name}")

HOOKS["PreToolUse"].append(log_hook)   # 保存函数本身
HOOKS["PreToolUse"].append(log_hook())  # 错：现在执行，保存返回值

log_hook 是“以后可以调用的函数对象”；log_hook() 是“现在就调用， 并把返回值拿回来”。本课的注册表需要前者，因为事件还没有发生， block 也还没有准备好。

s04 用 register_hook 把这一步包起来： 

def register_hook(event: str, callback):
    HOOKS[event].append(callback)

传入 register_hook("PreToolUse", log_hook) 后，表里多出一个函数； 直到未来执行 trigger_hooks("PreToolUse", block)，它才会收到 block。这就是“延后调用”。

代码 L128–131； North README 的注册表说明 L56–72。

3. trigger_hooks：取表、传参、按顺序执行

def trigger_hooks(event: str, *args):
    for callback in HOOKS[event]:
        result = callback(*args)
        if result is not None:
            return result
    return None
  1. HOOKS[event]：按事件名取出 callback 列表。例如 event == "PreToolUse" 时，得到 [permission_hook, log_hook]。
  2. for callback in ...：按照注册顺序逐个取函数。先注册的先运行。
  3. *args（定义处）：把 event 后面多出来的位置参数收进一个元组。 元组是一组按位置保存的值。详见下面「打包 / 解包」。
  4. callback(*args)（调用处）：把元组再拆开传给 callback。 详见下面对照表。
  5. callback 返回非 None 时，立刻 return result； 后面的 callback 不再运行。所有 callback 都返回 None，触发器最后返回 None。

3′. * 出现两次：先打包，再解包

同一行代码里有两个带星号的 args，但方向相反。 可以记成：触发器先把本次事件的参数收进包，再把同一包 拆给每个 callback。 

def trigger_hooks(event: str, *args):   # ① 定义处：打包
    for callback in HOOKS[event]:
        result = callback(*args)        # ② 调用处：解包
        ...
位置写法方向在干什么
函数定义 def trigger_hooks(event, *args) 外面 → 里面 把调用时写在 event 后面的额外位置参数，收成一个元组 args。多传几个都行。
函数调用 callback(*args) 里面 → 外面 把元组 args 拆开，按位置传给 callback。 不是把「整个元组」当成一个参数塞进去。

为什么需要这一套？因为四个事件多出来的参数个数不一样， 但希望共用同一个触发器：

调用打包后的 args解包后实际调用
trigger_hooks("UserPromptSubmit", query) (query,) context_inject_hook(query)
trigger_hooks("PreToolUse", block) (block,) permission_hook(block) 等
trigger_hooks("PostToolUse", block, output) (block, output) large_output_hook(block, output)
trigger_hooks("Stop", messages) (messages,) summary_hook(messages)

注意 (block,) 里的逗号：单元素元组必须写逗号，否则 (block) 只是加了括号的表达式，不是元组。

若不用 *args，触发器就得为参数个数写死签名，例如只能多传一个： 

# 假想：写死「只能多传一个」——PostToolUse 的 output 塞不进去
def trigger_hooks(event, arg1):
    callback(arg1)

# 假想：写死「必须多传两个」——PreToolUse 的 permission_hook(block) 会多收一个参数而报错
def trigger_hooks(event, arg1, arg2):
    callback(arg1, arg2)

有了打包 / 解包：触发器只写一次；多传几个、传什么，由调用点决定； 每个 callback 自己声明要几个参数，触发器原样转交，不关心内容。 像快递中转站：箱子里有 1 件还是 2 件它不管，只负责原封不动交给收件人。

两个易混点：

  • callback(*args) ≠ callback(args)。 前者拆开传位置参数；后者把整个元组当成一个参数， permission_hook 会收到「元组」而不是 block。
  • 这里的 * 不是乘法，也不是「并行启动所有 callback」。 它只做参数的收发。

触发器真实代码 L133–138； Pre 调用 L236； Post 调用 L245。 本课对 *args 的语法说明是 Python 补充，North README 只展示了调用效果。 官方： Arbitrary Argument Lists、 Unpacking Argument Lists。

4. 返回值协议：None 不是“失败”

hook 返回值要先分成两层看：

callback 返回trigger_hooks 怎么做通常表达什么
None 继续调用下一个 callback 本 callback 没有阻止意见；例如记录完日志后放行
非 None，如 "Permission denied" 立刻返回，不调用后面的 callback 本 callback 给出了控制信号或原因

“返回非 None”是触发器层的协议；“这个返回值是否改变主循环” 还由调用位置决定：

调用点拿到非 None 后主循环效果
UserPromptSubmit 当前脚本忽略返回值 原始 query 仍被 append，hook 只能打印
PreToolUse 保存到 blocked 并判断 回填拒绝观察，跳过 handler
PostToolUse 当前脚本忽略返回值 输出照原样回填，hook 只能观察 / 提醒
Stop 保存到 force 并判断 把文本追加为 user 消息，继续下一轮

这也解释了一个容易误读的地方：README 说“返回值不为 None 时 hook 说停”，但并不表示四个事件都拥有同样的业务效果。 trigger_hooks 只负责传回信号；调用者决定把信号当成拒绝、继续、 还是完全忽略。

5. 四个事件放在 Agent cycle 的哪里？

s04 的四个事件不是四个平行 Agent，而是同一根循环上的四个插口：

事件发生时机传给 callback本课用途
UserPromptSubmit 用户输入提交后、进入模型前 query: str 打印工作目录；可作为将来输入校验 / 上下文注入的入口
PreToolUse handler 执行前 block 把 s03 权限检查和调用日志接在工具前
PostToolUse handler 返回 output 后 block, output 提醒超大输出；不改变当前 output
Stop 本轮没有 tool_use、循环准备退出时 messages 打印工具调用统计；非空返回可以阻止退出

事件表和触发位置 README L46–52、 L82–180。

6. 一个重要的事实：名字叫 inject，不代表真的注入

def context_inject_hook(query: str):
    print(f"\033[90m[HOOK] UserPromptSubmit: working in {WORKDIR}\033[0m")
    return None

这个函数名叫 context_inject_hook，但它的真实代码只打印工作目录， 没有修改 query，也没有向 history append 新消息。 而且入口这样调用： 

trigger_hooks("UserPromptSubmit", query)
history.append({"role": "user", "content": query})

返回值也没有被接住。因此当前版本准确的说法是： UserPromptSubmit 提供了“将来可以注入”的扩展点，本章示例只做日志。 不能把函数名当成行为证明；要看参数是否被修改、返回值是否被调用方使用。

hook 定义 code.py L192–195； REPL 调用 L260–264。

7. callback 的顺序是行为的一部分

s04 按以下顺序注册两个 PreToolUse callback： 

register_hook("PreToolUse", permission_hook)
register_hook("PreToolUse", log_hook)

所以正常工具调用的顺序是： permission_hook → log_hook → handler。 如果权限 hook 返回拒绝字符串，trigger_hooks 在第一步就短路， log_hook 不会执行，handler 也不会执行。 这和“每次调用都必然留下日志”不是一回事。

如果审计日志必须覆盖被拒绝的调用，可以把日志放在权限检查前， 或让权限 hook 自己记录；注册顺序不是排版细节，而是程序语义。 本课不改上游代码，只要求你能从真实顺序推出结果。

注册顺序 L203–208； 短路规则 L133–137。

8. Stop 是“退出前最后一问”，不是每轮都跑

Agent 收到模型回复后，先筛出 tool_calls。只有列表为空，才会触发 Stop： 

tool_calls = [
    block for block in response.content if block.type == "tool_use"
]
if not tool_calls:
    force = trigger_hooks("Stop", messages)
    if force:
        messages.append({"role": "user", "content": force})
        continue
    return

这里要分三案：

情况Stop hook结果
回复含 tool_use 不触发 先执行工具，把 tool_result 回填，再调模型
回复无 tool_use，所有 Stop callback 返回 None 触发但放行 return，本次 agent_loop 结束
回复无 tool_use，某个 Stop callback 返回字符串 触发并阻止退出 字符串进 messages，continue，模型再来一轮

因此 Stop hook 可以把“模型说完了”改成“还不准结束”。这已经是一个很小的 持续执行机制，但它仍然不是测试框架：除非 callback 自己检查文件或结果， 它不会凭空知道任务是否真的完成。

HOOKS = {

C. permission_hook：s03 逻辑换了位置，没换语义

s03 的 check_permission(block) 被改名 / 包装为 permission_hook(block)，内部仍是同一组边界： bash 先扫 DENY_LIST；危险命令或工作区外文件再询问； 不允许时返回原因字符串；没有问题时返回 None。 

def permission_hook(block):
    if block.name == "bash":
        # deny list / destructive command / ask user
        ...
    if block.name in ("read_file", "write_file", "edit_file"):
        # workspace boundary / ask user
        ...
    return None

最重要的变化不是 if 条件，而是谁调用它： 

# s03：循环知道权限函数的名字
if not check_permission(block):
    ...

# s04：循环只知道 PreToolUse 这个扩展点
blocked = trigger_hooks("PreToolUse", block)
if blocked:
    ...

以后再加审计、速率限制或参数检查，循环不需要知道每个函数的名字； 只要注册到正确事件即可。权限本身仍然是约束，不是模型提示词。

新 hook L145–175； 与 s03 的差异 README L188–196。

D. 另外四个 callback：观察不等于改变

D1. log_hook：工具执行前打印预览

def log_hook(block):
    args_preview = str(list(block.input.values())[:2])[:60]
    print(f"\033[90m[HOOK] {block.name}({args_preview})\033[0m")
    return None

block.input.values() 取参数字典的值； list(...) 把这些值变成列表；[:2] 只留前两个； 外层 [:60] 再把显示文本截到 60 个字符。 这是给人看的预览，不是发给模型的参数，也不是对工具输入做截断。 返回 None 让下一个 callback / handler 继续。

D2. large_output_hook：工具执行后提醒

def large_output_hook(block, output):
    if len(str(output)) > 100000:
        print(f"\033[33m[HOOK] Large output from {block.name}: "
              f"{len(str(output))} chars\033[0m")
    return None

它接收两个位置参数，所以只能在 PostToolUse 触发： block 说明哪个工具，output 是 handler 的返回值。 len(str(output)) 数的是字符串字符数；超过 100000 才打印提醒。 它没有返回一个新 output，调用方也没有接住返回值，因此不会截断结果、 不会重试工具，也不会阻止下一轮。

D3. context_inject_hook：当前只记录输入时机

def context_inject_hook(query: str):
    print(f"\033[90m[HOOK] UserPromptSubmit: working in {WORKDIR}\033[0m")
    return None

这个函数的参数是原始 query，但没有改它。它证明了 UserPromptSubmit 的时机，不证明“上下文已注入”。如果未来真的要注入， 需要同时设计数据通道，例如让调用方接住返回的新文本，或显式 append 一条 允许的消息；仅仅改函数名不会改变 messages。

D4. summary_hook：退出前统计轨迹里的 tool_result

def summary_hook(messages: list):
    tool_count = sum(
        1 for m in messages
        for b in (m.get("content")
                  if isinstance(m.get("content"), list) else [])
        if isinstance(b, dict) and b.get("type") == "tool_result"
    )
    print(f"\033[90m[HOOK] Stop: session used {tool_count} tool calls\033[0m")
    return None

它遍历已有的 messages，只统计 content 是列表、且列表项是 dict、 类型为 tool_result 的块。拒绝的工具调用也会在循环里回填 tool_result，所以这个数字表示“回填过多少工具结果”，不一定表示 “多少次 handler 成功执行”。这是统计口径，不能随便把它叫成成功调用数。

四个 callback L178–201。

E. 注册顺序：L203–208

register_hook("UserPromptSubmit", context_inject_hook)
register_hook("PreToolUse", permission_hook)
register_hook("PreToolUse", log_hook)
register_hook("PostToolUse", large_output_hook)
register_hook("Stop", summary_hook)

这里没有把一个 callback 注册到所有事件；每个 callback 的参数形状决定它应该挂在哪： permission_hook(block) 不能直接挂到需要 (block, output) 的 PostToolUse。 同一事件可以有多个 callback，列表顺序就是执行顺序。

F. 主循环：三处触发，核心形状没被扩展代码污染

F1. 退出前的 Stop：L221–233

if not tool_calls:
    force = trigger_hooks("Stop", messages)
    if force:
        messages.append({"role": "user", "content": force})
        continue
    return

summary_hook 会打印统计并返回 None，所以正常情况下落到 return。如果另一个 Stop callback 返回非空字符串，字符串会进同一份 messages，下一次 while 又会调模型。它没有重新进入 REPL， 也没有创建第二个 agent_loop。

F2. 工具前的 PreToolUse：L238–243

for block in tool_calls:
    blocked = trigger_hooks("PreToolUse", block)
    if blocked:
        results.append({
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": str(blocked),
        })
        continue
  1. 先触发权限 callback；没有拒绝时它返回 None，再轮到日志 callback。
  2. 如果得到非空拒绝字符串，追加带有相同 block.id 的 tool_result。
  3. continue 跳过当前 for 迭代，因此当前 block 的 handler 不会运行。
  4. 这个 continue 只跳过当前工具，不跳过同一轮后面的其他 tool_use。

注意这里调用方写的是 if blocked:，判断的是 Python 的真假。 触发器虽然按“非 None”短路，但 callback 应返回有内容的原因字符串； 返回空字符串 "" 会被触发器传回来，却在这里被当成假值，结果不会进入拒绝分支。 这是本教学脚本的接口约定：拒绝请返回非空消息。

F3. 工具后的 PostToolUse：L245–248

handler = TOOL_HANDLERS.get(block.name)
output = handler(**block.input) if handler else f"Unknown: {block.name}"

trigger_hooks("PostToolUse", block, output)
results.append({
    "type": "tool_result",
    "tool_use_id": block.id,
    "content": output,
})

handler 已经返回后才触发 PostToolUse。large_output_hook 此处只是检查并打印； 它的返回值没有赋给变量，原来的 output 照样放入结果。 以后若想让 post hook 能修改 output，就必须重新设计协议，例如让触发器返回新值， 再由循环明确写成 output = trigger_post_hooks(...)；当前 s04 没有这条通道。

Stop L221–233； Pre / Post L238–248。

G. 外层 REPL：UserPromptSubmit 在 agent_loop 外

query = input("\001\033[36m\002s04 >> \001\033[0m\002")
if query.strip().lower() in ("q", "exit", ""):
    break
trigger_hooks("UserPromptSubmit", query)
history.append({"role": "user", "content": query})
agent_loop(history)

外层 REPL 负责“读你的一行、送入本次 agent_loop、打印最后文本、再读下一行”； UserPromptSubmit 在这层触发，因为它描述的是用户提交输入， 不是模型每次调用前。它与 PreToolUse / PostToolUse / Stop 都挂在同一进程里， 但时机和参数不同。

入口 L251–271。

把一次调用完整走一遍

案例一：普通 read_file，所有前置 hook 放行

  1. 你输入 query，触发 UserPromptSubmit；它打印工作目录，返回 None，原 query 进入 history。
  2. 模型返回一个 tool_use，名字是 read_file。
  3. PreToolUse 先跑 permission_hook；工作区内路径没有命中规则，返回 None。
  4. 同一事件继续跑 log_hook，终端看到 [HOOK] read_file(...)。
  5. dispatch map 取出 run_read 并执行，得到 output。
  6. PostToolUse 跑 large_output_hook；普通小输出不打印提醒。
  7. 循环把 output 和原 block.id 组成 tool_result，追加到 messages，再调模型。

hook 没有替代 dispatch；它只包住执行前后。权限、日志、实际 handler、观察回填仍是四件不同的事。

案例二：危险 bash，PreToolUse 短路

  1. 模型给出 bash tool_use，例如命令包含 deny list 中的 sudo。
  2. permission_hook 打印阻止原因，返回 "Permission denied by deny list"。
  3. trigger_hooks 立即返回；同一事件后注册的 log_hook 不运行。
  4. 主循环把这个原因转成 tool_result，使用相同的 tool_use_id。
  5. continue 跳过 handler；模型下一轮会看到拒绝观察。

这说明“hook 能拦”与“hook 一定记录”不能同时默认成立；取决于 callback 顺序。 若想拒绝也审计，需要改变注册顺序或在权限 callback 中记录。

案例三：模型没有 tool_use，Stop 放行

  1. 模型回复只有 text，tool_calls 是空列表。
  2. 触发 summary_hook(messages)，统计已有 tool_result 并打印。
  3. summary 返回 None，force 为空。
  4. 主循环执行 return，把本轮最后的 text 交给外层 REPL 打印。

案例四：Stop callback 要求继续

这不是上游脚本已注册的 callback，而是为了读懂接口的最小假设： 

def require_check_hook(messages):
    if "CHECK_OK" not in str(messages):
        return "请继续运行检查命令，并把结果写进对话。"
    return None

如果把它注册到 Stop，模型即使本轮没有 tool_use，只要对话中没有 CHECK_OK，就会收到这条 user 消息并继续。这个 hook 不是验证命令本身； 它只根据现有 messages 做判断。真正的检查仍必须由 bash 等工具执行。 这正是 Harness 中“触发继续”和“实际验证”之间的区别。

位置s03s04结果
权限逻辑 check_permission(block) 写在循环调用点 permission_hook 注册到 PreToolUse 语义保留，依赖方向改变

常见坑 + 边界

  • 写了 hook 就会自动运行：错。必须先注册到对应事件， 还必须在循环 / REPL 的正确时机调用 trigger_hooks。
  • 注册写成 register_hook("PreToolUse", log_hook())： 错。括号会立刻执行；注册应传 log_hook 函数对象。
  • 四个事件都传同样的参数：错。UserPromptSubmit 收 query， Pre 收 block，Post 收 block + output，Stop 收 messages。
  • 所有 callback 都会执行：不一定。某个 callback 返回非 None 就短路；s04 的权限拒绝会跳过后面的 log hook。
  • 返回 False 和返回 None 完全一样： 在触发器层不一样——False is not None，会短路；但主循环的 if blocked 会把 False 当假值。因此控制 hook 应返回非空原因字符串。
  • PostToolUse 能自动改掉 output：错。当前调用方忽略 Post 的返回值； large_output_hook 只能提醒，原 output 仍回填。
  • context_inject_hook 已经把 WORKDIR 发给模型： 错。当前它只打印；query 没有被改写，返回值也没有被外层接住。
  • Stop 每次工具执行后都会跑：错。只有本轮没有 tool_use、循环准备退出时才触发。
  • hook 代替了 agent loop：错。模型请求、tool_use 筛选、 handler 执行、tool_result 配对和 while 仍由循环负责；hook 是插口。
  • hook 系统本身就是安全沙箱：错。它只是把检查接到某个时机； s04 仍继承教学版字符串黑名单、shell=True 等边界。
  • Stop 返回非空就一定安全地继续：错。它只是追加一条消息； 如果没有全局预算或其他出口，设计不当的 Stop hook 可能让循环持续很久。
  • 把权限移到 hook 后，拒绝就不用回填结果：错。位置变了， Messages 协议没变；仍须用原 tool_use_id 回填 tool_result。
