系统讲解

1. 三种名字

先澄清：下面例子里的 Bag / bag 不是关键字。 Bag 是作者给类起的名字（像「袋子」）；bag = Bag(...) 是该实例的变量名。 换成 Box / box 机制完全一样。要记的是属性名前缀规则，不是 bag 这个词。

Python 没有 Java 那种编译期 public / private。 属性默认可从类外读写；「别乱摸」靠命名约定告诉读代码的人，解释器多数时候不拦。 教材原话大意：大家都是成年人。

1.1 总表

写法作者意图类外 bag.xxx该不该当公开 API
self.token 公开字段 / 公开接口的一部分 正常读写 可以：稳定依赖它
self._cache 内部实现；请走公开方法 / property 语法允许读写（不报错） 不该：升级时可能改名或删掉
self.__secret 名称改写（mangle），主要防子类踩名 bag.__secret → AttributeError 仍非安全私有；真名是 _Bag__secret

1.2 公开名：token

无前缀下划线 = 「这是接口的一部分」。外面写 bag.token 是预期用法。 类作者若改掉或删掉它，就算破坏兼容——所以公开名要慎重。 

bag = Bag("sk-demo")
print(bag.token)      # 正常：公开 API
bag.token = "sk-new"  # 也允许（除非另有 property 拦住）

1.3 单下划线：_cache（最常见、最重要）

一个前导 _ = 门上贴条「内部通道」。 门没锁：bag._cache 能读能写，不会 AttributeError。 含义是：实现细节；外面应调用公开方法，不要把 _cache 写进自己的业务逻辑。

情况结果该怎么想
类里面用 self._cache正常作者自己的零件
类外面读 bag._cache语法成功能跑 ≠ 该当接口；很脆
模块级 _DISALLOWED_CHARS = re.compile(...)同约定内部正则；对外用 normalize_mcp_name(...)

North s19 正是模块级单下划线： _DISALLOWED_CHARS 是编译好的正则零件；公开入口是 normalize_mcp_name。 「内部正则，别当公开 API」= 别 from xxx import _DISALLOWED_CHARS 当自己的依赖。

和 0012 的 ToolRegistry._tools 同一约定：注册表内部的 dict，外面请用 register / dispatch。

1.4 双下划线：__secret（名称改写，少用）

类体里写 self.__secret 时，解释器改写存储名为 _类名__secret （本例类叫 Bag → 真名 _Bag__secret）。这叫 name mangling（名称改写）。

写法结果
bag.__secretAttributeError（按字面找不到这个属性）
bag._Bag__secret能读到（绕过改写后的真名）
子类里再写 self.__secret变成 _子类名__secret，不会盖住父类那份

为什么要改写？看父子各写一遍同名属性。

继承：Child(Parent) 表示 Child 是 Parent 的子类，会先跑父类初始化，再跑自己的。 问题是：子类作者可能不知道父类已经用了某个内部名，自己又写了同名 → 单下划线会盖住父类的值。 

class Parent:
    def __init__(self):
        self._cache = "父:_cache"
        self.__secret = "父:__secret"   # 存成 _Parent__secret

class Child(Parent):
    def __init__(self):
        super().__init__()              # 先让父类把格子建好
        self._cache = "子:_cache"       # 同一名字 → 盖住父的
        self.__secret = "子:__secret"   # 存成 _Child__secret → 父的还在

child = Child()
child._cache              # → "子:_cache"（父的没了）
child._Parent__secret     # → "父:__secret"（还在）
child._Child__secret      # → "子:__secret"
前缀子类写同名后一句话
_cache只剩子的；父的被覆盖同一格子抢着用
__secret父、子各一份（真名不同）自动加类名前缀，互不踩

所以双下划线不是「外面绝对读不到」（仍可用 _Parent__secret 读到）， 而是「继承树里别无意同名踩踏」。 日常库代码更常见单下划线 _x；双下划线少写，除非真在写会被大量继承的基类。 可跑对照：examples.py 例 1b。

1.5 别和「两边都是双下划线」搞混

样子是什么例子
前导一个 _ 约定内部 _cache、_tools、_DISALLOWED_CHARS
前导两个 __，后面没有再跟 __ 名称改写 __secret → _Bag__secret
两边都是 __...__（dunder） 语言/协议认的特殊名，不是「私有」 __init__、__name__、__slots__、__repr__

过关口诀：__name__（模块入口那套）和属性 __secret（改写）不是一类东西。 见 0012「哪些是 Python 的，哪些是你起的」。

2. __slots__：锁死「允许哪些属性名」

「三案」= 故意对照的三种情况，不是第三个 API。 先问一个问题：实例上能不能临时新加一个属性？

2.1 默认：实例像一个小字典（动态属性）

0012 已见：普通类的实例，格子可以随时加。 你在 __init__ 里只写了 self.name，外面仍可 obj.extra = 1——解释器会新建格子。 这叫动态属性：属性名不必事先全部申报。 

class OpenBox:
    def __init__(self, name):
        self.name = name

box = OpenBox("a")
box.extra = 1      # 成功：临时加了一个叫 extra 的格子
print(box.extra)   # 1

灵活，但也容易打错字：本意写 box.name = "x"，手滑写成 box.nmae = "x"， 不会报错，只是多了一个没用的 nmae，原来的 name 没改到——这类 bug 难查。

2.2 声明 __slots__：只允许名单里的名字

__slots__ 是类里的一个特殊声明（两边双下划线，语言认的 dunder，不是「私有」）。 写成元组/列表，列出本类实例允许拥有的属性名。名单外赋值 → AttributeError。 

class ClosedBox:
    __slots__ = ("name",)   # 注意：单元素元组要有逗号

    def __init__(self, name):
        self.name = name

("name",) 的逗号：写成 ("name") 只是加了括号的字符串，不是一元组。

2.3 三案对照（必背）

案写法结果说明
① 无 __slots__，再 obj.extra = 1 成功 默认动态属性（0012 行为）
② 有 slots，改名单内的 name 可读写 名单不是「只读」，只是「只许这些名字」
③ 有 slots，再加名单外的 extra AttributeError 没有这个格子，也不许新建 
# ①
open_box = OpenBox("a")
open_box.extra = 1          # OK

# ②
closed = ClosedBox("b")
closed.name = "b2"          # OK：name 在名单里

# ③
closed.extra = 1            # AttributeError

2.4 和「私有」无关；North 怎么用

易混澄清
slots 是不是 private？ 不是。它管的是能不能动态加字段名，不管谁能读。名单里的 name 外面照样 closed.name。
和单下划线 _value 一起用？ 可以。本课 name_guard.ToolName：__slots__ = ("_value",) + @property value——锁名 + 约定内部存储。
主要图什么？ ① 防打错字变成野属性；② 大量小对象时略省内存（默认每实例一个 dict）。

North 的 dataclass 没有开 slots（除非显式 @dataclass(slots=True)，20 章都没写）。 阶段 0 过关：见到能解释「锁属性名、可选省内存」；自己写 Agent 脚本不必先用。 可跑对照：examples.py 例 2；主脚本 name_guard.py 里 slots 拦住 bash.extra = True。

3. @property：方法当属性读

有时你想让外面写 policy.max_retries（像读字段），但背后其实要跑一段逻辑（读内部存储、做校验）。 property 就是把「无参方法」伪装成「属性访问」：读时不加 ()。

3.0 先认：是「装饰器」，不是「注释器」

行首的 @xxx 叫 装饰器（decorator），不要叫注释器。 注释是 # ... 给人看的；装饰器是真会改下一行定义行为的语法糖。

写法：@foo 紧贴在 def / class 上一行，表示「下面这个定义先交给 foo 加工再绑定名字」。 本阶段只认会用，不必自己写通用装饰器函数（0012 / Day17 已跳过）。

你见过的 @贴在什么上面加工后多了什么
@dataclass class 自动生成 __init__ / repr 等（0012）
@property def（getter） 读 obj.名 时调这个函数；默认不能写
@名.setter 同名 def 给已有 property 补上写通道
@staticmethod def 变成无 self 的普通函数，挂在类名下
@classmethod def 第一个参数变成 cls（类本身）

口诀：见到 @foo →「下一行的定义被 foo 加工过」。 不是发网络、不是删注释、也不是 Java 注解（annotation）——功能上有点像注解+框架挂钩，但 Python 里标准译名是装饰器。

3.1 getter / setter 是什么（先记这对词）

英文对应装饰器何时触发干什么
getter（读取器） @property 读：policy.max_retries 算出/取出值并 return；不加 ()
setter（设置器） @max_retries.setter 写：policy.max_retries = 5 校验后写入真格子 _max_retries

一对名字、两条钩子：读走 getter，写走 setter。 只有 @property、没有 @xxx.setter → 只有读钩子，没有写钩子 → 赋值会报错（下一小节）。

无参函数不必用装饰器。 普通实例方法照样写 def schema(self): ...，调用 obj.schema()（有括号）。 只有当你想让外面写成 obj.名（像字段、不加括号）时，才给这个无参方法加 @property。 装饰器是「需要时才贴」的加工标签，不是无参函数的通行证。

3.2 为什么不只写普通字段？

写法读写校验？
普通字段 self.n = n obj.n obj.n = -1 也成功 无；非法值照样进去
@property + setter obj.max_retries（无括号） obj.max_retries = -1 可拦截 有；setter 里 raise
只有 @property（无 setter） 同上 赋值 → AttributeError 只读对外接口

3.3 为什么「没有 setter」会报错？

@property 加工后，这个名字在类上变成一个受管属性： 解释器规定——读必须走 getter；写必须走 setter。 没挂 setter = 写通道不存在，不是「当成普通字段随便赋」。 

class ReadonlyLabel:
    def __init__(self, text: str) -> None:
        self._text = text          # 真格子：在 __init__ 里用 _text 直接写，OK

    @property
    def text(self) -> str:         # 只有 getter
        return self._text
    # 没有 @text.setter

label = ReadonlyLabel("bash")
print(label.text)     # OK → 调 getter
label.text = "other"  # AttributeError：property 没有 setter / can't set attribute
动作有 getter + setter只有 getter
读 obj.名调 getter调 getter
写 obj.名 = ...调 setterAttributeError（故意只读）
在 __init__ 里写 self._名 = ...直接写真格子，不走对外名同上；只读门面仍可在内部灌初值

这不是 bug：作者用「无 setter」表达 对外只读。 本课 ToolName.value、ReadonlyLabel.text 都是这种。 若既要对外可写又要校验，就补上 @名.setter（如 RetryPolicy.max_retries）。

3.4 两个名字 + 全流程（getter / setter 怎么接力）

max_retries 和 _max_retries 不是同一个东西：

名字角色
_max_retries真格子：普通属性，里面就是一个 int
max_retries对外门面：一对「读函数 / 写函数」，不是普通字段

@property / @max_retries.setter 告诉解释器： 读 policy.max_retries → 调 getter； 写 policy.max_retries = 5 → 调 setter。 所以 setter = 给「赋值」装上的钩子：先校验，再写入真格子。 

class RetryPolicy:
    def __init__(self, max_retries: int) -> None:
        # ① 先建内部格子（写 _max_retries，不走 setter）
        self._max_retries = 0
        # ② 再赋对外名（写 max_retries，会走 setter，创建时就校验）
        self.max_retries = max_retries

    @property
    def max_retries(self) -> int:           # ← 这是 getter
        # 读 policy.max_retries 时调用这里；必须 return _max_retries
        # 若写成 return self.max_retries → 又触发 getter → 递归炸栈
        return self._max_retries

    @max_retries.setter
    def max_retries(self, value: int) -> None:  # ← 这是 setter
        # 写 policy.max_retries = ... 时调用这里
        if value < 0:                      # 门卫：非法则抛错，不改数据
            raise ValueError("max_retries must be >= 0")
        self._max_retries = value          # 合法才写入真格子

创建 RetryPolicy(3)：

RetryPolicy(3)
  → __init__(self, max_retries=3)
      self._max_retries = 0          # 占位，不走 setter
      self.max_retries = 3           # 触发 setter(value=3)
           → 校验通过
           → self._max_retries = 3   # 真格子变成 3

# 若 RetryPolicy(-1)：setter 里 raise → 对象创建失败

读（无括号）与写：

policy.max_retries          # → getter → return _max_retries
# 不要写成 policy.max_retries()  —— getter 已返回 int，再 () 会 TypeError

policy.max_retries = 5      # → setter(value=5) → 校验 → _max_retries = 5
policy.max_retries = -1     # → setter → ValueError；真格子不变

对照图（对外名 ↔ 钩子 ↔ 真存储）：

外面读写的名字:     max_retries
                         │
          ┌──────────────┼──────────────┐
          │ 读                          │ 写 =
          ▼                          ▼
     getter (@property)         setter (@名.setter)
     return _max_retries        校验 → 写入 _max_retries
          │                          │
          └──────────┬───────────────┘
                     ▼
              真存储: _max_retries

# 若去掉 setter 这一支：写通道消失 → AttributeError（只读）

口诀：对外用 max_retries，对内只动 _max_retries；读 getter、写 setter、无 setter 则只读。

3.5 三案汇总（读 / 写 / 只读）

案操作结果
①print(policy.max_retries)走 getter，得到 int；不要写成 max_retries()
②policy.max_retries = 5 / = -1走 setter；合法写入 / 非法 ValueError
③只有 getter 的 property 再赋值AttributeError（没有写通道）

4. 三种方法：实例 / 静态 / 类方法

都写在 class 里，差别是第一个参数是谁、以及调用时手里要不要已有实例。 @staticmethod / @classmethod 也是装饰器（见 3.0）：加工紧挨着的下一个 def。

4.1 总表

种类第一个参数谁来调用典型用途
实例方法（默认） self（某一个对象） obj.schema() 要用到该实例上的数据
@staticmethod 无 self / 无 cls Cls.is_valid(x) 或 obj.is_valid(x) 和实例无关的纯规则，只是挂在类名下好找
@classmethod cls（类本身 / 图纸） Cls.from_dict(d) 工厂：return cls(...)；子类调用得到子类实例

4.2 实例方法：已经有对象

class ToolSpec:
    def __init__(self, name: str) -> None:
        self.name = name

    def schema(self) -> dict[str, str]:
        return {"name": self.name}   # 用到 self.name

ToolSpec("bash").schema()   # → {"name": "bash"}

0012 的 self：点号左边自动填进第一个参数。没有实例就谈不上 schema()。

4.3 @staticmethod：纯函数，挂在类上

有时规则根本不需要某个具体对象——比如「这个字符串算不算合法工具名」。 写成普通实例方法会别扭：还没造出对象，就不能问合不合法。 @staticmethod：把函数放进类的命名空间里，但不自动传入 self / cls。

写法和调用
class ToolSpec:
    @staticmethod
    def is_valid_name(name: str) -> bool:
        # 没有 self，也没有 cls —— 参数表里只有你显式写的
        return bool(name) and " " not in name

# 推荐：用类名调用（还没有实例）
ToolSpec.is_valid_name("rag_search")  # True
ToolSpec.is_valid_name("bad name")    # False

# 也能用已有实例调用，但第一个参数仍不会变成 self
spec = ToolSpec("bash")
spec.is_valid_name("x")               # 同样只是把 "x" 传给 name
为什么两个返回值不一样？

不是 staticmethod 有两套逻辑，而是传入的字符串不同：

实参bool(name)" " not in name结果
"rag_search"非空 → True无空格 → TrueTrue
"bad name"非空 → True有空格 → FalseFalse
""空 → False（短路，可不看）False
和「模块级函数」比；和实例方法比
写法差别
模块里 def is_valid_name(name): ... 完全可行；staticmethod 只是把函数挂到类名下，表示「这是 ToolSpec 相关规则」
实例方法 def is_valid_name(self, name): ... 必须先有实例；且容易误用 self。规则与实例无关时用 static 更干净
staticmethod 里写 self.xxx 不行：没有这个参数 → NameError

本课主脚本 ToolName.is_valid 同理：造 ToolName(...) 之前就能问名字合不合法。 Java 对照：接近 public static boolean isValidName(String name)。

4.4 @classmethod：第一个参数是类（图纸）

cls 不是关键字（约定名，别改），也不是某一个实例。 它是类本身：调用时点号左边是哪个类，cls 就是那个类。

selfcls
出现在普通实例方法@classmethod
是什么某一个已造好的对象（成品）类这个图纸
谁填进来obj.schema() 左边的 objToolSpec.from_dict(...) 左边的类名
工厂：用图纸造实例

工厂在这里不是工业术语，而是起名习惯：一个函数/方法的职责是 「按某种输入，造出对象并返回」。 往往比直接调用构造更方便——先加工输入（取 dict 字段、strip…），再 cls(...) / 类名构造。

普通构造工厂（本课）
ToolSpec("read")ToolSpec.from_dict({"name": "read"})
ToolName("bash")ToolName.parse(" bash ")
参数已是 __init__ 要的形状先加工，再造实例

@classmethod 工厂 = 这个入口写在类上，里面用 cls(...) 造； 子类调用同一份方法时，cls 变成子类，仍造出子类实例。 口诀：工厂 = 「帮你 new 出一个实例」的函数。 

class ToolSpec:
    def __init__(self, name: str) -> None:
        self.name = name

    @classmethod
    def from_dict(cls, data: dict[str, str]) -> "ToolSpec":
        # 调用 ToolSpec.from_dict(...) 时，cls 就是 ToolSpec
        return cls(data["name"])   # 等价于 ToolSpec(data["name"])，但别写死类名

obj = ToolSpec.from_dict({"name": "read"})
# 流程：
#   1. 解释器把 ToolSpec 填进 cls
#   2. data = {"name": "read"}
#   3. return cls("read") → 调用 ToolSpec.__init__，得到实例
为什么子类调用仍得到子类？
class SpecialTool(ToolSpec):
    pass

type(SpecialTool.from_dict({"name": "x"}))  # → SpecialTool

那句「要造实例，且希望子类调用时造出子类」怎么拆？

表里第二行其实是两个条件叠在一起，缺一就不必强上 classmethod：

条件含义反例（不满足时）
① 要造实例 这个函数的目的是返回一个新对象（工厂），不是只算 True/False is_valid_name 只返回 bool → 用 staticmethod 即可
② 希望子类调用时造出子类 以后若有 SpecialXxx(父类)，希望 SpecialXxx.工厂(...) 得到的是子类实例，而不是写死的父类 确定永远没有子类、或工厂写在模块里并写死类名也无所谓 → 不必纠结 cls

两个条件都满足 → 写成 @classmethod，里面 return cls(...)。

本课两个例子对照：

# examples.py：从 dict 造 ToolSpec
@classmethod
def from_dict(cls, data: dict[str, str]) -> "ToolSpec":
    return cls(data["name"])
# ToolSpec.from_dict(...)     → 造出 ToolSpec
# SpecialTool.from_dict(...)  → 造出 SpecialTool（子类白嫖同一份工厂）

# name_guard.py：从原始字符串造 ToolName（先 strip 再构造）
@classmethod
def parse(cls, raw: str) -> ToolName:
    return cls(raw.strip())
# ToolName.parse("  bash  ")           → ToolName('bash')
# 若将来有 class StrictName(ToolName): → StrictName.parse(...) 仍得 StrictName
例子① 造实例？② 照顾子类？怎么调用
from_dict 是：返回 cls(...) 是：SpecialTool.from_dict 时 cls 变子类 ToolSpec.from_dict({"name": "read"})
ToolName.parse 是：strip 后 cls(...) 是：同一写法，子类可继承 ToolName.parse("bash")
is_valid / is_valid_name 否：只返回 bool 不涉及造谁 用 @staticmethod

现阶段若还没有子类：你写 ToolName.parse 仍然合理——它是清晰的「构造入口」， 并且预先留好子类继承时不用改工厂。 不必为了 classmethod 硬造子类；读懂「写 cls 而不是写死类名」即可。

口诀：self = 某一个成品；cls = 图纸。 可跑：examples.py 例 4（含 SpecialTool）；主脚本 name_guard.py 看 parse。

常见坑 + 边界

  • 以为 _x 会报错：不会。只是约定；外面仍能读。
  • 以为 __x 是安全私有：能用 _Class__x 读到；目的是防子类踩名。
  • 把 __secret 和 __name__ 当成一类：前者名称改写；后者是语言特殊名（dunder）。
  • 把例子里的 bag 当成关键字：只是实例变量名，可换成任意合法标识符。
  • 以为 slots 是 private：不管可见性；只管能不能动态加字段名。
  • 写成 __slots__ = ("name")：少了逗号就不是元组，声明无效或行为怪异。
  • 把 @ 叫成「注释器」：标准译名是装饰器；注释是 #。
  • property 还加括号：policy.max_retries() 会把返回的 int 再当函数调 → TypeError。
  • getter 里写 return self.max_retries：应读 _max_retries，否则递归。
  • 奇怪为何无 setter 赋值报错：受管属性必须走 setter；没挂写通道 = 故意只读，不是普通字段。
  • staticmethod 里用 self：没有这个参数。
  • classmethod 里写死类名：return ToolSpec(...) 让子类工厂失效；应 return cls(...)。
