系统讲解

1. 文件是“磁盘上的字符串”，路径是它的地址

变量指向内存中的对象；文件存在于磁盘。Python 通过 open 打开文件，得到一个文件对象。最小读取代码如下：

with open("knowledge.txt", "r", encoding="utf-8") as file:
    text = file.read()

print(text)

逐词读：with 表示“进入一个需要清理的上下文”；open(...) 打开文件；as file 把文件对象命名为 file；缩进块里可以读；离开块后 Python 自动关闭文件。关闭很重要：文件句柄是有限的操作系统资源，异常发生时也必须释放。

2. Path 对象：先认识零件

Path 是「路径」的对象，不是已经打开的文件。它先帮你定位地址；真正读写还要 open 或 read_text。本课会用到这些零件：

零件做什么返回什么
__file__解释器提供的特殊变量：当前这份 .py 的路径通常是 str
Path(__file__)把字符串路径包成 Path，才能用下面的方法Path
.parent上一级目录（脚本所在文件夹）Path
/（Path 上）拼接子路径，等价于「进子目录 / 拼文件名」新的 Path；不要用字符串 + 手拼斜杠
Path.cwd()当前工作目录：你执行命令时「站」在哪Path
.name最后一段文件名（含后缀）str，如 "knowledge.txt"
.suffix扩展名（含点）str，如 ".txt"；无后缀则 ""
from pathlib import Path

print(__file__)                 # 当前脚本路径（字符串）
BASE_DIR = Path(__file__).parent
path = BASE_DIR / "knowledge.txt"
print(path.name)                # knowledge.txt
print(path.suffix)              # .txt
print(Path.cwd())               # 你现在站在哪
print(BASE_DIR)                 # 脚本躺在哪

绝对路径示例里的 r"D:\data\kb.txt" 是 0006 讲过的原始字符串：避免 \n、\t 被当成转义。Windows 路径里反斜杠多，常用 r"..."。

3. 路径三种锚点：cwd / 脚本目录 / 绝对路径

这是本课最容易踩坑、也最值得背下来的三案（对照你已会的可变默认值三案）：

锚点写法结果
当前工作目录open("knowledge.txt")相对你执行命令时所在目录；换目录运行就可能突然找不到
脚本所在目录Path(__file__).parent / "knowledge.txt"相对这份 .py 文件；练习与 Agent 工具默认应选这个
绝对路径Path(r"D:\data\kb.txt")不依赖 cwd；配置项、部署路径常用；本机硬编码要谨慎

Agent 里的配置、提示词和知识库都应该明确路径来源。默认优先「脚本目录拼接」；只有配置文件明确给出绝对路径时才用第三种。

4. exists() 与 resolve()：问的是两个不同问题

这两句常被并排写出，但不是同类操作：一个在问「有没有」，一个在问「规范成哪条绝对路径」。

方法问什么返回值路径不存在时
path.exists()磁盘上现在有没有这个路径指向的文件/目录bool（True/False）返回 False，一般不抛异常
path.resolve()把路径规范成绝对路径（去掉 .. 等；并尽量解析符号链接）新的 Path默认 strict=False：仍尽量给出绝对路径；不回答「有没有」
path = BASE_DIR / "knowledge.txt"

print(path)                 # 可能仍带相对感：.../0007-files-exceptions/knowledge.txt
print(path.exists())        # True 或 False —— 只回答存在性
print(path.resolve())       # D:\...\knowledge.txt —— 便于写进日志、报错信息

missing = BASE_DIR / "no-such.txt"
print(missing.exists())     # False
print(missing.resolve())    # 仍然是一条绝对路径字符串形态；存在性要用 exists 另查

记忆口诀：exists → 布尔检查；resolve → 把地址「写清楚」给人或日志看。需要「有没有」时用前者；需要「完整绝对路径」时用后者。二者常一起用，但职责不互换。官方说明见 Path.exists 与 Path.resolve。

5. 三个常用文本模式 + 一个安全写入：r、w、a、x

模式含义注意
r读取文件不存在会抛 FileNotFoundError
w覆盖写入打开瞬间清空旧内容；文件不存在会创建
a追加写入保留旧内容，把新内容写到末尾
x独占创建文件已存在则失败；避免误覆盖重要文件
log_path = BASE_DIR / "run.log"

with open(log_path, "w", encoding="utf-8") as file:
    file.write("启动\n")       # 每次运行先重置

with open(log_path, "a", encoding="utf-8") as file:
    file.write("调用 rag_search\n")  # 追加事件

不要把 w 当成“写一行”的意思，它是“我要这个文件的新内容完全由我负责”。日志通常用 a；生成一次性的输出文件才常用 w。

编码 encoding：磁盘上存的是字节；Python 里的 str 是字符。读写文本时必须约定「用哪套规则把字节 ↔ 字符」——这就是编码。中文知识库一律显式写 encoding="utf-8"：不写则跟操作系统默认走，换机器可能乱码或抛 UnicodeDecodeError。

6. open 与 Path.read_text：两种等价写法

# 写法 A：open + with（细粒度控制、适合逐行流式读）
with open(path, "r", encoding="utf-8") as file:
    text = file.read()

# 写法 B：Path 便捷方法（整文件读写更短）
text = path.read_text(encoding="utf-8")
path.write_text(text, encoding="utf-8")  # 等价于 w 覆盖写

小配置、小知识文件用 read_text 很合适。知识库可能很大、需要边读边过滤时，用 with open 逐行迭代更省内存。本课两个主脚本各示范一种：examples.py 偏 open，load_knowledge.py 偏 read_text。

7. read、readline、逐行循环：选择内存占用

with open(path, "r", encoding="utf-8") as file:
    whole = file.read()             # 一次读完，得到 str

with open(path, "r", encoding="utf-8") as file:
    first = file.readline()         # 读一行，末尾通常带 \n

with open(path, "r", encoding="utf-8") as file:
    for line in file:               # 逐行迭代，适合大文件
        cleaned = line.strip()
        if cleaned:
            print(cleaned)

小型 prompt 或配置可以 read()。如果知识库文件可能很大，逐行处理不会一次把所有内容塞进内存。注意：

  • read() → 一个大 str
  • readline() → 一行 str（常带末尾 \n）
  • readlines() → list[str]（一次载入所有行，大文件慎用）
  • for line in file → 边读边处理，通常最省内存

8. 把“加载文件”封装成函数

from pathlib import Path

def load_non_empty_lines(path: Path) -> list[str]:
    with open(path, "r", encoding="utf-8") as file:
        return [line.strip() for line in file if line.strip()]

lines = load_non_empty_lines(BASE_DIR / "knowledge.txt")

这里复用了 0006 的列表生成式：对文件逐行遍历，先过滤空行，再去除两端空白。函数的好处是：路径、清洗规则和调用处分离，之后换成 Markdown、数据库或 HTTP 接口时，主流程不必全部重写。

9. 扫目录：iterdir、suffix、sorted

load_knowledge.py 不是只读一个固定文件名，而是「打开一个文件夹，挑出知识文档」。新零件：

写法做什么
directory.iterdir()迭代该目录下一层的每个条目（文件或子目录），得到一串 Path；不递归进子文件夹
path.suffix扩展名；用 path.suffix in {".md", ".txt"} 过滤类型
sorted(...)0005 已学：让输出顺序稳定，便于对照
path.name只保留文件名，写进文档的 source 字段，避免把整段绝对路径塞进上下文
for path in sorted(directory.iterdir()):
    if path.suffix not in {".md", ".txt"}:
        continue
    text = path.read_text(encoding="utf-8")

10. 异常是运行时失败的控制流

语法错误通常在程序启动前就被发现；异常则发生在运行过程中。例如文件不存在、整数转换失败、字典键缺失。异常不是“Python 随机发脾气”，而是程序用来表达失败的控制流。官方教程把这类错误统称为 Errors and Exceptions：语法错在解析期，异常在执行期。

常用层次（从宽到窄记即可）：

Exception
 └─ OSError              # 文件系统相关总类
     └─ FileNotFoundError   # 路径不存在
     └─ PermissionError     # 没权限读/写
UnicodeDecodeError       # 字节无法按指定编码解成字符（不在 OSError 下）

匹配按书写顺序，具体异常放前面。若先写 OSError，后面的 FileNotFoundError 永远进不去。

11. 异常标准范式（整课心法）

后面所有策略都套在这一套骨架上。先背结构，再背决策，最后背五条硬规则。

11.1 结构骨架

try:
    # 1. 只放「可能失败」的最小几行
    text = path.read_text(encoding="utf-8")
except FileNotFoundError as error:
    # 2. 只捕获你知道怎么处理的具体类型；as 接住实例
    raise FileNotFoundError(f"知识文件不存在: {path}") from error
except OSError as error:
    # 3. 更宽泛的同类放后面
    raise RuntimeError(f"读取知识库失败: {path}") from error
else:
    # 4. 仅当 try 完全成功时执行（成功后的统计、继续加工）
    print(f"读到 {len(text)} 字符")
finally:
    # 5. 无论成败都会走；文件场景优先用 with，少手写 close
    pass

# 资源场景的标准写法（自动进入 finally 式清理）：
with open(path, "r", encoding="utf-8") as file:
    text = file.read()
子句何时执行本课用途
try先执行这里真正的 I/O / 转换
except T as etry 里抛出且类型匹配恢复、转换上抛、或记日志后跳过
elsetry 没有抛异常成功统计；避免把后续错误误判成读取错误
finally总会执行（有无异常都走）收尾；文件优先用 with 代替手写 close

11.2 决策：这一层该不该接住？

在函数边界问自己三个问题，答案唯一对应三种策略（下一节展开例子）：

问自己若答案是「是」策略名
我现在就能合理恢复吗？（默认值 / 跳过本条 / 换路径）except 后继续跑局部恢复
我恢复不了，但能把错误说成人话给上层吗？raise ... from error转换后上抛
我既不能恢复，也不比调用方更懂业务？不要 except，让它冒泡不捕获
                    发生异常
                        │
            ┌───────────┼───────────┐
            ▼           ▼           ▼
         能恢复？    只改语义？    都不行？
            │           │           │
       局部恢复    转换后上抛      不捕获
     （继续往下） （raise from）  （冒泡）

Agent / 工具边界的常见切法：底层小函数偏「不捕获」；知识库加载边界偏「转换后上抛」；批量扫目录时单文件失败偏「局部恢复」。

11.3 五条硬规则

  1. try 要窄：只包可能失败的那几行，不要把整个 main 塞进去。
  2. except 要具体：写 FileNotFoundError / ValueError，禁止裸 except:（会吞掉 KeyboardInterrupt 等）。
  3. 顺序从具体到宽泛：子类在前，父类在后。
  4. 边界才改写消息：用 raise NewError(...) from error 补业务语义，并保留原因链。
  5. 清理用对工具：文件 / 连接优先 with；finally 留给「with 管不到」的收尾。

11.4 和「先判断再动手」怎么选

Python 社区常说 EAFP（Easier to Ask Forgiveness than Permission）：先做，失败再用异常处理——例如直接 read_text，捕获 FileNotFoundError。这和 Java 里大量先 if (Files.exists(...)) 的风格不同。

但本课仍保留一条实用边界：若「不存在」是普通业务分支（例如可选配置文件），用 path.exists() 更清晰；若「不存在」是意外失败（例如必选知识库丢了），让它抛异常再用上面的决策处理。不要把异常当成普通 if/else 的替代品乱飞。

12. except ... as error：把异常对象接住

except SomeError as error 的意思是：匹配到该类异常后，把异常实例绑定到变量 error，以便读取消息或再抛出。这是标准范式里第 2 步的零件。

try:
    text = path.read_text(encoding="utf-8")
except FileNotFoundError as error:
    print(error)                 # 默认错误消息
    print(type(error).__name__)  # 类型名字符串，如 "FileNotFoundError"
    raise FileNotFoundError(f"知识文件不存在: {path}") from error
  • as error：接住实例（名字可自取，常用 e / err / error）
  • type(error)：异常的类；.__name__ 是类名字符串，适合日志里打印「跳过 xxx: PermissionError」
  • raise ... from error：再抛一个新异常，并保留原异常为原因链（调试时能看到底层原因）

13. 边界上三种异常策略（范式的落点）

这就是第 11.2 节决策表的可跑版本。工具函数、知识库加载、解析 tool_call 时，你会反复在这三种里选：

策略做法适用
局部恢复except 后给默认值 / 跳过本条，程序继续批量加载文档：坏文件不该拖垮整库
转换后上抛raise ... from error，补业务语义边界函数：底层说「路径不存在」，你说「知识库缺失」
不捕获让异常冒泡给调用方库代码不知如何恢复；由 Agent loop / main 决定退出或重试
# 1) 局部恢复 —— 我能扛
try:
    text = path.read_text(encoding="utf-8")
except FileNotFoundError:
    text = ""

# 2) 转换后上抛 —— 我说清楚，上层做决定
try:
    return path.read_text(encoding="utf-8")
except FileNotFoundError as error:
    raise FileNotFoundError(f"知识文件不存在: {path}") from error

# 3) 不捕获 —— 我什么都不说，直接冒泡
text = path.read_text(encoding="utf-8")

转换后上抛怎么读：底层异常太「系统」；边界函数把它改写成调用方听得懂的业务话，同时用 from error 把原件挂在原因链上。和 Java 的 throw new X("业务消息", cause) 同一思路。

和 Java 的另一差别：Python 不强制在签名上声明 throws，但职责仍然要设计——谁恢复、谁转换、谁决定失败。load_knowledge.py 用策略 1；read_lines_safely 用策略 2；策略 3 适合更底层的小函数。

14. else、finally 与 with（骨架里的第 4、5 步）

try:
    data = load_non_empty_lines(path)
except FileNotFoundError:
    data = []
except UnicodeDecodeError:
    raise ValueError("知识库必须是 UTF-8 文本")
else:
    print(f"成功加载 {len(data)} 行")
finally:
    print("这句话无论成功失败都会执行")

else 适合放“成功之后才做”的事，这样成功统计不会被误认成读取失败的一部分。finally 无论成功还是异常都会运行。对文件来说，with 已经替你完成关闭，因此通常不需要手写 finally: file.close()。

15. raise：在边界把错误说清楚

def load_text(path: Path) -> str:
    try:
        return path.read_text(encoding="utf-8")
    except FileNotFoundError as error:
        raise FileNotFoundError(f"知识文件不存在: {path}") from error

这是标准范式里「转换后上抛」的完整函数形态：接住 → 改写消息 → from error 保留链路 → 交给上层。函数不必自己吞掉错误；它可以转换后继续抛出，让更上层决定退出、重试还是跳过。

常见坑 + 边界

  • 当前目录不是脚本目录：命令在哪个目录执行，open("x.txt") 就从哪里找。用 Path(__file__).parent 明确锚点。
  • w 的破坏性：打开就截断，哪怕后面还没写入。重要文件可用 x 防止覆盖，或先写临时文件再替换。
  • write_text 也是覆盖：它等价于 w，不是追加。
  • 编码不匹配：中文文本通常用 UTF-8；UnicodeDecodeError 说明“字节无法按指定编码解释”，不是普通的空字符串。
  • 不要裸 except:：它还会捕获键盘中断等不应静默处理的情况。优先写具体异常。
  • 不要把异常当 if：能用 path.exists() 判断的普通分支，不必先打开再靠异常控制正常流程；异常留给真正意外的失败。
  • 三种策略别混用职责：边界函数若既吞掉错误又返回模糊空值，上层会以为“知识库是空的”而不是“加载失败”。
  • Java 易混：Python 没有 checked exception；函数签名不写 throws，但边界仍要设计谁负责捕获、谁负责继续抛出。
