系统讲解

1. 标准库 vs 第三方包

标准库：装 Python 时自带（json、pathlib、http.server）。第三方包：别人发布、你要额外装（requests、langchain、openai）。

import json          # 标准库，不用 pip
import requests      # 第三方，要先 pip install requests

Agent 项目依赖往往几十个第三方包 → 必须用清单文件（如本课 requirements-agent-demo.txt，真仓库常叫 requirements.txt）做可复现安装。

2.3 .venv 里到底有什么

venv（virtual environment）不是「又一个 Python 安装程序」，而是一份可复制的运行时布局：指向你本机已装 Python 的轻量壳 + 独立 site-packages。

路径（Windows）是什么
.venv\Scripts\python.exe激活后你用的解释器；show_venv_context 的 sys.executable 应指向它
.venv\Scripts\Activate.ps1激活脚本：改 PATH，让 python / pip 优先用 venv 里那份
.venv\Lib\site-packages\第三方包目录；pip install requests 把包装进这里
sys.prefix运行时报告的环境根，venv 里通常是 ...\playground\python\.venv
# 激活前（示意）：python 可能指向系统安装
C:\Users\...\AppData\...\python.exe

# 激活后：同一终端里
D:\agent-learning\playground\python\.venv\Scripts\python.exe

site-packages：第三方包落盘文件夹。标准库（json、sys）仍在 Python 安装目录；只有 pip 装的包在 venv 的 site-packages。

2.4 什么进 git、什么不进

文件/目录进 git？原因
requirements*.txt真项目：是；本练习场：在 playground 里故也不进教学 git记录「要装什么」；体积小、可复现
.venv/从不体积大、含平台路径；每人 python -m venv .venv + pip install -r 本地生成
playground/ 整目录本教学仓：否（.gitignore）练习脚本与 venv 都是本地产物
你的练习 *.py本仓：随 playground 忽略；真 Agent 仓：是源码要共享；环境不共享

不要把同事的 .venv 文件夹拷过来——路径、平台、小版本都可能不对。正确流程：clone → 自己建 venv → install -r。

2.5 激活（activate）到底做了什么

激活不会再装一遍 Python；它只是让当前 shell「默认用 .venv\Scripts 里的 python/pip」。

  1. 你在 playground\python 执行 .\.venv\Scripts\Activate.ps1
  2. PATH 前面插入 .venv\Scripts
  3. 此后 python、pip 命令走 venv
  4. python -m pip install 与 pip install 在激活后通常一致；仍推荐 -m pip 防 IDE/多 Python 混乱

IDE（Cursor）：终端激活 ≠ IDE 解释器自动对齐；若终端能 import requests 但 IDE 红线，在设置里把解释器选为 playground\python\.venv\Scripts\python.exe。

2.7 三个常问：不激活能用吗？激活干啥？版本怎么同步？

Q1：「激活后 python 指向 .venv」——不激活就不能用吗？

不是。.venv\Scripts\python.exe 一直存在、一直可用。激活只是让你在终端里打短命令 python 时，不用每次写全路径。

方式命令示例用的哪个 Python
未激活，打 pythonpython script.pyPATH 里第一个 python——通常是系统安装或 py launcher，不是 .venv
未激活，写全路径.venv\Scripts\python.exe script.py就是 练习场 venv，与激活后等价
已激活，打 pythonpython script.py.venv（因为 PATH 前面插了 Scripts）
推荐（可不激活）.\.venv\Scripts\python.exe -m pip install ...显式绑定 venv，不依赖 PATH

本仓库里你常看到 .\.venv\Scripts\python.exe 0011-packages\examples.py——没激活也能跑，因为路径已经写死到 venv 的 python。

Q2：激活脚本（Activate.ps1）的作用是什么？

它只改当前这个终端会话的环境，不会修改系统、不会重装 Python、不会写进 git。

  • 主要：把 .venv\Scripts 插到 PATH 最前面 → python / pip 命令优先找到 venv 里的 exe
  • 常见：设置环境变量 VIRTUAL_ENV（指向 .venv 路径），部分工具靠它识别「我在 venv 里」
  • 不会：复制一份新的 Python 安装包；venv 创建时已经链好本机 Python 3.12
  • 关闭终端 或 deactivate 后，PATH 恢复，又回到「打 python 可能是系统 Python」
# 激活 ≈ 给当前 PowerShell 贴一张便签：「python 请用 .venv\Scripts 里的」
.\.venv\Scripts\Activate.ps1

# 未激活但等价写法（便签没贴，但手写全路径）
.\.venv\Scripts\python.exe your_script.py

Q3：.venv 进不进 git？Python 版本怎么和大家保持一致？

问题答案
.venv 进 git 吗？不进。本教学仓 playground/ 与 .venv/ 均在 .gitignore；真 Agent 仓也一样只提交源码 + 依赖描述
那大家装什么包？提交 requirements.txt（或 pyproject.toml）→ 每人本地 pip install -r
Python 解释器版本怎么同步？不靠 .venv 文件夹；靠 README / requires-python = ">=3.11" / .python-version 等文字约定
每人具体怎么做？先装对版本的系统 Python（如 3.12）→ python3.12 -m venv .venv → pip install -r requirements.txt

requirements.txt 锁定的是第三方包版本（requests 2.34.2），不自动锁定「你必须用 Python 3.12.9」。解释器大版本由 README 约定；小版本差异（3.12.8 vs 3.12.9）通常可接受。

# 真项目 README 常见三行
Python 3.11+
python -m venv .venv
pip install -r requirements.txt

2.8 辨析：为什么「README + 依赖清单」进 git，.venv 不进？

一句话：git 管「要什么」；本机 .venv 是「已经装好的那一坨」，每人按同一清单自己重建。

进 git（声明）不进 git（本机实例）
requirements.txt / pyproject.toml.venv/ 整个目录
README：Python 3.11+、建 venv、安装命令Lib\site-packages 里下载好的 wheel
源码 *.py（真 Agent 仓）本教学仓整个 playground/

声明 vs 实例

  • requirements.txt = 声明：「需要 requests>=2.31」——小文本、可 diff、PR 里能 review（≈ Maven pom.xml 依赖块）
  • .venv = 实例：pip 已解析、已下载、已落盘的环境（≈ 本机 Maven 缓存 / target/，不当源码分发）

为什么不把 .venv 提交进 git？

原因说明
体积常几百 MB；拖慢 clone、污染历史
平台Windows Scripts\ vs Linux bin/；路径写死在你机器上，拷到别人电脑易坏
可复现方式目标是「按清单重建等价环境」，不是「共享同一个物理文件夹」；CI 也是每次新建 venv + install -r
安全与审计清单改一行依赖，PR 一眼可见；整包 .venv 难审查

Python 解释器版本谁管？

  • requirements.txt 锁第三方包版本，不锁「你必须 Python 3.12.9」
  • 解释器大版本（3.11 vs 3.12）靠 README、requires-python、.python-version 等文字约定
  • 每人：本机先装对版本的 Python → python -m venv .venv → pip install -r

.venv\pyvenv.cfg（你可打开看）记录「这个 venv 是用哪台机器上的哪个 Python 创建的」——是本地元数据，本教学仓随 playground 不进 git；不能代替 README 里的版本说明。

3. pip 是什么；为什么写 python -m pip

pip = Python 的包安装器（Package Installer for Python）。从 PyPI 等源下载并装进当前环境的 site-packages。

python -m pip install requests     # 推荐：绑定当前 python.exe
pip install requests               # 可能指向别的 Python（激活错时踩坑）

python -m pip 的含义：用「当前这个 Python 解释器」去运行 pip 模块——和 Java 用项目 JDK 跑 mvn 同一纪律。

5. requirements.txt 怎么读

requirements.txt = 依赖清单文本文件，一行一个依赖。

# 注释行，pip 会跳过
requests>=2.31.0
# 常见运算符：== 精确；>= / <= 范围；~= 兼容发布（了解）

本课练习文件 requirements-agent-demo.txt 只有 requests（0010 已用过）。脚本 parse_requirements.py 演示如何读文件、跳过注释、拆包名（不调用 pip）。

6. 装完之后怎么查：list / show / freeze

命令输出什么
pip list当前环境已装包及版本（表格）
pip show requests单个包元数据（版本、依赖、安装位置）
pip freeze包==版本 行，适合生成锁定清单

脚本 pip_commands_demo.py 用 subprocess 跑 python -m pip list/show，避免你记错「当前是哪个 pip」。

7. pip 包名 vs import 名（认即可）

多数一致（requests）；少数不同，例如 pip 装 pillow、代码里 import PIL。读 requirements 后验证能否跑，用 check_imports.py 或亲手 import。

8. clone Agent 仓库后的标准起手式

  1. 读 README：Python 版本、是否要求 venv
  2. python -m venv .venv + 激活
  3. python -m pip install -r requirements.txt（或 README 写的文件名）
  4. python -m pip list 或跑 README 里的 smoke 命令

常见坑 + 边界

  • 全局 pip：多项目版本地狱；Agent 学习一律 venv。
  • 不提交 .venv：仓库只提交 requirements；每人本地建 venv 再装。
  • pip freeze 乱：会列出所有包；生产清单常只写直接依赖 + 锁定版本策略。
  • 密钥进 requirements：不要；API Key 用环境变量。
  • Windows 中文注释：pip install -r 在中文 Windows 上常按 GBK 读文件；requirements.txt 注释请用纯 ASCII（中文放 README），否则会 UnicodeDecodeError。
  • Java 易混：Python 没有「编译期解析全部依赖」；装错环境要到运行 import 才爆。
