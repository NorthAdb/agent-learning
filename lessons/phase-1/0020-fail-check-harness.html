系统讲解

1. 模型强，不等于这次靠得住

能力鸿沟：模型在基准测试（讲义举 SWE-bench Verified 约 50–60%）上的表现， 和你把日常糊需求丢过去时的表现，中间有很大落差。 基准题有明确描述和现成测试；你的任务常常没有。

大多数人的第一反应是换更贵的模型。讲义说先别掏钱包。

如果同一个模型在类似的结构良好的任务中能成功，那优先假设是 harness 的问题。

能力鸿沟定义： L01 · 关键名词解释。 先修 harness： L01 · 遇到失败，先修 harness。

Anthropic 对照：同一句 prompt、同一个 Opus，裸跑游戏核心起不来；配上完整 harness 就能玩。 马没换，换的是马具。 这叫 Harness 诱导失败：能力够，环境结构有洞。

L01 · 同一匹马，两种命运 。planner / generator / evaluator 怎么搭，本课不展开。

三案（该不该换模型）：

案信号怎么做
① 同类任务、规格清楚时这个模型做成过 先修 harness。本课主路径
② 它说做完了，pytest / lint 没过 验证缺口。补完成定义，不是换大脑
③ 规格、测试、环境都齐了，这类题它一直做不到 才考虑换模型。地基阶段几乎不走这条

2. Agent 到底卡在哪：五种卡点

讲义把常见失败收成五类。本课每类对应五层归因里的一层。

卡点一句话落哪层
需求模糊 「加个搜索」等于没说：搜什么、要不要分页 任务规范
隐性约定 SQLAlchemy 2.0 只在 Slack 里；模型没见过 上下文供给（接 0017：没进上下文 = 不存在）
环境缺口 依赖缺、版本不对，窗口耗在 pip install 执行环境
缺少验证 没测试 / 没告诉它验证命令，它自己觉得做完了 验证反馈（验证缺口）
跨会话丢失 新对话又从探索仓库开始；长任务特别容易死 状态管理

五种卡点： L01 · agent 到底卡在哪。 「上下文焦虑」（窗口快满就赶工跳过验证）同节一带而过，本课不单列术语。

3. 五层归因：失败清单，不是第二套架构

每次失败问：是任务没说清、上下文不够、环境没配好、验证手段缺失，还是上个会话接不上？ 五层名字：任务规范、上下文供给、执行环境、验证反馈、状态管理。

和 L02 的「指令 / 工具 / 环境 / 状态 / 反馈」不是同一张表。 本课这张是出了问题往哪查；L02 是 harness 由哪些子系统组成，阶段 2 再开。

五层原文： L01 · 遇到失败，先修 harness。 L02 暂缓：计划写在阶段 1 的「故意不讲」里。

4. 验证缺口：口嗨完成不算完成

验证缺口：agent 对自己输出的信心，和实际对不对之间的偏差。 最常见：它说「做完了」，测试是红的。 这不是 0019 的「无 tool call 就停」出错——停是对的；错在停之前没有一道独立的验证门。

完成定义：一组可以用命令验证的条件。没有它，agent 会自己编一个「看起来合理就算完」。 

完成标准（讲义示例，缩过）：
- 新增 GET /api/search?q=xxx
- 支持分页，默认 20 条
- 新代码通过 pytest
- 类型检查通过

叠回 0018：生产 Harness 的「验证」就是把完成定义变成门禁。 约束是拦危险操作；验证是检查做得对不对。不要混。

完成定义与示例： L01 · 遇到失败，先修 harness。 书：生产系统要验证， L273。

讲义还说：仓库根目录放 AGENTS.md（技术栈、约定、验证命令）往往是投入产出比最高的第一步。 本课不要求你从空白写一份；阶段 2 对着 North 仓库再看现成的。

5. 诊断循环：失败是信号，不是「模型又傻了」

诊断循环：执行 → 观察失败 → 定位到某一层 → 修补那一层 → 再执行。 不要停在「再跑一遍碰运气」。记一笔：成功没有、失败落在哪层——几轮就能看出瓶颈。

定义在「关键名词解释」；操作在「遇到失败，先修 harness」。 接地气例子（一句话需求 vs 加了 AGENTS.md + 验证命令）： L01 · 一个更接地气的例子。
