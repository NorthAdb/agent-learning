Agent 公式：LLM + 上下文 + 工具

使命要求你能用一句话说清 Agent = LLM + 上下文 + 工具，并知道 Harness 落在哪一侧。 本课只钉公式本身：三块各是什么、环境为什么在外面、缺一块或路径写死分别叫什么。 Harness 展开和循环机制留给 0018 / 0019。不调模型，不跑 North code.py。

为什么要学？（动机）

你日常已经在用 Cursor / Claude Code。阶段 0 练的是「读得动 Python」。 从现在起，主技能换成心智模型：看到一个系统，能指出大脑、眼睛、手脚分别在哪， 以及你以后要造的 harness 先落在哪两块上。

课 0003 用 while 画过一个假 loop——那是控制流预习。 本课先回答「循环里转的是哪三块」，0019 再把 while 重新解释成 ReAct。

和 Java 怎么对照

本课概念Java 直觉关键差异
LLM 你调的一个「决策服务」 没有你能 step-through 的业务源码；策略在权重里，不在 if-else 树里
上下文 一次请求带上的 DTO + 会话状态 + 配置 模型只根据这次请求里的文本做决定；仓库里有文件不等于它看见了
工具 注入的 Repository / HTTP client / 文件 API 调不调、调哪个、传什么，默认由模型选，不是 Controller 里写死的调用顺序
Environment 真实 DB、磁盘、对端服务 在 Agent 外面；公式不包含它
工作流 写死的状态机 / 责任链 每步可以调 LLM，但「下一步去哪」由代码决定
自主 Agent while + 策略服务选下一动作 退出条件仍要你设（final / 触顶），见课 0003 的 max_turns

系统讲解

1. 公式：三块零件，加号不是奖励

1.1 它是什么？

书给出最小工程公式：Agent = LLM + 上下文 + 工具。 这里的加号表示把三块工程组件拼在一起，不是强化学习里把奖励加起来。 更直白的说法：Agent = 大脑 + 眼睛 + 手脚。

原文： 第01章.md · §1.1 L11 

Agent = LLM（大脑）+ 上下文（眼睛）+ 工具（手脚）
Agent  ↔  Environment（环境：公式外面）
零件一句话
LLM 决策内核：理解意图、规划、判断「要不要调工具 / 调哪个 / 传什么」。
上下文 这一次决策能看到的全部信息。不限于用户刚打的那句——观察、记忆、工具说明书都可以在里面。
工具 感知或改变外部世界的接口：读文件、跑命令、搜网页、调 HTTP……没有它只能「纸上谈兵」。

书还强调：这个公式只描述 Agent 边界之内的实现。 你与之交互的文件系统、网络、用户机器，叫 Environment（环境），不写在加号右边。

「没进上下文就像不存在」：书 §1.1.1 L36 起。

1.2 解决什么问题？

没有这张图，很容易把三件不同的事混成一个词「Agent」： 模型厂商的 API、你写的循环代码、真实世界里的文件和测试。 拆开以后才能回答使命里的第二句：Harness 落在「上下文 + 工具」这一侧 （再加约束 / 验证 / 纠正是 0018 的事）。

1.3 小例

用户说：「看看 app.py 里有没有 TODO，有就改掉并跑测试。」

零件这一次分别是什么
LLM决定：先读文件，再改，再跑 pytest，而不是直接回复「好的我改了」
上下文用户这句话 + 工具清单 + 稍后读到的 app.py 正文 + 测试输出
工具read / edit / bash（或你们项目里的等价物）
环境磁盘上的真实 app.py 和测试进程；它们不在模型权重里

2. 环境在外面：看不见 = 不存在

经典图景是闭环：环境给出观察 → Agent 选行动 → 环境改变 → 新观察。 Harness 干的第一件事，就是把观察转成上下文，再把模型选出的行动转成工具调用。

硬规则（书 §1.1.1）：没有通过观察通道进入上下文的信息，对模型来说就像不存在。 仓库里有 README.md、你脑子里有「我们用 SQLAlchemy 2.0」，都不算——除非写进这一次请求， 或做成模型能调的读文件 / 检索工具并真的调了。

对称的另一半：没有被动作接口允许的操作，模型再清楚也只能停留在文字建议上。 「我可以帮你删掉生产库」如果没有对应工具（或权限拦住了），它删不成。

所以模型固定时，提升任务表现的主杠杆常常是扩眼睛、扩手脚——把该看的数据送进上下文， 把该做的操作封成工具。产品案例（Manus 把浏览器和终端并进同一套接口）本课不展开， 记住这句杠杆就够。

3. 三案：缺一块就不是公式里的 Agent

易混点按三种缺法写满，对照主脚本 ①②④。

缺什么表面上像什么本仓库判定
缺 LLM cron、shell 脚本、写死的爬虫 自动化，不是 Agent——没有决策内核
缺上下文 每次只喂一句新问题，不带历史、不读仓库 盲打。文件在磁盘上 ≠ 模型看见了
缺工具 把文档贴进 prompt 的问答窗 能看不能做：纸上谈兵

课 0003 的假模型之所以能「跑」，是因为脚本里已经有工具表和 while； 那是形状，还不是本课的判定清单。本课先会贴标签，0019 再回到循环。

4. 一条边界：工作流不是自主 Agent

三块零件都在，仍可能不是本仓库说的 Agent。 书把工作流定义为：执行路径由开发者预先写死，LLM 只在节点内部生成。 自主 Agent：下一步由模型根据环境反馈实时决定。

原文：书 §1.2.4.1 L369 工作流；自主 Agent §1.2.4.2 L407。

工作流自主 Agent
下一步谁决定代码（状态机 / 节点图）模型
订机票验证 → 搜索 → 付款 → 确认，顺序锁死可先搜再发现要登录，再回头验证
失败时常停在该节点或走预设错误边模型可改策略（仍要有停止条件）

实践里可以混合：合规步骤用工作流，开放式排查用自主循环。 本课只要你能指出「下一步谁说了算」。不要把 n8n / LangGraph 节点图直接叫 Agent—— 那是工作流（或混合），和使命里要造的 harness 不是同一件事。

预告（不必本课记住细节）：把三块转起来的机制叫 ReAct（想 → 做 → 看）。 代码负责执行工具、把结果追加进上下文；是否继续由模型决定。那是 0019。

常见坑 + 边界

  • 把整个产品叫「模型」：模型只是大脑。Cursor / Claude Code 是模型 + harness。
  • 以为仓库在、模型就看见：没进上下文 = 不存在。要读，得有读文件工具并且真的调了。
  • 把聊天窗口当 Agent：只有 LLM（+一点历史）没有工具，改不了环境。
  • 把节点图当 Agent：路径写死在代码里，是工作流。
  • 把环境写进公式右边：环境是交互对象，不是第三块零件；第三块是工具（接口）。
  • 本课去翻 Ch1 后半 / 去跑 s01：过密。Harness、loop、失败归因按 0018–0020 来。
