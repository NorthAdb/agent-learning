s10：Task System

把任务、前置和进度写成文件；先造节点，再连边；完成只报告这一下新解锁的下游。

来源： s10 README L13–197； code.py L63–273。

一张图

create_task × N          拿到运行时 ID，blockedBy 仍为空
  ↓ 下一轮，参数里才能使用这些 ID
update_task              追加直接前置；先校验再保存
  ↓
claim_task               pending 且直接前置全部 completed
  ↓
complete_task            本人 in_progress → completed
  ↓
Unblocked                仅「这次之后才变得可开始」的下游标题

一条记录

.tasks/task_a1b2c3d4.json
{
  "id": "task_a1b2c3d4",
  "subject": "create API endpoints",
  "description": "",
  "status": "pending",
  "owner": null,
  "blockedBy": ["task_11111111"]
}
字段创建时谁可以改
idtask_ + 8 位小写十六进制不改；必须匹配文件名
statuspendingclaim、complete
ownernullclaim 写入；complete 保留
blockedBy[]仅 pending 且未认领时追加

blockedBy 存前置 ID。完成顺序是「前置 → 后继」，和列表里的引用方向相反。

状态机

pending ──claim──▶ in_progress ──complete──▶ completed
  • 不能跳过认领，不能从 completed 退回。
  • 认领失败、完成失败返回普通说明，不抛异常。
  • 非法 ID、对已认领任务加边会抛 ValueError，工具层收成 Error:。
  • 本章工具把 owner 固定为 agent。

加边校验

  1. 目标仍是 pending，且 owner 为空。
  2. dict.fromkeys 按原顺序去掉重复 ID。
  3. 拒绝自依赖；每个前置文件必须存在。
  4. 新边若会沿前置链走回自己，拒绝成环。
  5. 已有边再添加一次：不双写，也不再做环检测。
  6. 全部通过后保存一次。

环检测 L127–139； 更新 L141–171。

开工 vs 解锁

  • can_start 只看直接前置是否都为 completed。空列表可以开始。
  • 前置文件缺失或内容非法，视为未完成。
  • 环检测会传递行走；can_start 不会。缺掉的边不会自动补上。
  • Unblocked = 完成后新变得可开始、状态仍是 pending、且自己有前置的任务标题。
  • 标题顺序来自文件名排序，不是拓扑顺序。

依赖检查 L219–231； 完成 L248–273。

创建

  • secrets.token_hex(4)：4 字节随机数，写成 8 位十六进制。
  • open(..., "x")：排他创建。撞文件就换 ID，最多 100 次。
  • save() 会覆盖该 ID。排他只保护创建，不保护后续更新。
  • ID 必须整串匹配 ^task_[0-9a-f]{8}$，路径还必须留在 .tasks 内。
